# Learning triage: dotfiles-T132-make-update-followups-a01

These are candidates only; nothing is promoted.

1. [memory:failure] On macOS, `mktemp -d` without a template ignores `TMPDIR` and creates its directory in the Darwin per-user temp directory, which the Claude Code sandbox denies (`mkdtemp failed on /var/folders/…: Operation not permitted`). Any test that runs a script calling a bare `mktemp`/`mktemp -d` (here `update_omp` and `update_hcom`) therefore fails inside a Claude seat's sandbox on origin/main too (validation §5 and §6). A worker can show red and green locally with a validation-only `mktemp` shim on `PATH` that adds a `$TMPDIR` template. That shim lives only in the scratchpad and is declared in the validation record. CI, which runs unsandboxed on both runners, is the authority for those tests.
2. [memory:decision] uv records a tool installed from a local wheel with that wheel's path in its receipt, so `uv tool upgrade <tool>` and `uv tool upgrade --all` fail on it with `Distribution not found at: file:///…whl` once the temporary wheel is gone (VERIFY 3). Index upgrades skip such tools, and `update-agent-assets.sh` moves them. In the manifest, the marker of a wheel-pinned tool is an `assets.<name>.files` URL ending in `.whl`. `upstream` is the PyPI project page and does not end in `.whl` (VERIFY 1).
3. [memory:decision] Shell scripts in this repository do not parse `home/dot_agents/agent-config.yaml`. They consume constants rendered from it (`scripts/lib/installer-pins.sh`, the `render:` blocks). Rendering a new constant was out of scope here (no manifest or renderer change), so `upgrade-tools.sh` reads the manifest's block style with `awk`. That reader is declared as a `shortcut:` comment, and a test pins it to the rendered `HCOM_PIN_VERSION`. If a second consumer appears, the better mechanism is a rendered list of wheel-pinned tools.
