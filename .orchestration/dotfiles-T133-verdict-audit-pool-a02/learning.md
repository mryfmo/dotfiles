# Learning: dotfiles-T133-verdict-audit-pool-a02

1. `uv run --no-project` still picks its interpreter from the working directory and the environment. Measured with uv 0.13.1: a `.python-version` naming a path, `UV_PYTHON`, `VIRTUAL_ENV` (even a bare `bin/python`) and a checkout `.venv` that has a `pyvenv.cfg` each made uv execute a planted interpreter. Only `env -i` together with `uv run --no-config --no-project --offline --python <absolute path>` ran none of them. Mechanism: `test_verdict_pins_tools_interpreter_and_environment_before_reading_a_pr_checkout` plants all four under `--apply` and fails when any of them runs.
2. `python -I` ignores every `PYTHON*` variable, `PYTHONDONTWRITEBYTECODE` included. Loading a checkout module with `importlib` (here `scripts/require-crit-review.py` and, through its masker, `scripts/validate-agent-assets.py`) then writes `scripts/__pycache__/` into the checkout. That untracked directory made the `--apply` guard (`git ls-files -o --exclude-standard -- scripts .schemas` must be empty) refuse every later run. Mechanism: the checker runs with `-B`; the retained `--apply` test and the pinning test each run verdict.sh several times in one checkout, so a regression fails them.
3. A gap list that a URL labels must be decided before the URL is formatted. The old condition 4 keyed saved dispositions by `.url // ""`, so a null URL or a shared check-run URL made a gap print as an empty string, and that read as "no gaps". Mechanism: the gaps are printed by `require-crit-review.py`'s own `missing_feedback`/`parse_disposition`/`commit_in_range`, one line per gap with a fixed prefix, and three regression tests cover the null, shared and duplicate cases.
4. Cap pressure: both test modules were new in this PR, so the 500-line test cap covered all of their lines. Compacting them without dropping a case used `TestCase.enterContext` (Python 3.11+; it saves two lines per `setUp`), one-line imports, and fakes as single-line strings. shfmt expands `{ a; b; }` onto separate lines but keeps `{ a && b; }` on one; inside a `|| { echo … >&2 && exit 2; }` guard a failing `echo` still fails closed, because the group's status ends the `||` list under `errexit`.
5. My validation generator printed a false exit status. `make unit-test …; echo "… $(git rev-parse --short HEAD) exit status: $?"` expands the command substitution before `$?`, so it printed the substitution's 0 instead of make's 2. Mechanism: the rerun captures `rc=$?` as the first statement after the command; every other status line in this task's generators was checked and has no substitution before its `$?`. Only the rerun block is kept, with the reason stated in validation §8a. A status line that shares an `echo` with a `$(…)` is a review check for the next validation generator.
