# M-20261015-03

- **Evidence:** `integrate-pr.sh` → `local-advisory.sh` wrote `local-finding: … not-applicable:advisory P2 owned by <owner>; evidence=git show origin/main:.orchestration/tasks/<owner>.md …` rows for owner tasks that existed only as names in the chain's `followup-owners.tsv`; the audits of 2e3ff49 (`[P2] … that task is absent from the merge base, final head, origin/main, and supplied checkout. The cited evidence command fails`) and d3bc745 (`[P2] … the named owner task is absent from origin/main at the audited base`) each raised it; the orchestrator wrote the owner tasks after the audits (0e88cadd at 07:5xZ, 75129cde at 08:2xZ).
- **Detection and why not earlier:** the task Completion clauses say the orchestrator writes the owner task "when the first advisory P2 appears, before the PR's dispositions", but nothing in the chain checks it: `local-advisory.sh` takes the owner id from `followup-owners.tsv` and writes the row and its evidence command without testing that the task file exists, so the record carried a disposition whose evidence could not be replayed until an auditor replayed it.
- **Root cause:** the owner-first rule (C-32) lives in prose (the Completion clause, the SKILL's step 10) and the chain's glue encodes only the owner's name, not its existence; a rule with no check in the tool that writes the line is skipped under time pressure.
- **Should have been:** `local-advisory.sh` (and `integrate-pr.sh` before it) refuses to write an advisory row whose owner task file is absent from the orchestrator's checkout, printing `write the owner task <id> first`, so the chain stops where the clause says the orchestrator acts; the evidence command of an advisory row names the task file's sha256 in the orchestrator's checkout (replayable before the boundary) rather than `git show origin/main:` (replayable only after it).
- **Corrections:** C-51.
