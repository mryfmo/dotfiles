# refkit-P4: 学びの候補（トリアージ）

## 候補 1: リンターのテンプレート整合チェック（E024 相当）に「キー追加」を提案する指示は、既存の accepted 文書を壊し得る

**観察**: task_file はテンプレートへの新規キー追加（`proposed-on`）と、既存の accepted な文書へのキー追加禁止を同時に指示していたが、リンターの front-matter 整合チェックは文書種別ごとに「テンプレートとのキー集合完全一致」を機械的に検査するだけで、`status` に応じた例外は無い。この組み合わせは、リンターを変更しない限り必ず矛盾する。
**一般化できる点**: 「テンプレートにキーを追加し、一部の既存文書には追加しない」という指示を受けたら、まずそのテンプレート整合チェックが文書種別全体に無条件で適用されるのか、それとも文書ごとの条件分岐を許すのかを、リンターのコードを実際に読んで確認する。読まずに指示どおり両方を実行すると、指示が暗に前提していた（別タスクでの）リンター変更が完了するまで、既存の合格が壊れる。
**昇格の判断**: 判定者に一任。refkit-P3 の候補（既存 RULE-ID の転用、新規 ID 波及）と同種のパターンであり、汎用的に有用。

## 候補 2: 生成された「証跡」ファイルは、対象の変更に追随して芋づる式に陳腐化する

**観察**: ADR に新しい Mermaid 図を 2 つ追加しただけで、`04_TRACEABILITY.md`（既知）に加えて `evidence/mermaid_render.json`（新規）も陳腐化し、リンターの新しいエラー（E103）が発生した。`evidence/`はこのタスクの`allowed_files`に含まれておらず、対応する再生成スクリプト（`render_mermaid.py`）の実行も許可されていなかった。
**一般化できる点**: 「文書だけを編集する」タスクでも、その文書が figure/表/追跡表など「証跡付きの生成物」の入力になっている場合、変更のたびに複数の証跡ファイルが連鎖的に陳腐化し得る。着手前に、変更対象の文書を入力とする生成物・証跡の一覧（`kit.toml`の`docs`設定や、リンターの E1xx 系チェック）を洗い出し、どれが`allowed_files`の範囲内で再生成できて、どれができないかを事前に把握しておくと、後から複数の「新規許容エラー」を後追いで発見せずに済む。
**昇格の判断**: 判定者に一任。

## 候補 3（重要度：高）: グローバル prettier フォーマッタの `.prettierignore` は起動時の cwd に依存する

**観察**: `refkit-P0-05` で追加した `.prettierignore` は、リポジトリルートを cwd として実行した `prettier --check`/`--write` では正しく機能するが、cwd が異なる（例：`/tmp`）状態で絶対パスを渡すと機能しない（無視されず再整形される）ことを実験で確認した。実際のグローバル PostToolUse フック経由での書き込みで、新規作成した 2 つの ADR ファイルが実際に再整形された事実が、この cwd 依存性を裏付けている。
**一般化できる点**: `.prettierignore`／`.gitignore` 系の無視ファイルに依存する保護策を導入する際は、それを呼び出す実際のプロセス（今回は Claude Code のグローバル PostToolUse フック）の起動 cwd を確認し、その cwd から見て無視パターンが解決されることまで確認する。リポジトリルートで手動再現しただけでは不十分。
**昇格の判断**: 高優先度。`.prettierignore`／`ruff.toml` はこのタスクの `allowed_files` に含まれないため、ここでは修正していない。フォローアップタスクとして、フックの起動 cwd をリポジトリルートに固定するか、`--ignore-path` を明示指定する対応を推奨する（report にも記載）。
