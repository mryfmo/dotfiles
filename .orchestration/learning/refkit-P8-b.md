# refkit-P8-b: 学びの候補（トリアージ）

## 候補 1: 「本枝には未反映」という記述は、統合（merge）が起きた瞬間に真偽が反転する時限性を持つ

**観察**: refkit-P8-a では、複数ワークツリーが並行して進む中で「プログラム全体としては受入済みだが、この枝のコードには無い」という事実を正確に書いた（[[refkit-P8-a]] の学び候補 1）。ところが、そのわずか数十分後に統合（merge 1d5b093）が起こり、その記述は即座に古くなった。「今この瞬間のコードの状態」を文書に埋め込むと、コードが動く（merge される）たびに文書側の追従が要る。
**一般化できる点**: 「この枝には無い」「未反映」のような、ブランチ・時点に紐づく記述を文書に書くときは、それが恒久的な事実（設計判断そのもの）ではなく、一時的な進行状況のスナップショットであることを自覚する。可能なら、直後の統合タスク（本タスクのような）が既に計画されている前提で、「どこを見れば最新の真偽が分かるか」（ここでは `grep -c gherkin_source` のような 1 コマンド）を書いておくと、後続タスクが機械的に確認・是正できる。実際、refkit-P8-b の task_file 自身がこの手を使っていた（「Verify with `git log --oneline -3` and `grep -c gherkin_source` before editing」）。
**昇格の判断**: 判定者に一任。今後も同様の並行ワークツリー統合が起きるプログラムでは、直前タスクの記述に同じ時限性の問題が起きる。

## 候補 2: 「変更を指示されたが、確認したら既に正しかった」場合は、変更せずその判断を報告するのが正しい

**観察**: task_file item 3 は 03_CONVENTIONS.md の §3・§5・§7 を「確認せよ」と指示していたが、実際に読むと、いずれも既に統合後の実装と一致していた（`[ids] prefix` の記述、`last_run` の無条件 evidence 要求、E104 と `[mermaid] allowed_types` の対応）。同様に 06_TEST_STRATEGY.md §5 のテスト名行・W160 行にも、そもそも枝名や「未反映」という文言は入っていなかった。
**一般化できる点**: task_file の「item X を直せ」という指示は、直す必要が実際にあるかどうかの検証を含んでいない場合がある（執筆時点での推測に基づく）。読んでから「既に正しい」と分かったら、無理に文言を変えて余計な diff を作らない（ponytail：正しいものを書き換えるのは無駄な変更）。その代わり、報告書に「確認したが変更不要だった」と明記して、判定者が「見落としではなく確認済みである」と分かるようにする。
**昇格の判断**: 判定者に一任。他タスクでも「一覧の全項目を機械的に変更する」より「一覧の全項目を確認し、必要な項目だけ変更する」方が正しい診断姿勢。
