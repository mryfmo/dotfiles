# U17 Claude Code: secret-file protection the Linux sandbox enforces — brief

GOAL
The managed Claude Code settings protect secret files at both layers on macOS and Linux, in the forms the Claude Code documentation defines: the Read/Edit permission rules guard Claude's own file tools, and the Bash sandbox guards every subprocess through `sandbox.credentials.files` and `sandbox.filesystem.denyRead`. After the change `claude doctor` on a Linux host no longer lists `Read(id_rsa*)` or `Read(id_ed25519*)`, the SSH directory and `.env` files are unreadable from sandboxed commands on both platforms, and the Read tool can no longer open a plain `.env`.

CONTEXT (every fact with its source)
1. The symptom. On a Linux host, `claude update` and `claude doctor` (Claude Code 2.1.309) print: `Warning: Glob patterns in sandbox permission rules are not fully supported on Linux` / `Fix: Found 4 pattern(s): Read(.env.*), Read(id_rsa*), Read(id_ed25519*) (1 more). On Linux, glob patterns in Edit/Read rules will be ignored.` (operator paste, 2026-10-24 JST). On macOS `claude doctor` 2.1.309 prints no such line (coordinator run 2026-10-23T22:3xZ); the binary's function is `getLinuxGlobPatternWarnings` (strings of `claude.exe`). The fourth pattern is `Edit(.env*)`. `Read(secrets/**)` is not counted: a trailing `/**` renders as the directory deny `secrets` (the session's sandbox config lists `"secrets"` and `"config/credentials.json"` as plain paths beside the three globs).
2. What the rules match (code.claude.com/docs/en/permissions, "How path patterns match"): `path` or `./path` is a "Path relative to current directory"; a bare filename matches at any depth under that directory; `~/path` is from the home directory; `//path` is absolute. So `Read(id_rsa*)` and `Read(id_ed25519*)` match only under the session's working directory and never `~/.ssh/id_*` in a project session: today they protect nothing where the keys live. Same page: "Read and Edit deny rules apply to Claude's built-in file tools, to file commands Claude Code recognizes in Bash, such as cat, head, tail, sed, and tee … They don't apply to … arbitrary subprocesses that read or write files indirectly … For OS-level enforcement that blocks all processes from accessing a path, enable the sandbox."
3. What the sandbox does (code.claude.com/docs/en/sandboxing): the table row "`Read` and `Edit` deny rules | Block access to specific files or directories" (permission rules are merged into the sandbox config); "Default read behavior: read access to the entire computer, except certain denied directories. This default still allows reading credential files, so protect credentials you don't want commands to read."; "`sandbox.credentials` … For entries with `"mode": "deny"`, file paths are denied for reads inside the sandbox, the same restriction that `filesystem.denyRead` applies" with the example `{ "path": "~/.ssh", "mode": "deny" }` (a directory is accepted); the `denyRead` wildcard example `"~/**/.env"` ("A wildcard deny holds inside a wider allow the same way an exact path does"); the admin note "Add `sandbox.credentials` entries for credential directories such as `~/.aws` and `~/.ssh` … since the default read policy still allows them". Relative sandbox paths resolve against the settings file's directory (`.` in `~/.claude/settings.json` is `~/.claude`), so a project-relative sandbox entry is not expressible from user settings; `~/**/...` is the documented form.
4. Linux enforcement: anthropics/claude-code#92684 (open, labels area:sandbox, area:security, platform:linux): `sandbox.filesystem.denyRead` enforces literal, trailing-`**` and mid-path globs on Linux (EACCES measured), while the glob forms of Edit/Read permission rules are the ones the Linux sandbox drops. CHANGELOG 2.1.299 "Improved sandboxed Bash on Linux: Esc and Ctrl-C now work while wildcard read rules are being expanded for a command" (a `denyRead` wildcard is expanded per command on Linux; its cost on a large home directory is unmeasured, see the handout row), 2.1.304 "Fixed sandboxed commands failing to start on Linux when a `sandbox.filesystem.denyRead` glob contains brackets".
5. The tool-layer recommendation (code.claude.com/docs/en/settings, "Edit a settings file"): `"deny": ["Read(./.env)", "Read(./.env.*)"]`. The current list has `Read(.env.*)` but no `Read(.env)`: the Read tool may open a plain `.env` today.
6. Current code: `render_claude_sandbox` (scripts/generate-agent-configs.py:387-410) emits `filesystem.allowWrite` only; `render_claude_settings` copies `permissions.deny` verbatim; `validate_claude_sandbox` (scripts/validate-agent-assets.py:303-356) checks `allowWrite` extras are glob-free `/` or `~/` paths; `test_claude_deny_rules_use_edit_for_file_mutations` (tests/unit/test_generate_agent_configs.py:2542) asserts `- Edit(.env*)` is in the manifest. The Makefile targets: `make unit-test`, `make validate-agent-assets`, `make render-check` (`generate-agent-configs.py --check`); the generating command is the same script without `--check` (read the Makefile).
7. The dotfiles deploy `~/.ssh/config` from `home/private_dot_ssh/private_config`; the repository copy stays readable. `chezmoi apply` and `make update` run in the operator's terminal outside Claude sessions (README "Claude Code sandbox", the manifest's sandbox comment), so a `~/.ssh` read deny inside the sandbox does not break them.
