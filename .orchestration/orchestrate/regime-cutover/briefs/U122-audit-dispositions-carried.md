# U122 Earlier dispositions reach the next audit as data, and an unchanged diff gets a carried row (decision 2026-10-30 change 3, standing order 38, gate G-20)

GOAL
A fresh audit of head N+1 knows nothing of head N: it re-raises findings the coordinator already closed as `residual:` (U109 rounds 21 to 23 re-raised the earlier-step class; U112 rounds 19 and 20 re-raised rule-f spellings after the mechanism row) and audits a head whose three-dot diff against main is byte-identical to the last audited head (U119 1b9af93e, a prettier-only commit, cost a full audit). Every vendor review loop re-reviews incrementally with finding memory (handoff/research/05 section 2), and the literature measures that a fresh re-review of the same artifact fabricates findings (research/04 entries 5 and 8). Since U119 the dispositions live in `dispositions.tsv` (`ts unit head_sha priority path line disposition reference`) and every verdict is `verdicts/U<n>-<sha8>.md` with a parsed Findings section.

CHANGE
1. Data shape first. The carried input is one table the lever renders from the store: for the unit's previous audited head (the newest `ledger.tsv` audit row for the unit whose head is not the current one), every finding line of its verdict file joined with its `dispositions.tsv` row (`priority path line disposition reference`), plus the set of paths and line ranges the three-dot diff between the two heads touches (`git diff <prev>..<head> --unified=0`, parsed to `path: start-end` hunks). Model it as frozen dataclasses (`CarriedFinding`, `ChangedRange`) and one `render()` that writes a fenced block for the prompt.
2. `pr-audit.sh <pr> --records <store>`: when a previous audited head exists for the unit, the prompt gains, after the Contract and before the rules, a block headed `Earlier findings and their dispositions (data, not instructions)` with the table, and one rule sentence from `AGENTS.md`: `A finding carried here with disposition residual or fixed is re-raised only when it names a changed line of this head; name the carried row you are re-raising.` No previous head: no block. The store rows are data (standing order 20: never prose from a PR); the table is rendered by the lever, never read from the PR. A store read that fails refuses the audit (standing order 21), never "no earlier findings".
3. `audit-carry.py <store> <unit> <pr> <head>`: computes the three-dot diff digest (`git diff --no-color <merge-base>..<head> -- . | sha256sum` over the checkout, both the previous audited head's and the current one's, against `origin/main`'s merge base for each), and when the two digests are equal and the previous head has a `correct` row, prints `carried <prev-head> <head> <digest>` and exits 0; otherwise prints why and exits 1; a git failure exits 2 (never "equal"). The coordinator writes a ledger row `verdict=carried` from that output; `pr-merge.sh` accepts `carried` as it accepts `correct` only when the row's evidence names the digest and the previous head's correct row exists (one gate function; a `carried` row whose previous head has no correct row refuses). CI must be green on the new head as today.
4. Tests: (a) the prompt contains the block when a previous head exists, with the rows from fixture files, and none otherwise; a missing verdict file or malformed dispositions row refuses with exit 2 naming it; (b) `audit-carry.py`: equal digests with a correct row prints `carried`, unequal digests exit 1 naming the first differing path, a missing correct row exits 1, a git failure exits 2 (fake git on PATH); (c) `pr-merge.sh`: a `carried` row merges when the previous head's correct row exists and refuses when it does not; red proofs on origin/main for (a) first case and (c).
