# U174 two tests stop failing healthy Linux runners: the checkout-guard pointer test accepts git's own wording, and the holder scan waits for a reader still inside its open

GOAL
Two unit tests failed healthy GitHub runners on 2026-11-04 with the code under test unchanged. First, `tests/unit/test_checkout_guard.py` `test_a_separate_git_directory_whose_name_ends_in_lf_is_installed_into` (`:767-812`) ends with a documentation pin, `self.assertIn("gitfile does not point to a valid repository", err)` (`:812`), after proving that a `gitdir:` pointer file naming the LF directory is refused (`:810-811`); git's wording for that refusal differs by version, and three runs printed `fatal: not a git repository: (null)` instead (run 41756000929, ubuntu-24.04 server, 01:51Z; main's run 41774055657 at 40bf5241 on the required ubuntu-24.04 server cell, runner image 20261015.610, job 126390162293; PR 652's run on the ubuntu-26.04 canary, job 126411081083). Second, `tests/unit/test_trusted_exec_contract.py` `test_a_recorded_read_names_its_holder` (U166) failed on the ubuntu-26.04 canary (job 126411081083) with the record `opened for reading by no pid whose descriptors this user can read (175 unreadable)` for the in-thread reader, while the `cat` reader on the same run was named: a reader still inside its blocking `open()` of the FIFO already counts as a reader for the probe's non-blocking write-open (the kernel raises the reader count before the open sleeps), but its descriptor is not in its table until that `open()` returns, so the scan `WorkerRoot._holders` runs in `tests/unit/trusted_exec_contract.py` can look before the entry exists. After this unit the pointer test asserts the refusal and accepts either wording, and the holder scan repeats itself for at most 200 ms until it names a holder, so a reader that the write-open just woke is named once its `open()` returns, while a run with no readable holder still ends with the unreadable count.

CONTEXT
Measured 2026-11-04 on `origin/main` 5ebd07b4. The pointer pin (`test_checkout_guard.py:806-812`) exists to say why the symlink is the one form (a pointer naming the LF directory resolves to the stripped sibling, which is no repository); the behaviour it proves is git's `--git-dir` query exiting nonzero through that pointer, which held on every failing run; only the message changed. `WorkerRoot._holders(self, writer)` (`trusted_exec_contract.py`, after `_not_sentinel`) scans `self.PROC_ROOT` once: for each numeric entry it lists `fd`, stats each link and compares `(st_dev, st_ino)` with `self._dev_ino`, and returns `by pid <pid> (<comm>, ppid <ppid>: <cmdline>)` per holder, `by no pid whose descriptors this user can read (<n> unreadable)` when none is found, or `reader not identified (no /proc)` when the root cannot be listed; `_attempt` calls it as `self.reads.append(f"{self.input} opened for reading {self._holders(fd)}")` while the probe's writer `fd` is still open (the reader is released only by the `finally` that closes it). The three scratch-tree tests of U166 round 2 (`test_the_holder_scan_names_a_holder_from_the_descriptor_table`, `..._tolerates_a_pid_that_exits_mid_scan`, `..._opens_no_fifo`) drive the scan through `PROC_ROOT` pointed at a scratch tree and a helper `holder_scan(probe)` that opens its own reader first. On the failing run the scan found no holder among the readable pids: the in-thread reader's `read_bytes()` call was inside `open()`, woken by the probe's write-open, and its descriptor appeared after the scan.
