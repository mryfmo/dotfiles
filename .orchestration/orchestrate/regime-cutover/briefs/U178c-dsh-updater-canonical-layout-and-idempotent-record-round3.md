# U178c the updater accepts only the layout it makes, re-records before it prunes, and never lets a cleanup change its status (round 3 of U178)

GOAL
Round 2 of U178 (PR 656, head ee4a2a49, `verdicts/U178-ee4a2a49.md`) judged the head correct with six P2 findings; three are at or above the weight threshold and must be answered before the merge, and the three under it cost a few lines each. (1) f2 s6: after a failed record whose restore also failed, a receipt at the pin that still names the prior tree (a U172-era receipt) lets the next run take the already-installed exit and prune the tree the receipt names, so the receipt points at a missing path for good. (2) f2 s5: a `current` that reaches the active tree indirectly (`current -> dsh-v0.1.0/relay`, a symlink inside an older tree, or `current -> dsh-v0.1.0/../active`) passes the shape checks, and the prune removes `dsh-v0.1.0`, the directory the link traverses, leaving `current` dangling with exit 0. (3) f10 s2: the two `pwd -P` reads of `dsh_prune_older` have no failure-injection test. Under the threshold: (4) f2 s4 the EXIT trap's `rm` is unguarded under `errexit`, so a cleanup that fails turns a WARN with exit 0 into exit 77; (5) f2 s3 after a restoring `ln -sfn` that unlinked `current` before failing, the message still says `current` names the new tree; (6) f2 s3 the rollback's `rm -f` of `current` is unguarded under `errexit` and ends the step before its message. The cause of (2) and of the two rounds before it is one: the step tries to repair or tolerate layouts it never made, and each tolerated layout is a new state for the next failure to find. After this head the step accepts exactly one layout and refuses every other before any download: `current` absent, or a symlink whose target is `${DSH_HOME}/dsh/<name>` with no `/` in `<name>`, `<name>` a directory that is not a symlink; `bin/dsh` absent or a regular file; the receipt absent or exactly one JSON object. Within that layout the prune needs no path resolution (so (3) dissolves), the already-installed exit re-records before it prunes (so (1) cannot arise), and no cleanup read changes the step's status (so (4) and (6) cannot arise).

CHANGE
1. The canonical layout (f2 s5). Right after the existing `current` symlink check and before the receipt read, when `current` is a symlink: read its target (`readlink`, status checked as now), anchor a relative one at `${DSH_HOME}/dsh/` as now, then refuse with exit 1 (`update_deepseek_harness: %s points at %s, which is not a directory directly under %s/dsh; the step repairs only the layout it makes (move the link aside and rerun make update); nothing installed, nothing recorded.`) unless all hold: the target starts with `${DSH_HOME}/dsh/`, the remainder holds no `/` and is not `.` or `..`, and the target is a directory that is not a symlink (`[ -d ] && [ ! -L ]`). The installed-state read then uses that target. Tests: `current -> dsh/dsh-v0.1.0/relay` (relay a symlink to the real tree), `current -> dsh/dsh-v0.1.0/../dsh-v0.2.1-rc.5.abc123` and `current -> dsh/dsh-v0.1.0` where `dsh-v0.1.0` is itself a symlink to a directory: each exits 1 with that line, makes no `curl` call, records nothing and leaves every path as it was.
2. `dsh_prune_older` without path resolution (f10 s2 dissolves). With item 1 the target of `current` is a direct child of `dsh/`; the helper removes a directory under `dsh/` when its name matches `dsh-v*` or `.staging.*`, it is a directory and not a symlink, and it is not the inode of `current`'s target (`-ef`); the two `pwd -P` reads and the ancestor check go, with their comments; the shdoc header says the layout item 1 enforces is why no resolution is needed. The round-2 tests of the helper keep their observable claims (an older `dsh-v0.1.0` goes, `keep-me` stays, a failed removal is a WARN, the already-installed exit prunes); the nested-current test of round 2 becomes item 1's refusal.
3. Re-record before the prune on the already-installed exit (f2 s6). On that exit, when the receipt's recorded `paths` for the step are not exactly `[<DSH_HOME>/dsh/current, <DSH_HOME>/bin/dsh]` (read with `jq -r '.steps["update_deepseek_harness"].paths // [] | join("\n")'`, status checked, a failed read a refusal), call `manifest_record` with the step's current arguments before `dsh_prune_older`; a failed record there is exit 1 with `the record could not be rewritten; the older trees are kept` and no prune. Test: a receipt at the pin whose `paths` name `dsh/<tag>` (the U172 form) with a good tree under `current` and an older tree at `dsh/<tag>`: the run exits 0 with the already-installed line, the receipt's `paths` become the two current paths, and only then is the older tree gone; a second test where `manifest_record` fails on that exit: exit 1, the older tree still present, the receipt unchanged.
4. Cleanups never change the status (f2 s4, f2 s3). The EXIT trap becomes `trap 'rm -rf ${download_dir:+"${download_dir}"} ${tree:+"${tree}"} ${wrapper_tmp:+"${wrapper_tmp}"} || :' EXIT`; the rollback's `rm -f "${DSH_HOME}/dsh/current"` and any other cleanup `rm` inside the function carry `|| :` with the message naming what remains when it fails (`current could not be removed and still names the new tree <tree>, which is kept`), and `tree` is emptied in that case so the trap keeps it. Tests: an `rm` that fails on the trap's cleanup after a failed download: exit 0 and the WARN line; an `rm` that fails on the rollback's `current` removal after a failed record with no prior target: exit 1, the message, the new tree still present and `current` still on it.
5. The restore message says what is there (f2 s3). After a restoring `ln -sfn "${prior_target}"` fails, test `[ -L "${DSH_HOME}/dsh/current" ]`: when the link is absent print `current is absent; the prior tree <prior> and the new tree <tree> are on disk under dsh/; nothing recorded; the next make update reinstalls`, else the existing `still names the new tree` line; the new tree is kept in both cases (`tree=""`).
