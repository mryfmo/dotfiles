CHANGE
1. `path_patch` runs with `--unified=3`. Each `@@ -<a>[,<b>] +<c>[,<d>] @@<rest>` line is kept with its two number pairs replaced by nothing (`@@  @@<rest>` or the same form every time; a line starting with `@@ ` that does not match the shape is a refusal naming the path, exit 2, never dropped). The `index ` lines are dropped as now. Every other line is kept byte-exact, the context lines (a leading space) included.
2. The occurrence index. For each hunk of a path with a merge-base blob (status `M`, `T` or `D`, never `A`), compute the hunk's old-side window: the sequence of its context and `-` lines without their first character, in order. Let `start` be the hunk's old start line `<a>` from the `@@` line before it was blanked (git's numbering, 1-based; a hunk with `<b>` 0 has no old lines and its window is its context alone, anchored at `<a>+1`). The index is the number of occurrences of the window (as consecutive lines, compared byte-exact) in the merge-base blob's lines that start before `start`; the window itself at `start` is not counted. Write the index into the hashed bytes right after the blanked `@@` line as its own line `@@occurrence <n>` (a shape git never emits). A merge-base blob the scratch repository cannot read is a refusal naming the path (exit 2). The blob is split on `\n` alone and compared as bytes; a file without a trailing newline is handled by the split (the last element has no newline), and a `\ No newline at end of file` line in the patch stays part of the hashed text as now.
3. Binary paths. When the patch text of a path holds a line starting with `Binary files ` (or `GIT binary patch`), append both blob ids from the raw record to the hashed bytes (`binary <old blob> <new blob>` as one line), whatever else the patch holds; the hunkless case keeps its current behaviour (which this rule now covers too). A symlink's own content lines (the link target, shown as `-`/`+` lines) stay part of the text.
