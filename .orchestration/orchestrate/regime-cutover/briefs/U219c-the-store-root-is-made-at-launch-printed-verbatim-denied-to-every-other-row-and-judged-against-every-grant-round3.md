GOAL
The round-2 audit of PR 733 (verdicts/U219-985b7c04.md, class write-boundary) found two P1 and one P2, all in hcom-seat's handling of the store root. (1) P1 hcom-seat:2161: `store_root_phys` is placed in `extra`, and every `extra` entry is resolved again through `physical_path` in `seat_write_roots` (:2170-2172), so a directory-to-symlink swap of the root during `seat_roots_out` (:2219), restored right after, rendered another directory (`~/.config/autostart` in the auditor's probe) as the orchestrator's write root; the held value must be printed verbatim, as the dsh row's `held=${state_root_phys}` is (:2159, :2173). (2) P1 hcom-seat:1981: `store_root_overlap_check` judges `HCOM_DIR` alone; a worker whose `~/.omp/run` (or any other rendered write root) is a link to the store root launches with the store in `allowWrite` and no covering `denyWrite`. (3) P2 hcom-seat:1815: an absent root is granted but never made before sandbox entry, and srt 0.0.81's Linux backend skips an absent write path (and an absent deny path), so the first regime-init inside a Linux orchestrator seat could not write it and the worker's deny would be void; the launch makes the root (every component under `umask 077`, each held to a real 0700 directory of this user, a planted entry refused by name) before any settings file is rendered, as it makes `~/.omp/run` (:2847) and as regime-init makes the root.
