# U37 Seat logins on a remote host: the browser is on the laptop, the seat is on Ubuntu — brief

GOAL
An omp seat on the Ubuntu host (reached from macOS through `herdr --remote <ssh-target>`) gets its Claude and ChatGPT logins without a browser on Ubuntu, by the two flows the vendors document for exactly this case, and `make doctor` on any host says which profile is logged in through which route. Nothing copies a token between hosts by hand, no secret enters the repository, and each host owns its own refreshes. The operator's report (pane, 2026-10-24T06:5xZ): 「macOS: ghostty+herdr+omp、Ubuntu: ghostty+herdr+omp、macOS の ghostty+herdr から Ubuntu の omp を起動する際に OpenAI ChatGPT、Anthropic Claude Code の OAuth がブラウザ起動でローカル認証となりリモートからは認証できない」.

CONTEXT (measured 2026-10-24T07:0xZ)
1. ChatGPT (openai-siwc): the extension binds `127.0.0.1` only, on `PREFERRED_PORT = 1455` when free, else a random port (`src/oauth.ts:12,179-190`), and hands the authorization URL to omp's login UI through `callbacks.onAuth({ url, instructions })` (`:64-65`); the registration record is `~/.omp/profiles/<profile>/agent/openai-siwc/registration.json` = `{ hostId: urn:uuid:…, clientId?, accountId? }` (`src/store.ts:5-8`, created by `newRegistration()` `:19-20`), tokens live in the profile's `agent.db` (extension README step 3). The SIWC docs allow only a `127.0.0.1` loopback redirect ("Do not substitute with `localhost`"; the port may vary per attempt) and describe the remote case in "Self-hosted VMs": a `127.0.0.1` callback reaches the computer running the browser, so either complete OAuth locally and transfer the protected credential file while preserving the VM's own `ext_agent_host_id`, after which the VM owns the refreshes; refresh tokens rotate, so one credential session cannot be shared by two hosts, and one issued `client_id` may serve several hosts, each with its own host ID (token-sharing-open-source.md "A client vs. an agent host"; sign-in.md `redirect_uri`, step 5). Consequence: the Ubuntu seat needs its own session, obtained either through an SSH local forward of the loopback port (`ssh -L 1455:127.0.0.1:1455 <target>`: the macOS browser's redirect to `127.0.0.1:1455` lands on Ubuntu's listener, which is the documented loopback contract satisfied end to end) or through the transfer path, which moves the macOS session rather than copying it.
2. Claude (pi-claude-bridge → Agent SDK → Claude Code child): the child uses the host login (docs/pi-claude-bridge.md:82-87; Keychain on macOS, `~/.claude/.credentials.json` mode 0600 on Linux per the Claude Code authentication doc "Credential management"). The same doc gives two browserless routes: (a) `/login` or `claude auth login` over SSH shows the URL, and when the browser cannot reach the local callback it shows a code to paste at `Paste code here if prompted` ("common in WSL2, SSH sessions, and containers"); (b) `claude setup-token` on the laptop mints a one-year OAuth token for `CLAUDE_CODE_OAUTH_TOKEN` (Pro/Max/Team/Enterprise; applies to the CLI and the Agent SDK; not read in bare mode; precedence rank 5, above the `/login` credential). Reports of (a) failing in some SSH setups exist (anthropics/claude-code issues #35714, #48048, #42965, 2026), so the handout gives (b) as the fallback.
3. Reaching Ubuntu: `herdr --remote <ssh-target>` attaches through SSH to a remote herdr server (`herdr --help`); `herdr machine` manages saved SSH machines. The seats on Ubuntu are launched there by `hcom-seat` in the Ubuntu herdr server; the logins are per host (standing order 4: a login is an operator step, reported as an exact command, never run by a seat).
4. Standing order 6: tokens are never printed, logged or written by a seat; the setup-token route therefore ends in the operator's hands: the operator stores the token on Ubuntu in a host-local file outside the repository (`~/.config/claude-code/oauth-token`, mode 0600, created by the operator), and the login shell exports `CLAUDE_CODE_OAUTH_TOKEN` from that file when it exists (one `[[ -r … ]] && export` line in the managed zsh/bash environment, no secret in dotfiles).

DESIGN (the data shape first)
- A per-host login record per route: Claude = `~/.claude/.credentials.json` or the Keychain or `CLAUDE_CODE_OAUTH_TOKEN`; ChatGPT = `registration.json` + the `agent.db` record of the profile. `check_seat_logins` reads only presence and mtimes (never contents) and prints one line per (profile, route): `audit openai-siwc: registered (host urn:uuid:…, client oaiapp_…), tokens mtime <ts>` or `absent`; `orchestrator claude-bridge: login present (credentials file 0600, mtime <ts>)` / `(env token)` / `absent`.
- `openai-siwc`: `OPENAI_SIWC_CALLBACK_PORT` (default 1455) so the forward and the listener agree; fail with a clear message when the port is taken instead of falling back to a random one while the variable is set; `omp` login UI already shows the URL (measure in a scratch HOME with `BROWSER=false`). A `registration seed --client-id <id>` subcommand (or a documented hand edit of `registration.json`) lets Ubuntu reuse the macOS `clientId` with a fresh `hostId`, so the ChatGPT account shows one agent and the returning sign-in skips the consent screen (sign-in.md "Expected returning sign-in").
- Handout rows (operator, from macOS): (1) `ssh -L 1455:127.0.0.1:1455 <target>`; (2) on Ubuntu `OPENAI_SIWC_CALLBACK_PORT=1455 omp --profile audit`, `/login openai-siwc`, open the shown URL in the macOS browser, see "Signed in" in the tab; (3) `claude auth login` on Ubuntu in the same SSH session, open the URL on macOS, paste the code; fallback (3b) `claude setup-token` on macOS, then on Ubuntu write it to `~/.config/claude-code/oauth-token` with mode 0600; (4) `make doctor` on Ubuntu shows every profile logged in; (5) `hcom-seat <role>` there. Each row with `source` and `dry-run` columns.

ADDENDUM 3 (orchestrator-sari, 2026-10-24T07:2xZ): the operator's direction 「tailscale＋ssh で仕組み化」
The network layer is the tailnet, the transport is SSH. Measured on this host: `tailscale` is installed (`/opt/homebrew/bin/tailscale`, node `macbook-pro` 100.112.230.94) and the dotfiles install it on the Ubuntu client (`home/.chezmoiscripts/ubuntu/run_once_53-client-install-tailscale.sh.tmpl`); README:78-84 already keeps mosh inside the tailnet. Design changes:
1. The Ubuntu machine entry in `home/private_dot_ssh/private_config` uses the MagicDNS name (`HostName <node>.<tailnet>.ts.net`) with the two forwards of ADDENDUM 2; `herdr machine add` saves that entry, so `herdr --remote` rides the tailnet. OpenSSH on Ubuntu is reached only over the tailnet (the Tailscale KB "Protect your SSH servers using Tailscale" is the pattern).
2. Tailscale SSH (`tailscale up --ssh`, Tailscale as the SSH server) is measured before it is relied on: tailscale/tailscale issues #6575 and #5091 report that it did not carry `-L`/`-R` forwards, so the forwards go through OpenSSH unless the measurement shows Tailscale SSH now forwards; record the result in the handout.
3. The laptop's URL opener (ADDENDUM 2 item 2) may be exposed to the tailnet with `tailscale serve` (HTTPS on the laptop's tailnet name, reachable only from tailnet peers and restricted to the Ubuntu node by an ACL) instead of the `RemoteForward`; choose one after measuring both, prefer the one with fewer moving parts, and keep the host allow-list in either case.
4. The pre-flight detects remote versus local from `SSH_CONNECTION` and names the peer from `tailscale status --json` (self and peer `DNSName`), so the handout and the opener target need no hand-typed addresses.
SCOPE gains `install/ubuntu/client/tailscale.sh` only if an `--ssh` or ACL step belongs there; the tailnet ACL itself is an operator step (admin console), written as a handout row with its exact JSON snippet.
