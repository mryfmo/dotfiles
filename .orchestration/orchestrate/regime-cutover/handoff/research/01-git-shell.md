### 1.2 Exit status of `git config --get`

The page lists exit codes 1 (section or key invalid), 2 (no section or name), 3 (config file invalid), 4 (cannot write), 5 (unset of a missing key, or multiple lines match), 6 (invalid regexp), with 0 on success (doc, git-config DESCRIPTION). It does not list a code for "key not set". Measured on 2.56.0:

| Case                                        | Status | stderr                                                  |
| ------------------------------------------- | ------ | ------------------------------------------------------- |
| key not set                                 | 1      | none                                                    |
| key name without a section                  | 1      | `error: key does not contain a section`                 |
| `--default ''` on an unset key              | 0      | none                                                    |
| `-f <file>` unparsable                      | 128    | `fatal: bad config line 1 in file ...`                  |
| `-f <file>` missing                         | 1      | none                                                    |
| `-f <file>` unreadable (mode 000)           | 1      | `warning: unable to access ...: Permission denied`      |
| repository `.git/config` unreadable         | 128    | `warning:` then `fatal: unable to access '.git/config'` |
| repository `.git/config` unparsable         | 128    | `fatal: bad config line`                                |
| global file unparsable, key present locally | 128    | `fatal: bad config line`                                |
| global file unreadable, key present locally | 0      | none (the global file is ignored)                       |
| `include.path` to an unreadable file        | 128    | `fatal: unable to access`                               |
| `include.path` to a missing file            | 0      | none (silently skipped)                                 |
| configured empty value                      | 0      | none, prints an empty line                              |

Two consequences. The documented code 3 for an invalid file is not what 2.56.0 returns on these paths (128), so no reader may encode 3. Status 1 is overloaded: unset, invalid key name and an unreadable `-f` file all return 1, and only the last two write to stderr. A reader that maps 1 to "unset" is correct only when the key is a literal and the source is the repository or global file, never an explicit `-f` file.

### 1.3 Does the final design match

The P3 final design (records-sync.sh at 65f630b6) and what the documentation and probes say about each piece.

- Scratch repository from `git init --bare --template=`, every command there as `git --git-dir=<scratch>` under `GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_NOSYSTEM=1`. Matches the documented level switches. The repository level of that repository is the five keys init wrote plus whatever the script writes. No hooks directory exists, so no hook can run there whatever `core.hooksPath` is (it is unset).
- Every inherited `GIT_*` removed by a `compgen -e` loop with a second pass that refuses a survivor. Matches and exceeds the githooks advice. This is the only thing that closes `GIT_CONFIG_PARAMETERS` and `GIT_CONFIG_COUNT`, because `GIT_CONFIG_GLOBAL=/dev/null` does not touch the command scope (measured: both override repository config).
- Identity as `GIT_AUTHOR_*`/`GIT_COMMITTER_*` on `commit-tree`. Matches the documented top of the precedence (measured on `commit-tree`).
- `-c core.fsmonitor=false -c core.hooksPath=/dev/null` on the one `ls-files` in the checkout. Both documented. Measured: necessary (the hook ran under `ls-files` without it) and sufficient for those two channels. `ls-files` wrote no index in the probed modes, so `post-index-change` is not a live channel for it, but the `hooksPath` override costs nothing and covers a future mode.
- Refusal when `ls-files` writes anything to stderr. Necessary: the documented status does not cover an unreadable directory (exit 0 with a warning, measured) and the page documents no status for it. This refusal is the only mechanism that turns the U101 round 11 defect (files becoming deletions) into a fail-closed stop. A `find -type d` walk plus a `-r -x` test per directory, done before the listing, is the second guard.
- `hash-object -w --no-filters` on each file read from disk. Documented as ignoring every attribute-chosen filter, eol conversion included.
- `read_config <git function> <key> <variable>`: status 0 with an empty value refuses, 1 refuses as unset, any other status fails naming the status. Matches the measured table for the two sources it reads (repository config via `git`, `git_plain` for `remote.origin.url`). The design never uses `-f`, so the status 1 ambiguity of an unreadable `-f` file does not reach it. Keys are literals, so "invalid key" cannot occur.
- Push over https with `credential.helper=!gh auth git-credential` only and no `pushInsteadOf` from any file (none is read). Documented.

### 1.4 What remains (the gap)

1. The checkout's own repository configuration during the one `ls-files`. Every key of `.git/config`, `config.worktree` (when the extension is on) and every `include`/`includeIf` it names still applies (measured for `includeIf`). Only two keys are overridden. Keys that can still change the listing: `core.excludesFile` and the default global ignore file (`$XDG_CONFIG_HOME/git/ignore` or `~/.config/git/ignore`, read by `--exclude-standard` even with `GIT_CONFIG_GLOBAL=/dev/null`, since the default path is not a config key), `.git/info/exclude`, `core.sparseCheckout` and `index.sparse`, `core.precomposeUnicode` (no output difference measured on this host for one NFD name, so this one is inferred only), `include.path` to a file the user later makes unparsable (then the listing exits 128, fail closed). Effect of the ignore channels: an untracked store file is omitted from the sync (not pushed as a deletion, because cached entries are listed regardless of ignore rules). This is a silent omission, which standing order 21 classes as a defect.
2. Environment variables outside the `GIT_*` prefix that the fetch and push consult through libcurl and OpenSSL: `http_proxy`, `https_proxy`, `NO_PROXY`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `CURL_CA_BUNDLE` (inferred from libcurl behaviour, not from git-scm.com). `HOME` and `XDG_CONFIG_HOME` select the default attributes and ignore files. `GH_*` variables select the account `gh auth git-credential` answers for.
3. Attribute files in the scratch repository: the default `core.attributesFile` path and the system `gitattributes` are still read. `--no-filters` neutralises them for `hash-object`, and `diff-tree --name-only` applies no attributes, so the effect is nil today. `GIT_ATTR_NOSYSTEM=1` and `-c core.attributesFile=/dev/null` (both already in pr-audit.sh's `git_tree`) would make this true by construction instead of by the choice of commands.
4. Four different isolation wrappers exist in the repository with four different flag sets: `git_plain` and `git_scratch` (records-sync.sh), `git_safe` and `git_tree` (pr-audit.sh, which add `--no-replace-objects`, `core.commitGraph=false`, `core.attributesFile=/dev/null`, `GIT_ATTR_NOSYSTEM=1`), the `git()` function of hcom-seat (which adds `extensions.worktreeConfig=false` and `protocol.allow=never`), and `GIT_C` in `scripts/lint-comparisons.py` (which adds `protocol.https.allow=always` and `core.sshCommand=false`). None is complete and each was hardened by its own audit rounds. This is RC1 in the small: the "set of flags that isolates git" is an open-ended input judged by hand four times.
5. A `git config --get` reader that is ever pointed at an `-f` file must treat status 1 with non-empty stderr as a failure, not as unset. The current reader does not look at stderr. Harmless today (no `-f`), a trap for the next caller.

### 1.5 Decision

Is `git init --bare --template=` plus `GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_NOSYSTEM=1` plus scrubbing `GIT_*` a complete isolation from user and repository configuration? For commands run with `--git-dir` pointing at the scratch repository: yes for configuration (the only sources left are the scratch config the script wrote and the `-c` options the script passes), yes for hooks (no hooks directory), and not quite for attributes and transport environment (items 2 and 3 above, closed by two more switches and an allowlist of non-`GIT_` variables). For the one command run in the checkout: no, and no set of `-c` overrides can make it so, because the repository scope has no off switch. Only the choice of command and the stderr-empty refusal bound it.

Is there a documented single switch for "run this git command with no configuration from anywhere"? No. The git man page documents a switch per level (`GIT_CONFIG_SYSTEM`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_NOSYSTEM`) and none for the repository level. `git config --no-includes` exists only for `git config` reads. The repository level is avoided only by running in a repository the automation created.

### 1.6 Recommended unit spec (one unit, one PR)

GOAL. One isolated-git function, used by every lever that runs git, replaces the four hand-made variants, and a lint refuses any other git invocation in the levers.

SCOPE. New `scripts/orchestrator/lib/git-isolated.sh` (sourced, one function `git_isolated` and one `git_env_scrub`). `scripts/orchestrator/records-sync.sh`, `pr-audit.sh`, `hcom-seat`, `worktree-gc.sh`, `pr-merge.sh` switched to it. `scripts/lint-comparisons.py` `GIT_C` reads the same list from the library file (one source of truth, data not code). New `scripts/ci/git-invocation-check.sh` (an AST walk with `shfmt -ln bash --to-json`, the `masked-dirname-check.sh` shape) that refuses a `git` command word outside the library and outside an `# git-isolated: allow <reason>` line. Tests `tests/unit/test_git_isolated.py`. The generated copies through `scripts/generate-agent-configs.py`.

CHANGE. (1) `git_isolated` sets `GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_NOSYSTEM=1 GIT_ATTR_NOSYSTEM=1 GIT_TERMINAL_PROMPT=0` and passes `--no-replace-objects -c core.hooksPath=/dev/null -c core.fsmonitor=false -c core.attributesFile=/dev/null -c core.sshCommand=false -c protocol.allow=never -c protocol.https.allow=always -c credential.helper= -c gc.auto=0 -c maintenance.auto=false -c credential.interactive=false` before the caller's arguments, so a caller's later `-c` wins by the documented last-wins rule (measured). (2) `git_env_scrub` removes every `GIT_*` name and refuses a survivor (the records-sync.sh loop moved here), and also removes the non-`GIT_` transport names `http_proxy HTTPS_PROXY https_proxy HTTP_PROXY NO_PROXY no_proxy SSL_CERT_FILE SSL_CERT_DIR CURL_CA_BUNDLE` unless the caller names them in an allowlist argument. (3) `read_config` gains a stderr capture and refuses status 1 with non-empty stderr, with a failure-injection test for the `-f` unreadable case (fake git prints the warning and exits 1). (4) The listing in records-sync.sh keeps its stderr refusal and documents the ignore-file omission as a known residual, or drops `--others` in favour of the `find` walk it already does (operator decision, recorded in a decisions row). (5) The lint's acceptance set is closed: a `git` command word is accepted only inside the library file, or when the statement is a call through `git_isolated`, or on a line with the allow comment.

ACCEPTANCE. `tests/unit/test_git_isolated.py` proves, with a repository config holding `core.fsmonitor=<marker hook>`, `core.hooksPath=<dir with every hook>`, `url.<x>.insteadOf`, `url.<x>.pushInsteadOf`, `author.name`, `includeIf "gitdir:**"` and `filter.<x>.clean`, that `git_isolated ls-files`, `hash-object -w --no-filters`, `commit-tree` and a `push` to a local bare repository run no hook, rewrite no URL and use the environment identity, by reading the marker files. A second test sets `GIT_CONFIG_PARAMETERS` and `GIT_CONFIG_COUNT` pairs and proves the scrub removed them. The lint run over every lever reports zero findings. `cmp` of each generated copy against its source is equal. CI green.

VERIFY. `uv run --no-project python -m unittest tests.unit.test_git_isolated tests.unit.test_scratch_git tests.unit.test_pr_levers`. ShellCheck 0.11.0 with the repository `.shellcheckrc`. `shfmt -i 4 -sr -d`. `scripts/ci/masked-dirname-check.sh` and the new check on the lever set.

FORBIDDEN. No change to the push target, the credential helper or the identity source. No `safe.directory=*`. No new `|| true`.

### 2.2 Does the final design match

The repository `.shellcheckrc` enables `check-extra-masked-returns` and sets `source-path=SCRIPTDIR`. `tests/unit/test_hcom_seat.py` additionally runs ShellCheck with `check-extra-masked-returns,require-variable-braces` on hcom-seat and refuses `read < file` forms. `masked-dirname-check.sh` covers the `dirname`/`basename` exemption with an AST rule. The U101 round-10 reader (`read_config`) implements the three-way outcome of standing order 21 (value, unset, failed) and carries a failure-injection test. These match the documentation, and the `dirname` exemption gap is real (source, `isHarmlessCommand`).

### 2.3 Is `check-extra-masked-returns` sufficient to catch "producer status unread"?

No. The five P2 instances show what it does not see.

1. A plain `x=$(producer)` with no status handling is not flagged. The status reaches the assignment, and ShellCheck leaves what happens next to `set -e`. Under `set -e` the assignment aborts the script, except inside an `if` test, a `&&`/`||` list or a function called from one (SC2310/SC2311 cover the function case only when `check-set-e-suppressed` is enabled, which the repository does not enable). Without `inherit_errexit` the body of the substitution itself runs without `-e`, so `x=$(jq ... | ...)` reports the last command's status only (U25 F1 is this shape).
2. A producer that exits 0 on a partial failure is invisible to any status lint. `git ls-files` with an unreadable directory (U101 round 11) and `git config -f` with an unreadable file are measured examples. The only detector is a side channel (stderr captured and required empty, or a pre-walk), which no lint can require without knowing the producer.
3. Status 1 that means two things (unset and a failed read of an `-f` file) is a semantic conflation (the Codex finding 4379614437 shape). A lint sees one `||` and is satisfied.
4. `cmd > file` followed by a test on the file, and `read x < file`, are not command substitutions. SC2312 does not look at redirections from files. The U85 test refuses `read < file` by text, which is the right instinct but a text rule.
5. `[[ -n $(cmd) ]]` is flagged (`T_Condition`), good, but the fix a reader applies (`out=$(cmd) || ...; [[ -n $out ]]`) still conflates "empty" with "nothing to report" unless the function maps the three outcomes explicitly.

### 2.4 What standing order 21 adds, and whether a lint can encode it

Standing order 21 (preferences.md) requires: the decision reads the producer's status, distinguishes "the read failed" from "the read returned nothing", aborts the destructive step with a message naming the file, and carries a failure-injection regression test. Beyond ShellCheck it adds the three-way outcome, the naming, and the test. Of these, a lint can encode:

- The grammar of where a `$(…)` may appear (an AST rule, closed): the whole right-hand side of an assignment whose statement is itself the test of `if`/`while` or the left operand of `||`, or an argument of a named reader function from a table. Everything else is a finding. This is stricter than SC2312 and removes case 1.
- The presence of `set -euo pipefail` and `shopt -s inherit_errexit` as the first statements after the shebang and comments (an AST rule on the first `Stmt` nodes), removing the subshell and pipeline half of case 1. Requires bash 4.4 or later, which the levers have on both hosts (inferred from the pinned bash in the repository's tooling, not measured in this research).
- A table of status-blind producers (`git ls-files`, `git config -f`, `find`, `ls`, `jq` with `-e` absent) whose every invocation must redirect `2>` to a captured file that a following statement tests with `-s` (an AST rule keyed on the command word, closed by the table). This encodes case 2 for the producers the table names and nothing else, which is the honest limit.
- The failure-injection test cannot be checked by a lint, but a test can require it: every function whose name is in a `readers` table of the library must be referenced by a test file that also references the fake-producer status variable (`FAKE_GIT_FAIL_STATUS` today). A missing reference fails the test.

### 2.5 Recommended unit spec

GOAL. The fail-closed rule becomes checkable: one producer-reader library, one AST lint for the grammar of command substitutions and script prologues, one table of status-blind producers, and a test that every reader has a failure-injection test.

SCOPE. New `scripts/orchestrator/lib/read.sh` (`read_config`, `read_listing` with stderr capture, `read_file` replacing `read < file`), `.shellcheckrc` (add `enable=check-set-e-suppressed`), new `scripts/ci/producer-status-check.sh` (shfmt `--to-json` walk, the `masked-dirname-check.sh` shape, with the producer table as data in `scripts/ci/status-blind-producers.tsv`), `tests/unit/test_producer_status_check.py`, the standing order 21 text gains one sentence naming the producer table (coordinator row, not the unit).

CHANGE. (1) The lint refuses a `CmdSubst` node whose parent is not one of the three accepted positions. (2) It refuses a script whose first statements are not `set -euo pipefail` and `shopt -s inherit_errexit`, in that order, when the shebang is bash. (3) For each command word in the producer table it requires a `2>` redirect to a word that a later `[[ ! -s ... ]]` or the library reader tests. (4) It refuses a file it cannot parse (exit 2), never reads it as clean. (5) The readers map status to exactly three outcomes and print the file or key in every message. (6) The test asserts each reader name appears in a test with a failure-injection variable.

ACCEPTANCE. Fixtures reproduce the five P2 shapes (jq inspection error read as absence, `git config` status 3 and 128, `git ls-files` warning with exit 0, `read < unreadable`, `local x=$(false)`) and the lint or the tests catch each. The lint over the lever set has zero findings after the readers are adopted. ShellCheck 0.11.0 passes with both optional checks.

VERIFY. `uv run --no-project python -m unittest tests.unit.test_producer_status_check tests.unit.test_pr_levers tests.unit.test_scratch_git`. ShellCheck and `shfmt -d` as the repository runs them.

### 4.2 Does the final design match

- pr-audit.sh's Python supervisor: `Popen(start_new_session=True)`, wait in slices, `killpg` TERM, grace, `killpg` KILL, reap, Linux `PR_SET_CHILD_SUBREAPER` sweep, `PR_SET_PDEATHSIG`, `EPERM` accepted only when `ps` shows no live member of the group. This matches the documented primitives and goes beyond them exactly where the documentation is silent: process groups are not a containment boundary (a descendant that calls `setsid` leaves), which the subreaper closes on Linux and nothing closes on macOS (documented in the script as a residual with a `ps` snapshot as detection only). The `EPERM` handling matches the killpg(3) note that BSD returns `EPERM` when the check fails for at least one member, which is what a vanishing group with zombies produces.
- U99: `run-bats.py` signals nothing, names the stalled test and exits 124, and the step's `timeout-minutes` plus the runner stop the processes. The runner source confirms both mechanisms the script's docstring cites (the 5 s rule and the job-end orphan kill). This is the removal mechanism of standing order 33, and it matches the Bats state: 1.14.0 has no per-test flag, `BATS_TEST_TIMEOUT` is set only from the environment or `setup_file()`, and #1206 makes it hold a run for the whole bound after any failing test.
- The levers bound `gh` with `perl -e 'alarm shift; exec @ARGV'`. The alarm reaches the exec'd process only. A child that `gh` starts (it runs `git` for some operations) is not bounded (inferred from the exec semantics, not measured). coreutils `timeout` is not on the macOS base system, which is why perl is used (inferred).

### 4.3 The gap

1. The step `timeout-minutes` kill and the cancel path both act on the runner's view of the process tree. A descendant that left the tree by `setsid` and also cleared `RUNNER_TRACKING_ID` from its environment survives both the step kill and the job-end orphan sweep (inferred from the source). For the repository's own tests this is theoretical, but a test that runs an installer which daemonises is this shape.
2. The perl alarm bound is a single-process bound. If `gh` hangs in a child, the alarm kills `gh` and the child keeps the output pipe, which is the #1020 shape in a different place.
3. macOS has no subreaper. The pr-audit.sh residual is correctly documented, but no test exercises the `ps` snapshot detection against a double-forked descendant on macOS (the fixture `fake-codex.py` has such a mode, and whether the CI macOS cell runs it was not checked by this research).
4. The run-bats.py default bound (600 s) and the step bound are related by `tests/unit/test_apt_mirror.py` BoundOrderTest, which is the right encoding (a test pins the order of two numbers). The same test does not exist for the lever `gh` bounds against `pr-audit.sh`'s deadline.

### 4.4 Recommended unit spec

GOAL. Every bounded external call in the levers uses one bound function that bounds the process group, not the process, and the relation between every inner bound and its outer deadline is pinned by a test.

SCOPE. `scripts/orchestrator/lib/bounded.sh` (one `bounded <seconds> <command...>` that runs the supervisor shape of pr-audit.sh in its minimal form: `python3 -I -S -c` with `Popen(start_new_session=True)`, slice waits, `killpg` TERM then KILL, exit 124 on the deadline and 125 on any supervisor fault), the nine `gh_bounded` copies in the levers switched to it, `tests/unit/test_bounded.py`, `tests/unit/test_network_bounds.py` gains a `BoundOrderTest` for `PR_LEVER_GH_TIMEOUT` against the pr-audit.sh deadline.

CHANGE. (1) The function replaces the perl alarm. (2) Its tests use the existing `fake-codex.py` double-fork mode to prove the group kill reaches a child of the bounded command and to record (not fix) the macOS escape as a named survivor line. (3) The order test asserts inner bound times the retry count is below the outer deadline. (4) The CI job that runs the lever tests keeps `timeout-minutes` above the sum, pinned by the same test shape as `BoundOrderTest`.

ACCEPTANCE. A fixture command that spawns a sleeping child and exits is killed with its child on Linux (measured in CI by pid absence), and on macOS the child is listed as a survivor. The nine levers have one `bounded` definition between them (a grep in a test counts definitions). CI green on both platforms.

VERIFY. `uv run --no-project python -m unittest tests.unit.test_bounded tests.unit.test_network_bounds tests.unit.test_pr_levers`. ShellCheck, `shfmt -d`, the AST checks.
