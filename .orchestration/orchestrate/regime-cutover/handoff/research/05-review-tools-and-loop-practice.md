The two things the table says as a whole (inferred). First, no vendor blocks a merge on a general finding by default; blocking is always an opt-in (CodeRabbit auto-approvals, Bugbot fail-on-unresolved, Ellipsis `request_changes`, Copilot approvals counting) or limited to security (Sourcery, the Claude Code team's internal rule). The repository's rule, where a single P2 finding makes the verdict `incorrect` and only a P3 passes, is stricter than every product default and than Codex's P0-and-P1 posting rule, and matches the two in-house programs that gate landing (RADAR, the Claude Code team). Second, every vendor that re-reviews on push has moved to some form of incremental review with finding memory between 2025 and 2026 (CodeRabbit, Bugbot, Qodo, Sourcery, Ellipsis, Claude Code Review; Copilot resolves but may repeat), and the Claude Code team measured why: 59% of what their reviewer kept flagging in late rounds was code unchanged since its first pass. The repository has neither, by the per-head verdict rule.

### 1.2 Confidence thresholds and review profiles

Three designs appear (inferred): a user-settable threshold or strictness number, a named profile, and a hidden verification or voting stage the user cannot tune.

- Threshold numbers (doc). Greptile `strictness` "1 = verbose (all issues), 2 = balanced (default), 3 = critical only", settable per directory in `.greptile/config.json` (https://www.greptile.com/docs/code-review/controlling-nitpickiness). Qodo v2 `inline_comments_severity_threshold` 1 to 3 (https://docs.qodo.ai/code-review/severity-thresholds); v1 `suggestions_score_threshold=0 # [0-10]| recommend not to set this value above 8, since above it may clip highly relevant suggestions` and `score_on_reflection_failure=7 ... set below suggestions_score_threshold to drop unvetted suggestions` (https://github.com/qodo-ai/pr-agent/blob/main/pr_agent/settings/configuration.toml). Gemini `comment_severity_threshold` default `MEDIUM` (https://docs.cloud.google.com/gemini/docs/code-review/customize-repo-review). Ellipsis legacy: "Modify `confidence_threshold` to show fewer/more comments. ... If there's too much noise, we suggest 0.9. The default value is 0.7." (https://web.archive.org/web/20250214202930/https://docs.ellipsis.dev/features/review). Meta RADAR: "ACR requires a confidence score of at least 8 out of 10, with all changes classified into safe categories" (https://arxiv.org/html/2605.30208v1).
- Profiles (doc). CodeRabbit "quiet for only the most important feedback, chill for balanced feedback, assertive for more feedback (which may feel nitpicky)" (https://docs.coderabbit.ai/reference/configuration). Sourcery "Quiet posts only the highest-priority comments. Balanced, the default, posts all but the lowest-priority ones. Verbose posts every comment." (https://docs.sourcery.ai/reviews/configure/). Claude Code local: "At `low`, the review reports the findings it's most confident in, so you see fewer false positives. From `medium` through `max`, the review broadens coverage." (https://code.claude.com/docs/en/code-review-local).
- Hidden verification (doc). Bugbot at launch: "Run eight parallel passes with randomized diff order ... Majority voting to filter out bugs found during only one pass ... Run results through a validator model to catch false positives ... Dedupe against bugs posted from previous runs" (https://cursor.com/blog/building-bugbot). Claude Code Review: "Verify: a verification step checks the candidate findings against the code and filters out false positives." (https://code.claude.com/docs/en/code-review); the team's internal version: "Several agents look for bugs at the same time. Then a separate group votes on each finding, and it only gets posted if enough of them agree it's real. Findings that are only about style, diagnostics, or cleanup get dropped." (https://claude.dev/blog/solving-code-review-at-anthropic/). Qodo v2: "a judge agent merges their findings, removes duplicates, and filters out anything low-confidence before it reaches the pull request." (https://docs.qodo.ai/code-review).
- Two vendors report that a self-rated severity does not work as a filter (doc). Greptile: "we figured we would simply add a filtering step where the LLM could rate the severity of a comment+diff pair on a 1-10 scale, and simply eliminate any comments rated less than 7. Sadly, this also failed. The LLMs judgment of its own output was nearly random." (https://www.greptile.com/blog/make-llms-shut-up). Google AutoCommenter: "started with a high confidence threshold of t=0.98. We manually sampled several hundred results and observed that around 80% of predictions below the threshold were still correct", replaced by per-rule thresholds (https://arxiv.org/html/2405.13565v1). Research 04 entry 1 measures the same instability for LLM judges in general.
- Precision as an explicit design target (doc). OpenAI: "Precision is more important for usability than recall" and "we explicitly accepted a measured tradeoff: modestly reduced recall in exchange for high signal quality and developer trust." (https://alignment.openai.com/scaling-code-verification). Google: "The final model was calibrated for a target precision of 50%." and the beta "indicated that a minimum precision of 70% was too conservative. Reducing the minimum precision to 50% increased the absolute recall value ... without reducing user satisfaction" (https://research.google/blog/resolving-code-review-comments-with-ml/, https://storage.googleapis.com/gweb-research2023-media/pubtools/7525.pdf).

### 1.3 Which severities block

- CodeRabbit (doc): "With Automatic Approvals, CodeRabbit's review decision follows its feedback. When a review leaves actionable comments, CodeRabbit requests changes. When that feedback is resolved and CodeRabbit has reviewed the latest commit, CodeRabbit approves the pull request." and "Automatic Approvals is off by default." (https://docs.coderabbit.ai/pr-reviews/automatic-approvals). On the check: "A required `CodeRabbit` check therefore blocks merging while a review is in progress, when a review fails with `fail_commit_status` set to `true`, when a review is cancelled, and while no check exists. It does not block skipped or rate-limited reviews." and "No setting guarantees that CodeRabbit reviews every pull request before it merges." (https://docs.coderabbit.ai/pr-reviews/status-check).
- Bugbot (doc): "Requiring the status alone does not block merges on findings because findings default to `neutral`. If fail-on-unresolved-issues behavior is available for your organization, enable it to make unresolved findings produce a failing status." (https://cursor.com/docs/bugbot).
- Copilot (doc): "By default, Copilot leaves a 'Comment' review, not an 'Approve' review or a 'Request changes' review." and, when approvals are on, "If new commits are pushed after Copilot approves, the approval is dismissed" (https://docs.github.com/en/copilot/how-tos/use-copilot-agents/request-a-code-review/use-code-review).
- Sourcery (doc): "Success, when the review posts with no blocking issues. Failure, when blocking security findings require changes. Skipped, when a rate limit or the re-review cap applies." and "The check posts even when Sourcery skips the review. Requiring it never blocks a merge." (https://docs.sourcery.ai/reviews/anatomy-of-a-review/).
- Ellipsis (doc): "Each reviewer marks every comment blocking or not. A review passes when no reviewer returned a blocking comment and fails otherwise." and the prompt pattern "Mark a comment blocking only when the change must not merge as is." (https://www.ellipsis.dev/docs/code-review).
- Claude Code Review (doc): the product "never approves or blocks your pull request, and the check run never concludes as a failure" (https://code.claude.com/docs/en/code-review-pull-requests); the team's own repositories: "A PR can't merge while any finding from the bug review or the security review is still open. You either fix it or close the thread with a short reason, which is how you clear a false positive." (https://claude.dev/blog/solving-code-review-at-anthropic/).
- Meta RADAR (doc): "If any risk signal is detected, the diff is automatically disqualified from auto-acceptance." and "Approved bot diffs land after a configurable delay, during which a human reviewer can still reject the diff." (https://arxiv.org/html/2605.30208v1).
- The one field measurement of what a non-blocking check does to humans (doc): "`success` means clean. `neutral` means findings. GitHub renders `neutral` as a flat grey square, which the human eye reads as 'this check didn't fail' ... We once caught a clearly-failing PR almost merged for exactly that reason." (https://dev.to/_vjk/best-ai-code-reviewer-in-2026-we-ran-4-in-parallel-for-3-weeks-146-prs-679-findings-1c0f).

## 2. Incremental review and finding memory

### 2.1 Reviewing only the commits since the last review

- CodeRabbit (doc): "`reviews.auto_review.auto_incremental_review` boolean (default: true) Incremental Review: Re-run the review on each push." and "`auto_pause_after_reviewed_commits` integer (default: 5) ... Pause automatic reviews after this many reviewed commits since the last pause." (https://docs.coderabbit.ai/reference/configuration). "An incremental review takes all comments that CodeRabbit has made since its most recent full review into consideration, and generates a review of only the new changes." (https://docs.coderabbit.ai/guides/commands).
- Bugbot (doc): "By default, Bugbot reviews only the changes since the previous Bugbot review. Turn off Incremental Review in Bugbot Automations to review the full pull request diff on every push." (https://cursor.com/docs/bugbot). The June 2026 post records the reason the default was changed: "Bugbot by default re-reviews the entire PR every time a change is pushed. This can result in new flags on code it had already reviewed and approved." (https://cursor.com/blog/bugbot-updates-june-2026).
- Qodo v2 (doc): "`enable_incremental_review = true` (default) Follow-up reviews focus only on changes since the last review"; "With every new commit, Qodo updates the existing review comment. If a new issue is introduced in a new commit, it appears as an additional finding marked with a ⭐️ New label." (https://docs.qodo.ai/code-review/persistent-review-comments). "Starting with the second review, Qodo narrows the review when you've resolved at least one Qodo finding and your new commits contain fixes rather than new functionality." with the caveat "If you're benchmarking Qodo with a strong emphasis on finding every possible issue, consider disabling it, as narrowing the review may affect recall." (https://docs.qodo.ai/code-review/optimize-review-focus-in-fix-loops).
- Sourcery (doc): "A re-review does less than the first one: Re-checks each existing Sourcery comment against the new code and resolves the threads the new commits address. Re-runs the security scans and posts any new findings as a fresh review. Leaves the rest of the review in place." (https://docs.sourcery.ai/reviews/anatomy-of-a-review/).
- Ellipsis (doc): "A reviewer only sees commits it has not reviewed before, and a comment on a line outside those commits is held back. A push with nothing new for any reviewer starts nothing." (https://www.ellipsis.dev/docs/code-review).
- Claude Code Review (doc): "A later review that starts on its own, such as after a push, focuses on what changed since the last review and posts fewer nits and pre-existing findings." and two skip states: "Code review skipped — no new changes: no Important finding from the earlier review is still open" and "Code review not repeated — earlier findings still open", kept when "The pull request still adds and removes the same lines, as after an empty commit, a clean merge of the base branch, or a clean rebase" (https://code.claude.com/docs/en/code-review-pull-requests).
- Copilot (doc): one review per PR unless "Review new pushes"; the 2026-09-11 changelog: "When you push a commit that addresses a Copilot code review comment, Copilot now resolves that comment during its rereview." (https://github.blog/changelog/2026-09-11-auto-resolution-and-analysis-updates-in-copilot-code-review/).
- Greptile and Graphite: not documented; both re-run on pushes when enabled (https://www.greptile.com/docs/code-review/greptile-json-reference, https://graphite.com/docs/ai-review-customization).
- The platform gap the field study names (doc): "most tools re-review the full base-to-head diff every time, since there's no easy way to trace the reviewed commits to calculate incremental changes." (https://arxiv.org/html/2508.18771v1).

### 2.2 Remembering earlier findings and dismissals

- Qodo v1 (doc), the most explicit mechanism found: "`max_previous_findings_chars` Character budget for the findings stored by earlier reviews ... ### 3.2 Stop conditions other than a count

- Progress defined before the run (doc): "A correction iteration qualifies only when at least 1 of these conditions holds: a previously failing deterministic check now passes without a new required failure; an accepted finding is fixed and its verification evidence is retained; a disputed finding is resolved by the named human owner with a recorded reason; the diff is reduced or split according to a predefined complexity rule. ... Rewritten comments, another model explanation, or a lower self-reported severity do not count." (https://www.florian.bruniaux.com/guides/bounded-code-review-loop/).
- Trajectory rather than count (doc): "The cap is how nearly every verify-revise loop gets stopped today, and it's wrong in both directions." A ratio of current to previous error classifies the loop "FAST_CONVERGE / CONVERGING / STALLING / OSCILLATING / DIVERGING" and may "stop and roll back to the lowest-error output so far"; reported "92.8% vs max_iterations=20" spend reduction on a 2,000-trial benchmark (https://news.ycombinator.com/item?id=48919562).
- A stuck detector between reviewer and author (doc): "Is the loop making progress toward resolution, or is it cycling? ... Respond with JSON: { 'status': 'progress' | 'stuck', 'reason': string }" and the severity policy "Only return 'fix' if there are unresolved critical or high severity issues. If the only remaining issues are low/nit, return 'submit'." (https://dev.to/ubcent/i-let-agents-write-my-code-they-got-stuck-in-a-loop-and-argued-with-each-other-36me).
- Vendor guidance (doc): "The task often terminates upon completion, but it's also common to include stopping conditions (such as a maximum number of iterations) to maintain control." (https://www.anthropic.com/engineering/building-effective-agents). "A good loop usually stops for one of four reasons: validation passes, the loop reaches a maximum number of attempts, the remaining delta stops changing, or the next decision needs human review. Those stop conditions are just as important as the repair prompt." (https://developers.openai.com/cookbook/examples/codex/build_iterative_repair_loops_with_codex). Codex continuation template: "status restatements and unexecuted plans are no progress." and "do not redefine success around a smaller or easier task." (https://github.com/openai/codex/blob/main/codex-rs/ext/goal/templates/goals/continuation.md).
- Anti-goal-post-moving as a stop rule (doc): "An agent may discover missing work within that policy; it may not weaken the requirement to turn a failure green." (https://www.florian.bruniaux.com/guides/bounded-code-review-loop/); Kent Beck stops on "Any indication that the genie was cheating, for example by disabling or deleting tests." ### 3.3 Escalation to a human

- Risk tiers set by the change (doc): "The change sets the tier, not the author. A classifier reads the change and picks its risk tier." Low needs no human "once automated review and security checks are green", Medium one person, High two; "An agent's approval never counts as a person's"; "Whoever prompted the change is on the hook for it."; "An approval covers one specific commit." (https://claude.dev/blog/solving-code-review-at-anthropic/).
- Judgment as the trigger (doc): "Escalate to a human only when judgment is required" and "iterate in a loop until all agent reviewers are satisfied (effectively this is a Ralph Wiggum Loop)" (https://openai.com/index/harness-engineering/). Flock: "if it hasn't converged by the cap, or the same class of blocker recurs, ESCALATE — never re-loop past the cap." and "If the reviewer returns NEEDS_CONTEXT, or the spec can't be satisfied as written → ESCALATE (ask the human), never loop." (https://github.com/duckbugio/flock/blob/main/core/agents/arbiter.md).
- Which failures are never retried (doc): "Do not automatically retry malformed output, insufficient context, failed authentication, a refusal, or an unknown state. Those need configuration repair or a person." and "The absence of a result never becomes `CLEAR`." (https://www.florian.bruniaux.com/guides/bounded-code-review-loop/).
- Human on the loop, not in it (doc): Meta JiTTesting "Engineers define success criteria early, let AI execute the testing, monitor the outcomes at an aggregate level, and intervene at the policy level rather than per item." (https://engineering.fb.com/2026/10/29/security/catching-bugs-before-they-land-jittestings-human-on-the-loop-approach-at-full-scale/); RADAR "Failure at any stage routes the diff to human review." (https://arxiv.org/html/2605.30208v1). Kief Morris: "The 'in the loop' way is to fix the artefact ... The 'on the loop' way is to change the harness that produced the artefact so it produces the results we want." (https://martinfowler.com/articles/exploring-gen-ai/humans-and-agents.html).
- Who holds the merge (doc): "Never let a bot's approval replace a required human's; dismiss approvals on new commits." (https://claude.dev/blog/solving-code-review-at-anthropic/); "A human reads a converged PR: the diff, the findings, and how each was resolved, and makes the one decision that stays human. Merge." (https://pydantic.dev/articles/harness-macroscope); "Enforce human approval before merging, as human-dominated reviews achieve 67.99% merge rates" (https://arxiv.org/html/2604.03196).

### 3.4 A persistent finding class as a design problem

Nine sources say this in their own words; none says "remove the feature" (inferred; the nearest is "reconsider the approach").

- "When the automated reviewer keeps flagging the same thing, we fix it at the source: in the skill, with a lint rule, or with updates to instructional files" and "Flag the class of bug, so the author fixes every instance, not one line." (https://claude.dev/blog/solving-code-review-at-anthropic/)
- "When something failed, the fix was almost never 'try harder.' ... human engineers always stepped into the task and asked: 'what capability is missing, and how do we make it both legible and enforceable for the agent?'" and "When documentation falls short, we promote the rule into code" (https://openai.com/index/harness-engineering/)
- "Same class of blocking finding appearing twice → do not CONTINUE again." (https://github.com/duckbugio/flock/blob/main/core/agents/arbiter.md)
- "A recurring review comment is evidence of an unencoded invariant." and "Promote a recurring review comment into a harness rule once it fires across 3+ PRs" (https://github.com/1lucascb/agentpatterns.ai/blob/main/code-review/review-feedback-to-rule-loop.md)
- "If a reviewer writes the same accepted correction every week, the team is buying the same lesson repeatedly." with the caution "Do not set a universal occurrence count. A second instance of a severe authorization gap may justify a control, while 10 minor wording preferences may justify nothing." (https://www.florian.bruniaux.com/blog/articles/recurring-review-comments-controls/)
- "The agents weren't broken. They were doing exactly what they were told. The spec was broken, and nobody in the loop had the job of noticing that" and "the arbiter is a policy, not just a judge. Left to its own devices, it defaults to 'fix everything,' which is technically correct and practically a treadmill." (https://dev.to/ubcent/i-let-agents-write-my-code-they-got-stuck-in-a-loop-and-argued-with-each-other-36me)
- "If Ralph is generating the wrong code or using the wrong technical patterns, then you should update your standard library to steer it to use the correct patterns. If Ralph is building the wrong thing completely, then your specifications may be incorrect." (https://ghuntley.com/ralph/)
- "anytime you find an agent makes a mistake, you take the time to engineer a solution such that the agent never makes that mistake again." (https://mitchellh.com/writing/my-ai-adoption-journey)
- "If you keep adding emphasis to a `CLAUDE.md` line and Claude still misses it, that's a sign the line belongs in a hook." and "A reviewer that's asked to find problems will always find something. If you fix every finding, you end up with extra abstraction layers and tests for cases that can't happen." (https://code.claude.com/docs/en/best-practices)
- Ronacher on the shape of the treadmill output: "If each iteration adds another small defense, the system slowly becomes less understandable while appearing more robust." and "the right fix is not 'handle every malformed case.' The right fix is to make the malformed case unrepresentable" (https://lucumr.pocoo.org/2026/6/23/the-coming-loop/).
