## 1. `codex exec` (RC4, V1)

### 1.1 Sandbox modes

Vendor statements:

- Non-interactive mode, [learn.chatgpt.com/docs/non-interactive-mode](https://learn.chatgpt.com/docs/non-interactive-mode.md): "By default, `codex exec` runs in a read-only sandbox." The two escalations are `codex exec --sandbox workspace-write "<task>"` and `codex exec --sandbox danger-full-access "<task>"`, with "Use `danger-full-access` only in a controlled environment (for example, an isolated CI runner or container)." Then: "`--full-auto` is no longer supported. Update scripts to use `--sandbox workspace-write`, or use `--approve-for-me` to route approval requests through automatic review with the workspace-write sandbox."
- Sandbox, [learn.chatgpt.com/docs/sandboxing](https://learn.chatgpt.com/docs/sandboxing.md): "`read-only`: The agent can inspect files, but it can't edit files or run commands without approval. `workspace-write`: The agent can read files, edit within the workspace, and run routine local commands inside that boundary. ... `danger-full-access`: The agent runs without sandbox restrictions."
- Agent approvals and security, [learn.chatgpt.com/docs/agent-approvals-security](https://learn.chatgpt.com/docs/agent-approvals-security.md), table "Common sandbox and approval combinations": "Read-only non-interactive (CI) | `--sandbox read-only --ask-for-approval never` | Codex can read files and run commands within the read-only sandbox; it never asks for approval." The same page: "For non-interactive runs, use `codex exec --sandbox workspace-write`."
- Same page, "OS-level sandbox": "macOS uses Seatbelt policies and runs commands using `sandbox-exec` with a profile (`-p`) that corresponds to the `--sandbox` mode you selected." The test command is `codex sandbox macos [--permissions-profile <name>] [--log-denials] [COMMAND]...` (aliases `codex debug`, `codex sandbox seatbelt`).
- CLI reference, [learn.chatgpt.com/docs/developer-commands?surface=cli](https://learn.chatgpt.com/docs/developer-commands.md?surface=cli): "When you need to grant Codex write access to more directories, prefer `--add-dir` rather than forcing `--sandbox danger-full-access`." And: "Pair `--json` with `--output-last-message` in CI to capture machine-readable progress and a final natural-language summary."

### 1.2 Writable roots and the temp directory on macOS

Vendor statements:

- Configuration reference, [learn.chatgpt.com/docs/config-file/config-reference](https://learn.chatgpt.com/docs/config-file/config-reference.md): `sandbox_workspace_write.writable_roots` (array of string) "Additional writable roots when `sandbox_mode = "workspace-write"`"; `sandbox_workspace_write.exclude_tmpdir_env_var` (boolean) "Exclude `$TMPDIR` from writable roots in workspace-write mode"; `sandbox_workspace_write.exclude_slash_tmp` (boolean) "Exclude `/tmp` from writable roots in workspace-write mode"; `sandbox_workspace_write.network_access` (boolean) "Allow outbound network access inside the workspace-write sandbox."
- Advanced configuration, [learn.chatgpt.com/docs/config-file/config-advanced](https://learn.chatgpt.com/docs/config-file/config-advanced.md), the example block: `exclude_tmpdir_env_var = false  # Allow $TMPDIR`, `exclude_slash_tmp = false  # Allow /tmp`, `writable_roots = ["~/.pyenv/shims"]`, `network_access = false`.
- Approvals page, "Defaults and recommendations": "The workspace includes the current directory and temporary directories like `/tmp`. Use the `/status` command to see which directories are in the workspace." And "Protected paths in writable roots": "`<writable_root>/.git` is protected as read-only whether it appears as a directory or file. If `<writable_root>/.git` is a pointer file (`gitdir: ...`), the resolved Git directory path is also protected as read-only. `<writable_root>/.agents` ... `.codex` ... `.aws` is protected as read-only when it exists as a directory. Protection is recursive."
- Permissions (beta profiles), [learn.chatgpt.com/docs/permissions](https://learn.chatgpt.com/docs/permissions.md): built-ins "`:read-only` keeps local command execution read-only. `:workspace` allows writes inside the active workspace roots and system temp directories. `:danger-full-access` removes local sandbox restrictions." Path forms include `:tmpdir` "The `$TMPDIR` location, when one is available", `:slash_tmp` "The `/tmp` folder, if it exists", `:root`, `:minimal`, `:workspace_roots`. Roots are added with `[permissions.<name>.workspace_roots]` or an absolute or `~/` path in `[permissions.<name>.filesystem]`. "Permission profiles do not compose with the older sandbox settings. Configure either `default_permissions` and `[permissions]`, or `sandbox_mode` / `sandbox_workspace_write`, but not both. If `sandbox_mode` appears in any loaded config file, you pass `--sandbox`, or the selected config profile sets `sandbox_mode`, Codex uses those older sandbox settings instead of `default_permissions`." Profiles require Codex 0.138.0 or later for a managed allowlist.

- `home/dot_agents/codex-audit/config.toml:5` `default_permissions = "audit"`; lines 23-57 define `[permissions.audit]` with `extends = ":read-only"`, `":root" = "deny"`, `":minimal" = "read"`, `"$AUDIT_TREE" = "read"`, `"$AUDIT_CWD" = "read"`, `":tmpdir" = "write"`, `":slash_tmp" = "deny"`, `"/var/tmp" = "deny"`, the credential stores denied, and `[permissions.audit.network] enabled = false`.

### 1.6 AGENTS.md discovery and `--cd`

Vendor statements, [learn.chatgpt.com/docs/agent-configuration/agents-md](https://learn.chatgpt.com/docs/agent-configuration/agents-md.md):

- "Codex builds an instruction chain when it starts (once per run ...). Discovery follows this precedence order: 1. ## 4. GitHub Actions security hardening: the threat model inside one job (V6, RC4)

### 4.1 Are earlier steps trusted?

Vendor statements:

- Secure use reference, [docs.github.com/en/actions/reference/security/secure-use](https://docs.github.com/en/actions/reference/security/secure-use) (the URL the plan cites, `security-hardening-for-github-actions`, redirects here): "The individual jobs in a workflow can interact with (and compromise) other jobs. For example, a job querying the environment variables used by a later job, writing files to a shared directory that a later job processes, or even more directly by interacting with the Docker socket and inspecting other running containers and executing commands in them. This means that a compromise of a single action within a workflow can be very significant, as that compromised action would have access to all secrets configured on your repository, and may be able to use the `GITHUB_TOKEN` to write to the repository."
- Compromised runners, [docs.github.com/en/actions/concepts/security/compromised-runners](https://docs.github.com/en/actions/concepts/security/compromised-runners): "If the secret or token is set to an environment variable, it can be directly accessed through the environment using `printenv`. If the secret is used directly in an expression, the generated shell script is stored on-disk and is accessible." "Although GitHub Actions scrubs secrets from memory that are not referenced in the workflow (or an included action), the `GITHUB_TOKEN` and any referenced secrets can be harvested by a determined attacker." Redaction "is not a true security boundary." "GitHub-hosted runners do not scan for malicious code downloaded by a user during their job."
- Secure use reference, self-hosted: "GitHub-hosted runners execute code within ephemeral and clean isolated virtual machines, meaning there is no way to persistently compromise this environment." The unit of isolation named is the virtual machine, that is the job; no page describes isolation between steps of one job.
- codex-action security (OpenAI's guidance for the same runner): "Recommendation: run `openai/codex-action` as the last step in a job ... Codex could have spawned processes that are still running after Codex exits. Codex could have overwritten the source code of other actions on the host, such as `actions/github-script`. Codex could have written to key configuration files, such as those in your `.git/hooks` folder, with the expectation that privileged processes may run later in the workflow that exercise them." And: "the combination of read-only access to the filesystem and `sudo` can be used to expose your `OPENAI_API_KEY`" because passwordless `sudo` is the default on GitHub-hosted runners and procfs exposes process memory.

Reading: GitHub's documents treat the job as one trust domain. Every step sees the same filesystem, the same environment, the same `GITHUB_TOKEN`, and every step runs as the same user with passwordless `sudo` on hosted runners. The docs give no reason to trust an earlier step more than a later one, and the OpenAI guidance says the reverse ordering concern also holds: a step that ran an agent taints every step after it.

### 4.2 `GITHUB_ENV`, `GITHUB_PATH`, `BASH_ENV`

Vendor statements:

- Workflow commands, [docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands): "You can make an environment variable available to any subsequent steps in a workflow job by defining or updating the environment variable and writing this to the `GITHUB_ENV` environment file. The step that creates or updates the environment variable does not have access to the new value, but all subsequent steps in a job will have access." "You can't overwrite the value of the default environment variables named `GITHUB_*` and `RUNNER_*`." The one security note: "Due to security restrictions, `GITHUB_ENV` cannot be used to set the `NODE_OPTIONS` environment variable." `GITHUB_PATH`: "Prepends a directory to the system `PATH` variable and automatically makes it available to all subsequent actions in the current job."
- GitHub Changelog, 2020-10-01, [Deprecating set-env and add-path commands](https://github.blog/changelog/2020-10-01-github-actions-deprecating-set-env-and-add-path-commands/): "A moderate security vulnerability has been identified in the GitHub Actions runner that can allow environment variable and path injection in workflows that log untrusted data to STDOUT." The files replaced the STDOUT commands; "If you need to log untrusted information such as issue titles, bodies, or commit messages to STDOUT we recommend that you disable command processing prior to doing that" with `::stop-commands::<token>`.
- `BASH_ENV`: a search of docs.github.com for the term returned only Copilot CLI pages (2026-10-30); the Actions documentation does not mention it. **Inferred** from the shell table in section 5: `shell: bash` runs `bash --noprofile --norc`, which skips the profile and rc files but not `BASH_ENV`, which bash reads for every non-interactive shell. A step that writes `BASH_ENV=<file>` to `GITHUB_ENV` therefore sources that file at the start of every later `bash` step. This is the mechanism, not a GitHub statement.

Repository today: `GITHUB_ENV` is written at `.github/workflows/private-bootstrap.yaml:82` and `remote.yaml:48` (`HOME=${RUNNER_TEMP}/dotfiles-home`) and `macos.yaml:154` (`auto_push=true`); `GITHUB_PATH` is written by `scripts/ci/install-pinned-lint-tools.sh` (`test.yaml:406-407`, "checks each install and lookup before it touches GITHUB_PATH"). The values written are literals or `RUNNER_TEMP`, never event data. `regime.yml:41-43` fetches `refs/pull/<n>/head` and compares it to the event sha but never checks the head out (research/03 section 2.6).

Verdict: the three writes are constants and the workflows that write them run on `push` and `pull_request` of the repository itself, so the documented injection path (untrusted data reaching the env file) is not open. The posture to record is that a step after an agent step inherits whatever that step wrote to the two files, which is why the audit runs locally and `regime.yml` runs no agent.

### 4.3 Script injection

Vendor statements, Script injections, [docs.github.com/en/actions/concepts/security/script-injections](https://docs.github.com/en/actions/concepts/security/script-injections): "Attackers can add their own malicious content to the `github` context, which should be treated as potentially untrusted input. These contexts typically end with `body`, `default_branch`, `email`, `head_ref`, `label`, `message`, `name`, `page_name`, `ref`, and `title`." "This example is vulnerable to script injection because the `run` command executes within a temporary shell script on the runner. Before the shell script is run, the expressions inside `${{ }}` are evaluated and then substituted with the resulting values." A valid branch name `zzz";echo${IFS}"hello";#` is given as a vector. Secure use reference, mitigations: "Use an action instead of an inline script" and "Use an intermediate environment variable" (`env: TITLE: ${{ github.event.pull_request.title }}` then `"$TITLE"`), "consider using double quote shell variables to avoid word splitting". The same page: `pull_request_target` and `workflow_run` "must not explicitly check out untrusted code"; CodeQL default setup scans workflows; "OpenSSF Scorecards can help you identify potentially vulnerable workflows."

Repository today: every `${{ }}` that carries event data in the eleven workflows is bound through `env:` (for example `regime.yml:40` `HEAD_SHA: ${{ github.event.pull_request.head.sha }}`, `remote.yaml:60`, `test.yaml:77`); research/03 section 2.6 and `tests/` pin that property for `regime.yml` (commit 0ef974d0).

### 4.4 Recommended controls

Vendor statements:

- Secure use reference: "The best measure is to lock your workflow dependencies with a lockfile. This records the exact commit for every action your workflows depend on, including transitive dependencies, and verifies the identity of each source repository at run time. This is the strongest protection available, and supersedes SHA pinning for repositories that adopt it." For repositories that cannot: "Pin actions to a full-length commit SHA ... When selecting a SHA, you should verify it is from the action's repository and not a repository fork." "Pin actions to a tag only if you trust the creator." "Regardless of your measures, always audit the source code of the action."
- GitHub Changelog, 2026-10-28, [Workflow lockfiles are generally available](https://github.blog/changelog/2026-10-28-github-actions-workflow-lockfiles-are-generally-available): GA on Free, Team and Enterprise Cloud; `gh actions-lock` writes `.github/workflows/actions.lock`; "Onboard workflows individually"; Dependabot regenerates the matching entry in the same pull request; a "Require lockfile" policy; a stale-lockfile check for CI. "Lockfiles help protect against unexpected dependency changes, but they don't determine whether a dependency is safe."
- Least privilege: "It's good security practice to set the default permission for the `GITHUB_TOKEN` to read access only for repository contents. Compromised runners: the token "expires after the job has completed", and an attacker "can automate the attack and perform it in fractions of a second" with it.
- CODEOWNERS on `.github/workflows`; Dependabot version updates for actions ("Dependabot only creates alerts for vulnerable actions that use semantic versioning and will not create alerts for actions pinned to SHA values"); dependency review; the audit log.
- OpenSSF Scorecard: "Scorecards is an automated security tool that flags risky supply chain practices. ... ## 5. `set -o pipefail` and the default shell for `run:` steps

Vendor statements, Workflow syntax, [docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax), `jobs.<job_id>.steps[*].shell`:

| Platform      | `shell:`    | Documented command                         | Documented note                                                                                                                                |
| ------------- | ----------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Linux / macOS | unspecified | `bash -e {0}`                              | "Note that this runs a different command to when `bash` is specified explicitly. If `bash` is not found in the path, this is treated as `sh`." |
| All           | `bash`      | `bash --noprofile --norc -eo pipefail {0}` | "The default shell on non-Windows platforms with a fallback to `sh`."                                                                          |
| Linux / macOS | `sh`        | `sh -e {0}`                                | fallback when no shell is given and bash is absent                                                                                             |
| All           | `pwsh`      | `pwsh -command ". '{0}'"`                  | Windows default                                                                                                                                |

"Exit codes and error action preference": "`bash`/`sh`: By default, fail-fast behavior is enforced using `set -e` for both `sh` and `bash`. When `shell: bash` is specified, `-o pipefail` is also applied to enforce early exit from pipelines that generate a non-zero exit status. You can take full control over shell parameters by providing a template string to the shell options. For example, `bash {0}`. `sh`-like shells exit with the exit code of the last command executed in a script, which is also the default behavior for actions." `defaults.run.shell` (and `jobs.<job_id>.defaults.run.shell`) set the shell for every `run:` step in scope; the example is `defaults: run: shell: bash`.

Reading: a `run:` step without `shell:` has `-e` and no `pipefail`, and it also has no `--noprofile --norc`, so the runner's bash startup files are read (a difference the docs call out only as "a different command"). A pipeline such as `cmd | tee file` in such a step succeeds when `tee` succeeds.

Repository today (`grep` over `.github/workflows/*.y*ml`, 2026-10-30): no `defaults:` block in any workflow. Seven steps declare `shell: bash` (`agent-assets.yml:48`, `private-bootstrap.yaml:95`, `:177`, `remote.yaml:61`, `:145`, `:195`, `:231`). Of the multi-line `run:` steps that rely on the default shell, these set `set -euo pipefail` themselves: `agent-assets.yml:85`, `:107`; `drift-watch.yml:56` (and `:40` `set -uo pipefail`, deliberately without `-e`); `macos.yaml:53`; `private-bootstrap.yaml:42`; `ubuntu.yaml:53`; `test.yaml:79`, `:284`, `:296`, `:331`, `:466`. These multi-line default-shell steps set neither `shell:` nor `pipefail`: `docs.yml:64`, `:73`; `drift-watch.yml:94`; `macos.yaml:110`, `:137`, `:141`, `:152`, `:189`; `private-bootstrap.yaml:80`; `remote.yaml:46`, `:127`; `test.yaml:159`, `:175`, `:258`, `:274`, `:411`, `:421`, `:448`; `ubuntu.yaml:100`, `:149`. Of those, the ones that contain a `|` pipeline were not enumerated here; `remote.yaml:171-173` documents the one place where the comment says "pipefail keeps a failed setup.sh failing through the tee", and that step does declare `shell: bash` (line 145).

Verdict: the vendor's two defaults differ in exactly the option the repository's standing order on masked returns cares about. A-7 makes the shell explicit once per workflow so that the AST lint of research/01 section 2.5 and the workflows agree on which options a `run:` script starts with.
