### 1.2 How each bounds its rule surface, and how it treats an earlier step in the same job

- zizmor. The surface is the audit list; each audit documents its type (workflow, action, Dependabot), offline capability and whether it is configurable (`forbidden-uses` and `unpinned-uses` take rule tables; `anonymous-definition`, `concurrency-limits`, `self-hosted-runner`, `stale-action-refs`, `undocumented-permissions` are pedantic-only; `misfeature` and `secrets-outside-env` are auditor-only). No custom-audit engine appears on the audits or usage pages read (inferred from absence). Its `adhoc-packages` audit is the nearest thing to the apt rule: "Detects `run:` steps that install or manipulate packages in an ad-hoc manner" for JavaScript (`npm`, `yarn`, `pnpm`) and Ruby (`gem`, `bundle`) only; no apt, no notion of a bound. On steps trusting each other: `github-env` says an attacker who sets variables "may be able to set `LD_PRELOAD` or otherwise induce code execution implicitly within subsequent steps" and advises "If you need to pass state between steps, consider using `GITHUB_OUTPUT` instead"; `self-repository` notes an action "can't load an action that was cloned at runtime in a previous step". The claim it does not make is that a step is trustworthy because an earlier one passed: it audits each `uses:`/`run:`/`with:` site on its own and flags the channels (env, path, credentials on disk) by which a step reaches the next. Its stated design rule for template expansions under the pedantic persona is the allowlist argument of section 3: "`zizmor` considers all template expansions in code contexts to be code smells, and attempting to selectively permit them is more error-prone than forbidding them in a blanket fashion" (doc).
- actionlint. The surface is the workflow grammar and the expression type system. It is flow-aware for `steps.<id>` only as typing: "Accessing the outputs before running the step causes `null`" and "Step objects are job-local" are errors, which is ordering, not trust. Its untrusted-input list does not contain `steps.*.outputs.*` or `env.*` (octoscan adds them), so a value an earlier step wrote is trusted by actionlint. For `run:` bodies it defers to ShellCheck, after replacing every `${{ }}` with underscores and disabling SC1091, SC2050, SC2194, SC2154, SC2157 and SC2043 "to avoid errors due to the syntax" (doc). It has no rule language; the config file only filters messages.
- poutine. The surface is 13 Rego rules plus user Rego. Its cross-step rule is a sequence pattern (checkout of `github.event.pull_request.head.*` then a command from the Living Off The Pipeline list), and the rule page says of the Azure DevOps variant "False positives are likely given that static analysis of solely the pipeline file is not enough to confirm exploitability". A custom rule sees `step.run` as a string and matches it with `regex.match` (the README's example), which is the text-rule shape plan D1 moved away from.
- octoscan. Same parser as actionlint, security rules only; its untrusted list is the widest of the four (step outputs, env, needs outputs), so it is the only one of these that treats an earlier step's output as hostile by default. No per-command or timeout rule.
- ghalint. Policies are key-presence checks on the YAML; `job_timeout_minutes_is_required` is the only timeout rule in any of these tools and it stops at `timeout-minutes` on the job or on every step. It does not read `run:` bodies.
- Scorecard. Three pattern checks over workflows, scored, meant for ranking repositories rather than gating a PR; it states its own blind spot ("does not detect whether untrusted code checkouts are used safely"). Pinned-Dependencies does read shell scripts for unpinned downloads, which is adjacent to U99's bound rule but about pinning, not time.
- harden-runner. Not a linter: it observes the job at run time and attributes each network call, process and file write to a step. It is the only tool here that sees what an earlier step actually did, and it sees it after the fact or blocks egress by allowlist; it has no view of `timeout` or of a stalled apt call except as absence of events.

### 1.3 Could any of them replace "every apt call in a workflow is bounded by timeout"

No. The rule U109 ended with (PR #585 Contract, measured) is: every apt call in `.github/workflows/*.y*ml` is the exact form `sudo /usr/bin/timeout --kill-after=10 <N> apt-get -o Acquire::http::Timeout=15 -o Acquire::Retries=3 update|install -y <packages>`, as a statement of its own in a step whose `run:` body holds nothing but such statements, whose `if:` equals one of two whole expressions, whose `timeout-minutes` is a formula of its bounds, whose `env:` names are a fixed tuple, under no `defaults`, with a `shell:` key absent or exactly `bash`, with the key sets of the workflow, job and step levels pinned to measured tuples, read from shfmt's typed JSON under the U105 contract, with a text layer over every line and an exemption table keyed by file and exact line. The parts an existing tool covers:

| Part of the U109 rule                                                | Nearest OSS coverage                                                                                            | Gap                                                                                                                                                 |

| `timeout-minutes` present on the apt steps and their job             | ghalint `job_timeout_minutes_is_required` (job, or every step)                                                  | Presence only; U109 pins the value to a formula of the per-call bounds (`BoundOrderTest`)                                                           |
| An install command in `run:` is of a known form                      | zizmor `adhoc-packages` (npm, yarn, pnpm, gem, bundle)                                                          | No apt; the audit asks for a lockfile, not a bound                                                                                                  |

| `GITHUB_ENV`, `BASH_ENV`, `LD_PRELOAD`, `PATH` reaching a later step | zizmor `github-env`, octoscan `dangerous-write` (writes to `GITHUB_ENV`/`GITHUB_PATH` under dangerous triggers) | Neither reads a workflow-level or job-level `env:` or `container:` as U109 rounds 16 and 17 do; both scope the finding to attacker-triggered events |

The closest honest delegation is ghalint for the presence of `timeout-minutes` (a key check that will not drift) and zizmor's regular persona for the channels its `github-env` audit names. Everything that made U109 take 22 rounds, the form of the command, the closed body, the shell, the environment and the key sets, has no tool, because no tool models "this step may do nothing else" (inferred; section 3 says why that is the only closable shape).

### 2.3 Does U112 match the vendor state, and what remains

U112's rule a is stricter than SC2312 where SC2312 is silent by design (the plain assignment whose statement is not an `if`/`while` condition or the left side of a handled `||`), rule b encodes producers ShellCheck cannot know (`git ls-files`, `git config -f`, `find`, `ls`, each with a measured row), rule c requires `set -euo pipefail` before the first substitution rather than "anywhere in the file", and rule e makes every exemption carry a reason. ## 3. Why "a command whose status is never checked" and "any way to rebind a word" are open-ended in full Bash

### 3.1 The theoretical frame

"Is this command's status checked" and "can this word name anything but the program it spells" are properties of what the script does when run, not of how it is written. Rice's theorem: "all non-trivial semantic properties of programs are undecidable", and the way around it that applies here is to "require programs to be annotated with extra information that proves the program is correct, or to be written in a particular restricted form that makes the verification possible, and only accept programs that are verified in this way" (doc, <https://en.wikipedia.org/wiki/Rice%27s_theorem>). The shell makes the semantic side worse than for most languages because the program text is itself data: `eval` "concatenated together into a single command, separated by spaces. Bash then reads and executes this command" (Bash 4.1), and the HotOS paper's diagnosis is that "the behavior of a shell program cannot be known statically", so "a static analysis would either have to be unsound, assuming that the state ahead of time will be the same as the state at runtime, or ineffective, conservatively assuming the worst for every part of the state that can be modified at runtime" (doc, HotOS 2021 section 2.2, B2). Research 04 entry 15 carries the same point from the 2025 and 2026 literature and entry 14 the measured fragility of command denylists.

### 3.3 The channels that lose a status

The manual's `set -e` exceptions: "The shell does not exit if the command that fails is part of the command list immediately following a `while` or `until` reserved word, part of the test in an `if` statement, part of any command executed in a `&&` or `||` list except the command following the final `&&` or `||`, any command in a pipeline but the last (subject to the state of the `pipefail` shell option), or if the command's return status is being inverted with `!`. If a compound command other than a subshell returns a non-zero status because a command failed while `-e` was being ignored, the shell does not exit." (4.3.1). Command substitution runs "in a subshell environment" (3.5.4) where "Bash clears the `-e` option" unless `inherit_errexit` (3.7.3). The declaring builtins return their own status (SC2155). `PIPESTATUS` is overwritten by the next command, `[` included (Google). Oils' summary of the design fault: "`local x=$(false)` ... 2 exit codes, but just one `$?`"; "`diff <(sort left) <(sort right)` ... 3 exit codes, but just one `$?`" (doc). BashFAQ 105: the `set -e` rules "are extremely convoluted, and they still fail to catch even some remarkably simple cases. Even worse, the rules change from one Bash version to another" (doc, <https://mywiki.wooledge.org/BashFAQ/105>). Whether a given `$(…)`'s status reaches a decision therefore depends on the enclosing construct, the options in force at that moment, the dialect and the Bash version, which is a semantic property in the sense of 3.1.

### 3.4 What a finite allowlist of accepted constructs buys

1. It turns the semantic question into a syntactic one. "Is this `CmdSubst` the whole value of the one assignment of a statement that is an `if` condition or the left side of a `||` whose branch is one of four shapes" is decidable by walking the tree, and the answer does not depend on run-time state. Rice's theorem is not evaded; the property checked is changed to one about the text, and every program outside the admitted set is refused whether or not it would have been safe (the false-positive side is accepted on purpose, as zizmor's pedantic template rule accepts it).
2. It bounds the residual risk to a list that can be read. After U109 round 12, the apt steps hold only the form, so the only ways a word in them names something else are the channels outside the step's text; rounds 15 to 17 then closed `defaults.run.shell` and `shell:`, `env:` (`BASH_ENV`, `ENV`, `SHELLOPTS`, `LD_PRELOAD`, `PATH` named), and `container:`, which are exactly the manual's startup inputs (6.2, 5.2) and the runner's own interposition. The remaining residual is written down in the Contract ("Left out": a composed string run through `eval` or `bash -c` in a step that runs no apt, and repository scripts a step runs are not read) rather than discovered one round at a time.
3. It makes the next finding a change to the set, not to a recogniser. U112's branch allowlist (four shapes) ended a class that a denylist of discarding branches had not ended in three rounds (decisions row 2026-10-29T10:53:54Z); U109's "no table of commands" removed `REFUSED_COMMANDS`, `ALLOWED_USES` and `WRAPPERS` and with them the question of spelling.
4. It is the form the vendors reach for when they want a guarantee: `rbash` is an allowlist of operations with its scope stated (startup files are read first, and a script it runs is unrestricted); Oils' `strict_errexit` "disallows" constructs rather than detecting bad outcomes and the author notes "the resulting style is straightforward and explicit. Earlier attempts allowed code that is too subtle"; the Google guide allowlists the language (Bash only), the size (100 lines) and the constructs (`eval` and aliases out).
5. What it does not buy: anything the allowlist admits by mistake is admitted for every file (so the set must be measured first, as `APT_ENV_NAMES`, `WORKFLOW_KEYS` and `KNOWN_CHARACTERS` were), and anything that reaches the process from outside the text (an exported function, `BASH_ENV` from a parent the workflow does not control, a modified `/usr/bin/timeout`) is closed only by the run-time switches (`-p`, a clean environment, a pinned image), never by a text rule (inferred).

## 5. Recommendation

The bespoke lints can hand off three things and should keep the rest. Hand off: the presence of `timeout-minutes` on every job and step to ghalint's `job_timeout_minutes_is_required` (a key check that cannot drift and costs one binary), the `GITHUB_ENV`/`GITHUB_PATH`, credential-persistence, permission and pinning audits to zizmor's regular persona with `--min-confidence=medium` in CI (41 audits the program would otherwise never write, each with a documented severity and confidence), and the shell baseline to ShellCheck 0.11.0 as today with `check-extra-masked-returns` and, after plan D2's measured row, `check-set-e-suppressed`. Keep: the exact apt form and the "an apt step holds nothing but the form" rule with its shell, environment and key-set closure (no tool models a step that may do nothing else, and poutine's custom-rule path is a regex over the body text), the two accepted positions of a command substitution and the four handled branches (stricter than SC2312 exactly where SC2312 is silent on purpose), and the producer table with its stderr capture (a measured fact about `git ls-files` and `git config -f` that no linter can know). Adopting zizmor and ghalint adds two more pinned tools to `scripts/ci/pinned-tool-version.sh` and two more version rows to the drift watch; the brief that adopts them should pin by SHA and measure the finding count on `origin/main` first, in the shape of the `check-set-e-suppressed` row, before any exit code is required (inferred).
