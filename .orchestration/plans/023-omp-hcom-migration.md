## <ubuntu-host>: two ways, one recommendation

| | hcom relay | herdr machine add + ssh |
|---|---|---|
| what it carries | messages and remote spawn (`--device`) | screens: the remote herdr's workspaces, tabs and agents in the local TUI |
| authentication | one PSK per relay inside the join token, shared by every device, no revocation (rotate with `relay new`); payloads encrypted end to end; the broker sees topics, timing and sizes | SSH keys and MFA; approval-based remote setup |
| exposure | a broker reachable by both machines: a public broker (default) or a private one (`--broker`, `--password`) | the SSH port only |
| failure | the broker down means no messages; the PSK leaked means a new relay | one machine lost does not disconnect the others |

Recommendation: both, each for its role, with the broker kept off the internet: a private MQTT broker on the Mac bound to localhost (an asset of PR A if hcom needs one beside the public default), reached from spark through an SSH port forward, so the join token's broker URL is localhost on both devices, the password guards the broker, the PSK guards the payloads, and nothing listens on a public address; herdr machine add attaches spark's panes to the Mac's TUI over the same SSH host. The token and the broker password travel only over SSH (`hcom relay connect <token>` typed on spark), never in chat, in the repository or in a rendered file; rotation is `hcom relay new` plus a reconnect on each device. The public-broker variant stays a documented fallback for a machine that cannot reach the Mac over SSH.
