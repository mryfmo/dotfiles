### 1.2 設計（失敗 class を不可能にする機構）

- 失敗 class「子が席の外に出る」: 子は omp プロセスの子（SDK が spawn）。hcom participant になる経路は `hcom omp` だけで、子は `hcom` を呼ばない（bridge の src に `hcom` の語が 0 であることを #19 で `grep -c` し、0 を記録）。herdr pane は `hcom omp --terminal herdr` だけが作る。→ assertion は participant 数と pane 数の**不変**（#21 (6)）。
- 失敗 class「子が omp の第 2 層（policy deny）を迂回する」: **設計で閉じる** = `tools: []` + MCP server 経由の実行【実測 facts §2b】なので、子に Bash/Edit/Read の native tool は無く、全 tool call は omp の `tool_call` hook と `bash.patterns` deny を通る。assertion = #21 の各 command が `events.log` に `tool_call bash …` として残る（omp が実行した同一性）+ (2) の `gh pr merge` が policy 層の拒否文を返す + (7) 子の tool 一覧の自己申告が bridged MCP tool 名だけで native 名を含まない。README の「Bash commands get Claude Code's 120-second default timeout」は MCP tool call 側の timeout として #21 (3) で測る。
- 失敗 class「子が操作者の個人設定・project 設定を実行入力に取る」: `settingSources` 既定で `~/.claude/settings.json` と cwd の `.claude/settings.json` が読まれる【実測 facts §2b】→ 体制 hook は `PI_CODING_AGENT` で skip（A-S6）; project 側は `<clone>/.claude` が denyWrite【plan §1.3 E-21】（X 後）、`<main>/.claude/hooks` が denyWrite【P-01】、main に入る変更は保護パス PR（操作者 merge）。残余 = merge 済 main の `.claude/settings.json` の hook が子で走る（P-01 と同 class）、#21 (4) の canary で実在を測る。X 後の既定 (31) で子の config dir を profile 配下にすると `~/.claude` 側は消える。
- 失敗 class「鍵の経路が増える」: bridge は API key を持たず、子は操作者の login を使う。席の環境に 3 名が無いことを `hcom-seat` が起動前に検査し（X 前）、validator が source を見る（A-S7）。omp の store に Anthropic 資格情報が無いことは v12 の probe のまま。
- 失敗 class「版の漂流」: 固定資産 + receipt（A-S2）。bundled binary の版は SDK `^0.3.293` の caret 解決【実測 facts §2】で変わりうるので receipt に版を記録し、doctor が差を warning にする（§5 行）。
- fallback の機構: `anthropic/` 経路は v12 の字面（§1.9 の `auth import`、§4 #6b）をそのまま残す。切替 = manifest の値 + `make update` + 席の再起動（席は `--model` で受ける【plan §1.4】）。
