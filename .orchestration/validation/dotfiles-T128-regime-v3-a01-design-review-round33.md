## Findings

[P1] high .orchestration/tasks/dotfiles-T128-regime-v3-a01.md:62 A `none` row is never cross-checked: the refusal list is "a reached or unknown count with no row, a row with an empty evidence, a det-check row without its two matching entries, or a p0p1 row whose ids fail the source check", so the gate validates only the claims that force a reset and accepts `trigger none` with any non-empty evidence even when its own data contradicts it (two `gate_refusals` entries of the same block naming one check on two commits of base..HEAD, which the gate itself wrote and reads; or a reached `bot_p1_heads` or `audit_p1_heads` count, whose two heads are by construction two P0 or P1 ids on two commits); the orchestrator therefore classifies every reached count as `none` and merges, which is R5 (threat_model line 46) in JSON form, and the `none` evidence is a pasted command output inside a sentence whose counts are "raw, never a pasted line". INV-1's one-account residual does not cover this: the residual is a record the gate cannot tell from a genuine one, not the gate declining to compare two fields it already holds. One clause closes it: the gate refuses a `none` row when its own entries meet the det-check condition or when the row's count is `bot_p1_heads` or `audit_p1_heads` (whose trigger is `p0p1` with the two heads' ids).

[P1] high .orchestration/tasks/dotfiles-T128-regime-v3-a01.md:62 "An unknown count stands as reached" is applied to "the gate and the boundary check" alike, but the parenthetical defines `unknown` by missing PR commits or `original_commit_id` while `scripts/regime-counters.sh:145-153,158` prints the same token for a task with no PR and for any `gh` failure, and the count line alone cannot tell them apart; live instance: `dotfiles-T121-claude-hook-install-hint-a01` (RESULTs carry no `pr=`, so `detail: pr=none`; its prose record says `pr=310`, the T118 PR; a legacy file with no `kind`; no reset record; revises 1, amendments 0, questions 0) fails both silencer branches and would be reported forever, and after T16 lands a transient `gh` failure at `scripts/check-regime-boundary.sh:295` turns every merged record's `threshold_dispositions: []` into a reported `unknown` with no row; D1 (`make check-regime-boundary` rc 0), the bar round 32's P1 used, is unattainable again. Fix: scope "stands as reached" to the gate (which always has a PR and a sweep), and have the boundary check treat `unknown` as reached only when the task's `detail: pr=` is digits and the counters' GitHub state was `ok` for the PR's commits.

[P2] high .orchestration/tasks/dotfiles-T128-regime-v3-a01.md:62 The det-check trigger cannot be reached by the sweep's checks: `main()` runs `pr_feedback_errors` at `scripts/require-crit-review.py:997` and exits at 1002 before `acceptance_errors` opens the record at 1018, and the sentence writes an entry only "after the record is opened and its task, head and pr verified" (the table's slug list at line 254 omits the sweep); so an undispositioned CI failure, a bad `fixed:<commit>`, or the `not-applicable` without `evidence=` that INV-6 itself names as a refusal never produce an entry on any head, and plan 020's "failed deterministic check" archetype is exactly that class. Either open and bind the record (file name, `pr`, `head`) before the sweep check so the sweep refusals are entries with their own slug, or state in the sentence that the det-check trigger covers only the post-record checks.

[P2] medium .orchestration/tasks/dotfiles-T128-regime-v3-a01.md:61 INV-5 and INV-6 specify the same manifest differently: INV-5 (byte-equal) says "path to sha256 of every input as read … the gate recomputes the manifest at gate time", while INV-6 says the manifest "covers the record without" `gate_refusals`; a V4 worker implementing INV-5 from its own sentence hashes the file and every post-audit entry stales the audit, which is the round-32 P2 restated. The note defers this to a later hashed change on purpose; it is recorded here so the next hashed change moves one clause into INV-5 (hash the record's pre-audit text with the gate's key removed).

[P3] medium .orchestration/tasks/dotfiles-T128-regime-v3-a01.md:62 Two predicates for one fact: the `bot_p1_heads` count takes only commits after the first RESULT's head (the counters' `$shas[$i + 1:]`), while the `p0p1` trigger needs "two distinct commits of the PR, the later after the first RESULT's head"; a trigger with one P0/P1 before the first RESULT has `n = 1` and so no row to live in (a row exists only for a reached count), making that half of the trigger definition unreachable unless another count is reached; name one predicate.
