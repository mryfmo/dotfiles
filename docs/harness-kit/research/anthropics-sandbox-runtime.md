## 1. The project

- Repository facts (measured with `gh api repos/anthropics/sandbox-runtime` on 2026-11-02): created 2025-10-20, default branch `main`, Apache-2.0, 6911 stars, 320 open issues, last push 2026-10-30. Tags v0.0.77 to v0.0.81; releases v0.0.79 (2026-10-07), v0.0.80 (2026-10-16), v0.0.81 (2026-10-20). Recent commits after the release: Windows install fixes, "proxy: a SOCKS CONNECT to a mitmProxy host goes through the MITM socket (#764)", a CI trust-store change. `package.json` on `main` still says `0.0.81`. The npm registry's newest version is 0.0.81 (measured with `npm view`), the version mise installs here.
- README, [github.com/anthropics/sandbox-runtime](https://github.com/anthropics/sandbox-runtime): "A lightweight sandboxing tool for enforcing filesystem and network restrictions on arbitrary processes at the OS level, without requiring a container"; "uses native OS sandboxing primitives (`sandbox-exec` on macOS, `bubblewrap` on Linux) and proxy-based network filtering"; "Beta Research Preview ... developed for Claude Code ... APIs and configuration formats may evolve."
- Shape: TypeScript, `bin.srt = dist/cli.js`, `engines.node >= 22.12.0`, runtime dependencies `@pondwader/socks5-server`, `commander`, `node-forge`, `zod ^3.25.0` (imports `zod/v3`). Vendored: `vendor/seccomp` (prebuilt BPF filters and `apply-seccomp` for x64 and arm64, sources in `vendor/seccomp-src`), `vendor/srt-win` (Windows helper), `vendor/java-proxy-agent` (a JVM agent injected through `JAVA_TOOL_OPTIONS` so Java tools honour the proxy). Three entry points: the `srt` CLI, the `SandboxManager` library (`initialize`, `wrapWithSandbox`, `registerCommandNetworkLists`, `annotateStderrWithSandboxFailures`, `updateConfig`), and `srt proxy` (`docs/srt-proxy.md`), the HTTP proxy alone with an external decider.
- Settings file semantics (README "Updating the config while the command runs" and the paragraph before it): no `~/.srt-settings.json` and no `--settings` means built-in defaults (no network, writes only to srt's own paths, unrestricted reads); a file that exists but is empty, unreadable or invalid is an error and srt exits; a `--settings` path that does not exist is an error too. `--control-fd <fd>` replaces the whole config from a descriptor while the command runs; only the network lists and `credentials.sigv4` change at runtime, the filesystem rules are fixed when the command is wrapped. Open issue [#434](https://github.com/anthropics/sandbox-runtime/issues/434) (2026-08-04): "Unknown top-level config keys are silently ignored, so a typo'd denyWrite fails open with no warning."
- Dual isolation model (README "How It Works"): "Both filesystem and network isolation are required for effective sandboxing. Without file isolation, a compromised process could exfiltrate SSH keys ... Without network isolation, a process could escape the sandbox and gain unrestricted network access." Reads are deny-then-allow (open by default, most specific entry wins), writes are allow-only (`denyWrite` beats `allowWrite`), network is allow-only.

## 2. Isolation primitives

### 2.1 macOS: Seatbelt through `sandbox-exec`

Read in the installed 0.0.81 `dist/sandbox/macos-sandbox-utils.js` (line numbers are that file's) and the README.

- The profile starts `(version 1)` (line 755), then `(allow process-exec)` (762): the sandbox does not restrict which binaries run, only what they can touch. A baseline mach-lookup list (772 to 813) includes `com.apple.SecurityServer` (907), which the manifest comment notes cannot be removed ("allowMachLookup only adds services", `home/dot_agents/agent-config.yaml:972-974`); `network.allowMachLookup` adds names or `global-name-prefix` entries (812-813). `enableWeakerNetworkIsolation` adds `com.apple.trustd.agent` (792); `allowAppleEvents` adds the coreservices names (799-805) and, per the README, "the sandbox no longer provides code-execution isolation".
- Reads: `(allow file-read*)` first (640), then `(deny file-read* ...)` for `denyRead`, `(allow file-read* ...)` for `allowRead`, then the denies that are more specific than the allows re-emitted (619-631). Writes: `(allow file-read* file-write* ...)` for each allowed root (1030) with denies inside them. Paths are compiled to Seatbelt `literal`, `subpath` or `regex` filters from a git-style glob grammar (`*`, `**`, `?`, `[abc]`, README "Path Syntax (macOS)"); the README adds that an entry with `*`, `?`, `[` or `]` is read as a pattern and also as the path when it exists, and that `{ "path": ..., "literal": true }` names a path and nothing else. That grammar is why `hcom-seat` refuses any settings path that is not `[A-Za-z0-9._@+-]` components (`home/dot_local/bin/common/executable_hcom-seat:217-220`: "srt 0.0.81 turns a settings path into a Seatbelt regex or a glob, so `/private/tmp/hcom*` would grant its siblings"). Open issue [#576](https://github.com/anthropics/sandbox-runtime/issues/576) (2026-09-19) describes a literal path with `[...]` compiling to a non-matching regex and voiding a `denyRead`.
- Network: `(deny network*)` by default and, when the network is restricted, `(allow network-bind|inbound|outbound (local|remote ip "localhost:<httpProxyPort>"))` and the same for the SOCKS port (982-992); nothing else leaves. `allowLocalBinding` renders `(allow network-bind (local ip "*:*"))`, `(allow network-inbound (local ip "*:*"))` and outbound to `localhost:*` (952-954), every interface, which is why no seat gets it (`executable_hcom-seat:1716-1719`; open issue [#131](https://github.com/anthropics/sandbox-runtime/issues/131), "Data exfiltration via IP when allowLocalBinding: true"). Unix sockets: `allowAllUnixSockets` renders `path-regex #"^/"` (966-967), `allowUnixSockets` renders `subpath` rules per path (975-976); nothing by default.
- `allowPty` renders `(allow pseudo-tty)` plus `/dev/ptmx` and `/dev/ttys*` (1025 and README); the seats set it (`executable_hcom-seat:1728`), since omp runs interactively in a herdr pane.
- Writable without listing (`dist/sandbox/sandbox-utils.js:499-508`): `/dev/stdout`, `/dev/stderr`, `/dev/null`, `/dev/tty`, `/dev/dtracehelper`, `/dev/autofs_nowait`, `/tmp/claude`, `/private/tmp/claude`; and `~/.npm/_logs` and `~/.claude/debug` unless a `denyRead` covers them (README "A few paths are writable without being listed"). `hcom-seat` counts all of them as seat write roots (`executable_hcom-seat:738-749`, `1349-1365`).
- Credential files in `mode: "mask"` degrade to deny on macOS ("SBPL cannot redirect reads", `src/sandbox/sandbox-config.ts`, the comment above `CredentialFileConfigSchema`).
- Violations: the README's "Violation monitoring: On macOS, tap into the system's sandbox violation log store"; the code runs `log stream` and filters `Sandbox:` deny lines (the `[Sandbox Monitor]` strings are also present in the Claude Code binary, measured with `strings` on `claude.exe` 2.1.312).
- **Measured** on this host (srt 0.0.81, settings: `denyRead ~/.ssh`, one `allowWrite` scratch directory, no domains):

  | Probe inside `srt`                                                | Result                                                                        |
  | ----------------------------------------------------------------- | ----------------------------------------------------------------------------- |
  | `touch <allowWrite dir>/w`                                        | `probe-write-ok`                                                              |
  | `touch ~/srt-canary-hk`                                           | `home-write-denied`, no file created                                          |

### 2.2 Linux: bubblewrap, namespaces, socat, seccomp

Read in the installed 0.0.81 `dist/sandbox/linux-sandbox-utils.js` and the README ("Path Syntax (Linux)", "Platform-Specific Dependencies").

- Mount view: `--ro-bind / /` (1966), then `--bind <path> <path>` for each `allowWrite` entry (2014) with ancestor "covers" where a write root sits under a pinned directory (1540-1602), `--ro-bind <path> <path>` for `denyWrite` entries inside write roots (2419, 2454), `--tmpfs` for a read-denied directory (2770; inside the sandbox it is "an EMPTY WRITABLE directory" whose content is lost at exit, README), `--ro-bind /dev/null <file>` for a read-denied file or a symlink in a denied path (2376-2404, 2621), `--dev /dev` and `--proc /proc` (`enableWeakerNestedSandbox` bind-mounts the container's `/proc` instead, README and Claude docs "Bubblewrap fails to start inside a container"). Masked credential files are fake files bound read-only over the real path, with the store directory bound read-only over itself (2633, 2792).
- Write entries are literal on Linux: "`allowWrite` / `denyWrite` take literal paths. A trailing `/**` is dropped ... any other glob pattern there is skipped"; `denyRead` and `allowRead` globs are expanded with ripgrep "to the entries that exist when the command is wrapped, so a file that appears later is not covered"; a pattern with a wildcard in its first component is skipped and "A skipped pattern hides nothing". Writes are granted "only to paths that exist", which is why `hcom-seat` creates the seat's directories first (`executable_hcom-seat:1641-1652`) and why the worktree-pattern denies are macOS only (`1674-1684`).
- Network: `--unshare-net` always when the network is restricted. The architecture note (1174-1196): the namespace has "NO network access"; the host runs socat bridges `UNIX-LISTEN:<tmp>/claude-http-<id>.sock,fork,reuseaddr` to `TCP:localhost:<httpProxyPort>` and the same for SOCKS; the sockets are bound into the sandbox, where socat listeners on `TCP6-LISTEN:3128` and `1080` forward into them (1455-1470); the command gets `HTTP_PROXY=http://localhost:3128` and a `GIT_SSH_COMMAND` through SOCKS. "Unlike macOS sandbox which can enforce domain-based allowlists at the kernel level, Linux's `--unshare-net` provides only all-or-nothing network isolation. Domain filtering happens at the host proxy level." `allowLocalBinding` is ignored on Linux: the namespace's loopback is private (README).
- seccomp: the packaged `apply-seccomp` binary (`vendor/seccomp/{x64,arm64}`) is run after the socat relays "so socat can still create Unix sockets" (1472-1476) and installs two filters: one refusing `socket(AF_UNIX, ...)` (`allowUnixSockets` is "Ignored (seccomp can't filter by path)"; `allowAllUnixSockets: true` disables the filter; ia32 is unsupported because `socketcall()` cannot be inspected, `generate-seccomp-filter.js:99-104`), and one refusing `unshare` and `clone` with the user or mount namespace flags, `setns`, `mount`, `umount2`, `pivot_root`, the newer mount calls (`EPERM`) and `clone3` (`ENOSYS`), with `user.max_user_namespaces` set to 0 (README "The command stays in the namespaces made for it"). Rationale: "Every write deny on Linux is a read-only bind mount, and a bind protects a path only in the mount namespace it was made in. Creating a user namespace ... gives its creator a full capability set over a private copy of the mount tree, from which the binds can be removed." Without the helper (`allowAllUnixSockets`, or an unsupported architecture) bubblewrap gets `--disable-userns` instead, which needs bubblewrap 0.8.0 or later, not setuid, and `enableWeakerNestedSandbox` off; "where it cannot be done nothing limits namespaces, and a warning is logged once per process". `allowNestedUserNamespaces: true` turns the limit off for commands that must sandbox themselves (Chromium, rootless podman, a nested bubblewrap or srt), and the README says to "treat `denyWrite` and the mandatory denies as not holding against any command run under it".
- Dependencies: `bubblewrap` (0.4.0 or later; 0.5.0 for binding non-regular files), `socat`, `ripgrep` (`install/ubuntu/common/dependencies.sh:8-11` installs all three). Ubuntu 24.04 and later restrict unprivileged user namespaces through AppArmor; the README offers the sysctl or a per-binary profile, and this repository ships the profile (`install/ubuntu/common/apparmor/bwrap-userns`, loaded by `apparmor_userns.sh`). `bwrapPath`, `socatPath`, `ripgrep.command` and `seccomp.applyPath` let a caller name absolute binaries, which `hcom-seat` does with checked physical paths (`executable_hcom-seat:1604-1621`).
- Open Linux issues worth knowing before the first Linux seat run: [#428](https://github.com/anthropics/sandbox-runtime/issues/428) "apply-seccomp fails with EPERM on /proc/self/setgroups on bare-metal Ubuntu 24.04: bwrap 0.9.0 clears CapBnd before the helper nests its own userns"; [#429](https://github.com/anthropics/sandbox-runtime/issues/429) "apply-seccomp aborts on Ubuntu: AppArmor denies CAP_SYS_ADMIN to bwrap children, so no sandboxed command can run"; [#498](https://github.com/anthropics/sandbox-runtime/issues/498) on the secure-mode bounding set; [#796](https://github.com/anthropics/sandbox-runtime/issues/796) (2026-10-30) "allow Unix sockets without removing the seccomp helper (for sandboxes nested in srt)". The seat shim's canary would refuse to start omp if any of these stopped the sandbox from holding, which is the intended fail-closed outcome (`executable_hcom-seat:1762-1772`), and `scripts/orchestrator/README.md:190` records "residual: Linux is unmeasured".

### 2.4 The network proxy, on every platform

- Two proxies on the host: HTTP (CONNECT) and SOCKS5, both deciding by the hostname the client presents. Lists: `network.allowedDomains` (exact names, `*.` wildcards, IP literals, bracketed IPv6, optional `:port`), `deniedDomains` (checked first; a bare `*` or `*:22` is deny-all), `deniedDomainReasons` (a model-facing reason, delivered in-band to an SSH client as a pre-key-exchange disconnect). Order of evaluation for the library (README): a `deniedDomains` match denies; an `allowedDomains` match allows; `strictAllowlist` denies; a per-command list registered under an unguessable 22-character id (presented as the proxy username) allows; otherwise the ask callback decides, and without one the connection is denied. The `srt` CLI registers no callback, so an unlisted host is simply refused (measured above: 403).
- Resolved-address check: before dialling an allowed hostname the proxy resolves it once and drops loopback, unspecified, link-local, multicast, broadcast, cloud metadata endpoints, the host's own interface addresses, IP literals in `deniedDomains`, and `deniedResolvedAddresses` (private ranges are not denied by default); `localhost` resolves to loopback only; an IP literal in `allowedDomains` is an explicit carve-out.
- TLS termination (experimental, `network.tlsTerminate`): the proxy terminates each CONNECT with a MITM CA (ephemeral or supplied), so `filterRequest` sees decrypted requests and credential masking can substitute sentinels; `excludeDomains` for mTLS or pinning clients; `refuseOpaqueTunnels`, `requireHostMatch`, `ambiguousRequestTarget` and `stripResponseHeaders` harden the terminated path. Needs Node 22.12 or Bun 1.4.
- `srt proxy` (`docs/srt-proxy.md`): the proxy alone, listening on an inherited descriptor, every request decided by a separate "decider" process over a framed JSON protocol, fail closed (5 s per verdict, protocol violation kills the link, nothing dialled before an allow), every CONNECT terminated, names pinned, private ranges dropped. Built for "an embedding host [that] runs the workload elsewhere (a VM, a container, another sandbox)".
- Default limitation, stated by Claude Code's documentation ([code.claude.com/docs/en/sandboxing](https://code.claude.com/docs/en/sandboxing), "Security limitations"): "the built-in proxy does not terminate or inspect TLS on outbound traffic ... Because the proxy makes its allow decision from the client-supplied hostname without inspecting TLS, code running inside the sandbox can potentially use domain fronting or similar techniques to reach hosts outside the allowlist." The same page: "Allowing broad domains such as `github.com` can create paths for data exfiltration."

### 2.5 Credentials and mandatory denies

- `credentials.envVars` and `credentials.files`, each `deny` (unset, or read-denied) or `mask` (a per-session sentinel inside, the real value injected by the proxy on egress to `injectHosts`, default the whole `allowedDomains`; needs `tlsTerminate` unless `allowPlaintextInject`; files masked on Linux only, `extract`, `decode: jwt`, `maskClaims`, `onExtractNoMatch`, `maskDuplicates`; AWS SigV4 re-signing). The manifest's comment that a `mask` lets a sandboxed client send the placeholder to an echoing endpoint and read the real token back (`agent-config.yaml:960-967`) is consistent with this design: injection applies to any request to an inject host, body included.
- Mandatory denies at the project root and up to `mandatoryDenySearchDepth` (default 3, `sandbox-manager.js:1677`): `DANGEROUS_FILES` `.gitconfig`, `.gitmodules`, `.bashrc`, `.bash_profile`, `.zshrc`, `.zprofile`, `.profile`, `.ripgreprc`, `.mcp.json`; `DANGEROUS_DIRECTORIES` `.vscode`, `.idea`, plus `.claude/commands` and `.claude/agents`; inside `.git`, `hooks` always and `config` unless `allowGitConfig: true` (`sandbox-utils.js:12-39`, `sandbox-manager.js:1680`). Claude Code's page [code.claude.com/docs/en/sandbox-environments](https://code.claude.com/docs/en/sandbox-environments.md) adds the platform difference: on macOS "these denies are checked when a write happens, so they also cover nested files and repositories created during the session"; on Linux "the runtime builds the deny list once at launch ... and does not cover anything the session creates later, such as `git init`". Open issue [#159](https://github.com/anthropics/sandbox-runtime/issues/159): the hardcoded `.idea` deny blocks some git operations.

## 3. Relation to Claude Code's built-in Bash sandbox (`claude.sandbox`, README point 9)

### 3.1 Same engine, two scopes

- [code.claude.com/docs/en/sandboxing](https://code.claude.com/docs/en/sandboxing): "Claude Code builds the sandbox on the open source `@anthropic-ai/sandbox-runtime` package." **Measured**: `strings` on the installed `claude.exe` 2.1.312 contains srt's own log lines (`[SeccompFilter] Found apply-seccomp binary in global install:`, `[Sandbox Linux] apply-seccomp binary not available - unix socket blocking disabled. Install @anthropic-ai/sandbox-runtime globally for full protection.`, `[Sandbox Monitor] ...`, `blocked-by-sandbox-runtime`), so the library is compiled into the binary, not called as a CLI.
- Scope ([sandbox-environments](https://code.claude.com/docs/en/sandbox-environments.md), the comparison table): the sandboxed Bash tool isolates "Bash, PowerShell, and Monitor tool commands and their child processes"; the sandbox runtime isolates "The whole Claude Code process, including file tools, MCP servers, and hooks". The sandboxing page lists what the Bash sandbox never covers: Read, Edit, Write, WebFetch, WebSearch, command hooks, local MCP servers, plugin monitors, LSP servers, the status line command and `apiKeyHelper`. The same page says the Bash sandbox "on its own constrains only shell commands, so it is not sufficient for fully unattended runs", and that `--dangerously-skip-permissions` sessions should run "inside a container, a VM, or the sandbox runtime". That is the tier the omp seats use (section 4.1).

This repository does not install it" (`README.md:627-630`): matches the docs ("The seccomp filter is optional and adds Unix domain socket blocking. Install it with `npm install -g @anthropic-ai/sandbox-runtime` if it is missing") and the srt table (`allowUnixSockets` "Ignored (seccomp can't filter by path)" on Linux). Nuance, **measured**: the Claude Code binary looks for the helper under the directory `npm root -g` prints (the string `npm root -g` sits beside the `[SeccompFilter] Found apply-seccomp binary in global install:` message, and the lookup code calls `execSync("npm root -g")`). On this host `npm root -g` is `~/.local/share/mise/installs/node/26.13.0/lib/node_modules`, which holds no `@anthropic-ai`; the srt this repository installs lives under `~/.local/share/mise/installs/npm-anthropic-ai-sandbox-runtime/0.0.81/lib/node_modules/@anthropic-ai/sandbox-runtime`, a separate prefix (`home/dot_mise/config.toml:23-24`). So the README sentence is right for Claude Code's purposes even though the package is present: a Linux host set up by this repository has srt for the seats and still shows Claude Code's Dependencies tab. Closing it means a copy the node prefix can see (`npm install -g`, or a link from `npm root -g` into the mise install); the second consequence of a missing helper, noted in section 2.2, is that nested user namespaces are then limited only by bubblewrap's `--disable-userns` where that flag is available (**inferred** from the README; unmeasured on this repository's Ubuntu host).
- "`sandbox.network.allowAllUnixSockets` is deliberately not used" (`README.md:641-644`): consistent with the srt table (on Linux it "Disable[s] seccomp blocking" entirely, so it would also drop the namespace filter).
- "`failIfUnavailable` is `true` ... `allowUnsandboxedCommands` is `false`" (`README.md:646-655`): Claude Code's own keys; the docs confirm both ("Claude Code ignores the `dangerouslyDisableSandbox` escape hatch") and add that this combination makes the sandbox "admin-required", so repository `.claude/settings.json` cannot widen it (docs "Repository settings under an admin-required sandbox").
- "Two commands run outside the sandbox ... `git push` ... `gh`" (`README.md:655-663`): consistent with the docs' macOS limitation "Claude Code tunnels git's SSH connection through the sandbox proxy, and the macOS tunnel can't authenticate to that proxy" and "Go-based CLIs fail TLS verification on macOS".
- `allowMachLookup: com.apple.trustd.agent` (`agent-config.yaml:1017`, measured in the rendered settings): the same service `enableWeakerNetworkIsolation` opens, about which the README says "enabling this opens a potential data exfiltration vector through the trustd service". The seat settings grant it too (`executable_hcom-seat:1726`). Residual to record if it is not already.
- Not used by the managed settings but available in both Claude Code and srt: `network.strictAllowlist` (docs: "Claude Code denies sandboxed commands access to any host outside the allowlist instead of prompting"; in auto mode unlisted hosts are already refused unless the command lists them and the classifier approves), `deniedDomains` with `deniedDomainReasons`, `deniedResolvedAddresses`.

## 4. Can omp or Codex use it?

### 4.1 omp: yes, and the repository already does

- omp 18.12.6 has no OS sandbox of its own: a search of `~/.local/lib/node_modules/@oh-my-pi/pi-coding-agent/src` for `sandbox-exec`, `bubblewrap`, `bwrap` or `sandbox-runtime` finds nothing (measured); the "sandbox" mentions are the `local://` artifact root, the browser's `--no-sandbox` flag, and task worktree isolation under `~/.omp/wt/` (`src/task/isolation-ownership.ts:1-8`), none of which is containment. The seat policies say so: "Approval is not containment: the OS boundary is the seat's srt sandbox, which `hcom-seat` sets up" (`home/dot_agents/omp/policies/orchestrator.yml:7-8`, `worker.yml:7-8`).
- omp does know it may be run inside one: `src/tools/file-write-fallback.ts:1-16` is "a seam" for "A host that embeds the agent inside an OS sandbox [that] can grant a path mid-session but cannot apply that grant to an in-process write", a registry where an extension can broker a denied `write`, `edit` or `apply_patch` byte-write through a privileged channel. The seats register nothing there (**inferred**: `hcom-seat` runs omp with `--no-extensions` plus the role's extension directories, none of which names this API). It would pair with srt's `--control-fd` only for network lists, since srt's filesystem rules are fixed at wrap time (section 1).
- The seat design (`executable_hcom-seat:1341-1797`, documented in `scripts/orchestrator/README.md:141-173`): on every launch `hcom-seat` writes `<seats-root>/.sandbox/<name>/srt-settings.json` and a shim `<seats-root>/.sandbox/<name>/bin/omp` that hcom pins as the pane's tool. The shim first runs a canary under the settings, `srt --settings ... -- /bin/sh -c '...'`, and refuses to start omp (exit 2) unless a write into the sandbox directory, a read of the settings file and a read of `~/.ssh` all fail inside (`1762-1772`); then `exec srt --settings <settings> -- /usr/bin/env PATH=<seat path> <physical omp> --no-extensions "$@"` (`1787`). The settings: `allowWrite` the seat worktree (or the checkout for the orchestrator), the git common directory, `$HCOM_DIR`, `~/.omp/profiles/<role>`, `~/.omp/run`, the Claude config dir and `~/.claude.json` (the bridge child writes them), `<seats-root>/.state/<name>` (`UV_CACHE_DIR`); `denyWrite` every `.sandbox`, the `.claude` settings and hooks, `.omp`, `.codex`, `.envrc`, `.mcp.json` of the worktree and the checkout, the git state host git reads (`config`, `config.worktree`, `info`, `hooks`, `commondir`, `gitdir`, plus `worktrees/*/...` patterns on macOS), hcom's control files, and the Claude settings, hooks, plugins, commands, agents, skills and `CLAUDE.md`; `denyRead` `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.netrc`, `~/.docker`, `~/.kube`, `~/.config/gcloud`, `~/.codex`, `~/.omp/agent`, `~/.omp/profiles`, `~/.hcom`, `~/.local/state/hcom`, the chezmoi sources, `~/Workspace`, every seats root and `.sandbox`, and for a worker the main checkout; `allowRead` back the seat's own paths and `<checkout>/.orchestration/orchestrate`; `allowedDomains` GitHub, PyPI, Anthropic and OpenAI hosts; `allowUnixSockets: []`, `allowLocalBinding: false`, `allowMachLookup: ["com.apple.trustd.agent"]`, `allowPty: true`; on Linux `bwrapPath`, `socatPath` and `ripgrep.command` as checked binaries. `tests/unit/test_hcom_seat.py:555-600` pins the shape against a fake `srt`.
- What `hcom-seat` relies on from 0.0.81 specifically, each a comment in the script: `SANDBOX_OWN_WRITE_PATHS` (`738-741`), paths read as patterns (`217-220`), `*` as `[^/]*` (`1681`), a deeper deny kept under an allow (`1696`), `allowLocalBinding` as `*:*` (`1717`), writes only to existing paths on Linux (`1641`, `1671`), literal write denies on Linux (`1674`). mise tracks `"npm:@anthropic-ai/sandbox-runtime" = "latest"` (`home/dot_mise/config.toml:24`), so a new release changes the engine under those assumptions without a change in this repository (section 5).

### 4.2 Codex: not as a wrapper

- Codex ships its own OS sandbox. [learn.chatgpt.com/docs/sandboxing](https://learn.chatgpt.com/docs/sandboxing) (the page `developers.openai.com/codex/sandboxing` serves): macOS "using the built-in Seatbelt framework"; Linux and WSL2 need `bubblewrap`, "Codex uses the first `bwrap` executable it finds on `PATH`. If no `bwrap` executable is available, Codex falls back to a bundled helper"; native Windows has its own sandbox. The Linux helper's README ([codex-rs/linux-sandbox/README.md](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md)): bubblewrap "is the default filesystem sandbox", `--ro-bind / /` then `--bind` for writable roots, protected subpaths re-applied read-only, `--unshare-user`, `--unshare-pid`, `--unshare-net` when the network is restricted, a fresh `/proc`, `PR_SET_NO_NEW_PRIVS` and seccomp filters that block network syscalls, `AF_VSOCK` and `io_uring`; a managed proxy mode with a TCP to Unix socket bridge, much like srt's; the legacy Landlock path is rejected for filesystem-restricted policies. Permission profiles (beta) are the layer this repository's audit uses (`home/dot_agents/codex-audit/config.toml`, `pr-audit.sh`).
- **Measured** on this host: `codex sandbox /bin/echo codex-alone-ok` prints `codex-alone-ok` (exit 0). Under srt, `srt --settings <probe> -- codex sandbox /bin/echo codex-nested-ok` prints `WARNING: proceeding, even though we could not create PATH aliases: Operation not permitted (os error 1)` and then `sandbox-exec: sandbox_apply: Operation not permitted`, exit 71. Codex's Seatbelt profile cannot be applied inside srt's, the same failure as the plain nested `sandbox-exec` probe of section 2.1. So on macOS a Codex process under srt could run only with Codex's own sandbox off (`danger-full-access`, or a profile that never spawns a sandboxed command), which trades Codex's per-command boundary for srt's whole-process one (**inferred**; not measured).
- Linux, **inferred** from the srt README: Codex's bubblewrap needs `unshare(CLONE_NEWUSER)`, which srt's seccomp helper refuses with `EPERM` ("a nested bubblewrap or `srt`" is the README's own example; a nested bubblewrap "blames a kernel setting and suggests a `sysctl`, which does not apply here"). `allowNestedUserNamespaces: true` lifts that at the price that srt's `denyWrite` and mandatory denies no longer hold. Open issue [#796](https://github.com/anthropics/sandbox-runtime/issues/796) asks for Unix sockets without removing the helper for exactly this nesting case.
- No Codex setting read for this note delegates sandboxing to an external command: the hosted documentation offers `sandbox_mode`, permission profiles, writable roots, network on or off, and managed proxy mode (**inferred** from the pages above and from `06-codex-and-actions-security.md` section 1). Pairing Codex's managed proxy mode with `srt proxy` as the egress decider is conceivable from the two documents and untested here (**inferred**).
- Conclusion: for Codex the current design is the right one. The audit lever already runs Codex under Codex's own `audit` permission profile with launch-time probes (`pr-audit.sh:60-81`, `1115-1240`), and runs it from the coordinator because `~/.codex` is unreadable inside a seat (`scripts/orchestrator/README.md:173`). Wrapping Codex in srt would break its sandbox on both operating systems.

## 5. The gap for the yolo seats

### 5.1 Status: closed by U85

- Decision D-024-92 (2026-10-22, `.orchestration/decisions.tsv:142`): "OS-level containment is a requirement of the new regime. Means: the seat processes ... run under the same engine Claude Code's sandbox uses, @anthropic-ai/sandbox-runtime (srt), with per-role settings". Unit U85 "OS-level containment of the yolo seats" landed as PR #543, merged f1374ba7, audit "correct ... round 30 (srt seat sandbox with fail-closed canary; Linux write roots; fresh-store first launch; G17 accepted boundary)" on 2026-10-26 (`.orchestration/orchestrate/regime-cutover/units.tsv:97`, `ledger.tsv:151`). Gate G17 was decided the same day: "G17 は U85 マージ後、srt を境界として受け入れる" with three conditions, seats on this repository only, seat output entering only through the PR diff, CI and the apply container, and any widening of allowed domains reopening G17 (`regime-cutover/decisions.tsv:203`).
- What was closed. A `yolo` seat approves every tool call (`approvalMode: yolo`, `orchestrator.yml:10`), and its `bash.patterns` denies see command text only: "another spelling of the program ... a glob, a script that runs it ... passes it, and srt and the seat GitHub identity (U88) are the controls for those" (`home/dot_agents/omp/policies/README.md:11`). srt supplies what the text rules cannot: writes confined to the seat's roots whatever the command's spelling, credential and other-seat reads denied, a network allowlist enforced outside the process, no Unix socket (so the herdr socket cannot start a pane outside the sandbox, and "No seat launches a seat", `scripts/orchestrator/README.md:149`), no listening socket, the git state host git reads write-denied (so a seat cannot plant `core.hooksPath` or `core.fsmonitor` for host git, `executable_hcom-seat:1668-1673`), and a canary that refuses to start omp when any of that does not hold. `docs/orchestrator-seat.md` describes the orchestrator seat's gate, supervisor and skill and leaves containment to `hcom-seat`; its threat table's "residual: ... owner: U85 (containment)" rows in `scripts/orchestrator/README.md:98` point at the same unit.

### 5.2 What srt does not close, as the repository records it

- Same-user host processes: "Host processes (the operator's shell, the coordinator, host git, editors) run as the same user, and they still read files the seat may write ... srt is the boundary for the seat process only" (`scripts/orchestrator/README.md:171`); accepted as G17. The lever self-checks (`claude.levers.sha256`) and `~/.local/bin/common` outside every write root are the mitigations.
- `/tmp/claude`, srt's own TMPDIR, "stays writable to every seat" (`README.md:173`). **Inferred**: it is one directory shared by every seat and by any sandboxed Claude Code command on the host, so it is a channel between seats that the per-seat `denyRead` of the seats root does not cover.
- `~/.claude.json` is writable by the bridge's Claude Code child and "also lists the operator's MCP servers" (`README.md:173`).
- A resumed or forked seat (`hcom r`, `hcom f`) "resolves `omp` from the caller's `PATH`, not through `hcom-seat`, and runs uncontained" (`README.md:173`).
- GitHub identity: `~/.ssh` is unreadable inside, so the seat pushes over HTTPS "through the gh credential helper" (`executable_hcom-seat:1732-1734`); the gh hosts file is not in the seat's `denyRead`, so a seat acts with the operator's token. U88 "seat GitHub identity that cannot merge" is planned, not landed (`units.tsv:100`).
- Allowed domains are exfiltration paths: the seats may reach `github.com`, `api.github.com`, the GitHub content hosts, PyPI, the Anthropic and OpenAI hosts (`executable_hcom-seat:1721-1724`), and the proxy decides by hostname without TLS inspection (section 2.4). G17's third condition names this.
- `com.apple.trustd.agent` is reachable by every seat (`executable_hcom-seat:1726`); the srt README calls it "a potential data exfiltration vector".
- Linux is unmeasured (`scripts/orchestrator/README.md:190`); the open Ubuntu issues of section 2.2 would surface as the canary's exit 2, which stops the seat rather than running it uncontained.
- Version drift: mise installs `latest` of a package whose authors say the configuration format "may evolve", while `hcom-seat` encodes 0.0.81 behaviours (section 4.1). A release that changed the `*:*` rendering, the own-write paths or the deny-under-allow rule would change the boundary silently; a release that renamed a key would make that key an ignored unknown key (issue #434) rather than an error. **Inferred** recommendation: pin the version in `home/dot_mise/config.toml` and bump it as a reviewed change, as the lint tools are pinned (U97).

### 5.3 What srt offers that the seats do not use yet (options, not findings)

- `deniedDomains` with `deniedDomainReasons` (a model-facing reason for a refused host) and `deniedResolvedAddresses` for the private ranges, which the resolved-address check leaves alone by default.
- `credentials.files` with `mode: "mask"` for the gh token under `tlsTerminate`, which would keep the real token out of the seat while `gh` still authenticates to `api.github.com`. Linux only for files (macOS degrades to deny), and the manifest's reason for not masking in Claude Code (an inject host that echoes the body returns the real value) applies here too.
- `strictAllowlist` changes nothing for the CLI (no ask callback), so it is not needed in the seat settings.
- `--control-fd` could re-shape the network lists of a running seat without a relaunch; the filesystem rules would still need a relaunch.
- `allowGitConfig` stays at its default `false`, which already denies `.git/config` at the project root; the seat adds the worktree and common-directory git state explicitly, which is the stronger form.
