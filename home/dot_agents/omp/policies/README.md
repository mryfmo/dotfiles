# omp seat tool policies

One omp settings overlay per seat role. chezmoi applies them to `~/.agents/omp/policies/<role>.yml`, and the seat launcher passes the role's file as `--config ~/.agents/omp/policies/<role>.yml` when it starts omp. On the pi-claude-bridge route the child Claude Code runs with `tools: []`, so these overlays are the only tool gate for a Claude-routed seat.

The common denies are the same list in every file: `sudo`, `rm -rf`, `curl` or `wget` piped (with any spacing) into a shell whose name ends in `sh`, `gh release`, `npm publish`, `uv publish`, `terraform apply`, `kubectl apply`, `gh pr merge`/`edit`/`close`/`review`/`update-branch`, `gh issue`, and `gh api` with a `POST`/`PATCH`/`PUT`/`DELETE` method or a request body (`-f`, `-F`, `--field`, `--raw-field`, `--input`). `tests/unit/test_omp_seat_policy.py` fails when the three copies drift.

## GitHub-write levers (U28)

Every GitHub write the loop needs beyond the merge, the worker's push and `gh pr create`/`gh pr comment`, runs through one lever: a script in `scripts/orchestrator/` that checks its arguments before any `gh` call, installed read-only as `~/.local/bin/common/<lever>` with its `claude.levers.sha256` pin and self-check (U31), and allowed by name in the role that owns the write. The orchestrator replies to and resolves review threads (`pr-thread-reply.sh`, `pr-thread-resolve.sh`), updates a branch (`pr-update-branch.sh`), closes the rows a clean-up table marks `close:` (`pr-close.sh --from-table`), checks the threads before a merge (`pr-threads-check.sh`, read-only) and syncs its records (`records-sync.sh`); the worker edits the body of its own branch's pull request (`pr-body-edit.sh --body-file`). Each allow row names only the installed path, so the lever runs alone as one simple command (an `allow` never matches a compound line), and the deny row right after it, `*<lever> *`, refuses every other spelling with arguments: the checkout path, an expanded HOME, an interpreter prefix, `pr-close.sh` without `--from-table`, and the lever chained to anything. `records-sync.sh` acts with no arguments too, so the orchestrator also allows its exact bare installed form, followed by a `*records-sync.sh` deny, and the worker denies both its argument and its bare forms (U28b F3). Every raw form stays denied (the common denies, `gh api` writes included). `scripts/validate-agent-assets.py` (`validate_omp_policies`) refuses an allow in either writing seat that is not the merge form (orchestrator only) or `~/.local/bin/common/<lever> [--<flag>] *` for a pinned lever with a byte-identical installed copy; `audit.yml` keeps its read-only allows. What each lever checks is in `scripts/orchestrator/README.md`, "Seat levers for GitHub writes".

The Claude Code coordinator keeps its `ask` rules for every GitHub write (`claude.permissions.ask` in `home/dot_agents/agent-config.yaml`) and gets none of these levers: the orchestrator seat owns the loop (D-024-143), and a Claude seat that widened its own GitHub rights would need the permgate change that the Routing invariant reserves to the operator.

## Why `task` and `eval` are denied

Every seat denies `task`, each for its own reason:

- audit: omp subagents run headless in `yolo`. omp `docs/approval-mode.md`, "Subagents": "Subagents run headless with `tools.approvalMode: yolo` so ordinary tier-based prompts do not stall them. The parent `task` approval is the authorization boundary." `docs/tools/task.md`: "`tools.approvalMode` is forced to `yolo` because headless subagents have no UI to confirm prompts against". The `always-ask` audit seat stops unlisted write and exec tools only because a headless prompt fails, so a `task` child would run those tools; the deny is a security boundary.
- orchestrator: an in-process subagent would be a delegation channel outside the hcom bus and the ledger.
- worker: the deny came in after the claude-bridge Task defect (`docs/pi-claude-bridge.md`, "Subagents"). Bridge patch 05 fixed the root cause in print mode. Lifting the deny needs a seat measurement first (hcom delivery into the seat after a Task and after a park); if lifted, the overlay sets `task.disabledAgents` so only read-only agents remain, `task.maxRecursionDepth: 1`, a small `task.maxConcurrency`, and keeps `eval: deny`.

`eval` stays denied in every file: `bash.patterns` do not reach a shell started through `eval`, and `eval` also exposes `agent()` and `workpool()`, a second way to spawn subagents.

## Mechanism (omp 18.11.3, `@oh-my-pi/pi-coding-agent`)

- `tools.approvalMode` (`src/tools/settings.ts:311-318`) is `always-ask`, `write` or `yolo`. A mode auto-approves up to a tier (`src/tools/approval.ts:124-128`); `bash`, `eval` and `task` declare `exec`, so `write` does not cover them, and a headless run stops such a call with `requires approval but no interactive UI available` instead of allowing it. That is why the two writing seats run in `yolo` with explicit denies, and the audit seat in `always-ask` with explicit allows.
- `tools.approval.<tool>: allow | deny | prompt` (`src/tools/settings.ts:295-305`) is honoured in every mode; a user `deny` is absolute (`src/tools/approval.ts:249-257`).
- `bash.patterns` (`src/exec/settings.ts:134-145`) is an ordered list of `{match, approval}` rules over the `bash` tool's command. `*` is the only wildcard; whitespace runs collapse to one space before matching and nothing else is normalised (`src/tools/bash.ts:239-249`). The first matching rule wins. A `deny` matches the whole command or any one segment split on `;`, `&&`, `||`, `|`, `&`, parentheses and newlines; an `allow` must match the whole command and never a line with shell control characters (`src/tools/bash.ts:281-314`). Quotes alone do not break an `allow`: `hasBashApprovalShellControl` (`src/tools/bash.ts:94-136`, called at `:303`) skips a `;`, `|`, `&`, `<`, `>` or parenthesis inside single or double quotes unless a `-c`, `-e`, `--command` or `--eval` option could reinterpret it (`:92`, `:135`), but a `$` or a backtick inside double quotes refuses the allow outright (`:121`), so the audit seat's reply pastes the sha and never carries `$(git rev-parse HEAD)`. A matched deny is absolute even in `yolo`; a matched allow runs at the `write` tier (`src/tools/bash.ts:533-540, 578`).
- `--config <file>` loads a strict per-process overlay: a missing file (`Config overlay not found`), invalid YAML or a top-level list (`Config overlay must be a YAML mapping`) is a hard error at start, so a seat never starts without its policy (`docs/settings.md`, "One-shot overlays").

## Text that policies see

A rule reads the whole command line the model typed, quoted text included, so two measured false negatives of the first orchestrator-seat run (O1, 2026-10-24) came from command text, not from a wrong rule. The audit seat ran `git rev-parse HEAD && git status --porcelain`; an `allow` never matches a line with shell control characters, so the catch-all denied it (`Blocked by bash pattern: *`) and the seat answered `verdict=blocked note=policy-denied-head-and-clean-tree-verification` (bus row 467). The orchestrator's `hcom-dispatch … "TASK … gh pr comment …"` (sent then with the retired `AGMSG-` prefix on the kind, which changes nothing here) met its own `*gh pr comment*` deny, because a `deny` matches any segment and the TASK prose named the command (pane read 2026-10-24T02:33Z). The worker seat met the same effect when its blocked-PONG note quoted the denied command it reported; the reworded note went through as bus row 810. The fix is in the seats' skills, not in the rules: the audit seat runs one command per bash call (`hcom-audit` SKILL, "Audit" step 1), a bus line carries ids, paths and a one-sentence note without command names while longer instructions go in a brief file (`hcom-orchestration` SKILL, step 2), and the worker keeps denied command names out of quoted arguments (`hcom-worker` SKILL, "Blocked").

## Verify

```bash
uv run python -m unittest tests.unit.test_omp_seat_policy -v
```

Dry-run a file against the installed omp without touching the real `~/.omp`:

```bash
HOME="$TMPDIR/omp-home" omp models ls --config home/dot_agents/omp/policies/worker.yml --json > /dev/null
```

A read-back of the parsed values uses the same scratch HOME: copy the file to `$TMPDIR/omp-home/.omp/agent/config.yml`, then `omp config get bash.patterns --json`.
