    pi-claude-bridge as an omp extension¶

    pi-claude-bridge is a Pi extension that registers the claude-bridge/<model> provider and answers each turn through the Claude Agent SDK, which runs the bundled Claude Code binary on the host's claude.ai login. This repository installs a pinned, patched copy as an omp extension directory (plan 025 decisions 30, 37, 38 and D-024-129). Pi executes the tools; the child Claude Code only produces the model turns.

    Route¶

    omp -e ~/.local/lib/omp-extensions/pi-claude-bridge --model claude-bridge/claude-haiku-4-5
  -> src/index.ts registers provider claude-bridge (omp rewrites @earendil-works/* imports to its legacy pi shims)
  -> @anthropic-ai/claude-agent-sdk query() spawns node_modules/@anthropic-ai/claude-agent-sdk-<platform>/cli
  -> the child authenticates with the host's claude.ai login (Keychain), tools: [] and bypassPermissions

    The model id after claude-bridge/ is the Anthropic catalog id. The seat profiles (model_profiles in home/dot_agents/agent-config.yaml) choose the model; this document covers only the asset.

    Install¶

    make update runs scripts/update-agent-assets.sh, whose update_pi_claude_bridge step:

    1. downloads pi-claude-bridge-<pin>.tgz from registry.npmjs.org and checks its sha256 against assets.pi-claude-bridge.sha256 in home/dot_agents/agent-config.yaml;
    2. extracts it into a staging directory beside the target and applies every home/dot_agents/assets/pi-claude-bridge/patches/*.patch in name order with patch -p1 -F0 (no fuzz: GNU patch would otherwise apply a patch whose context drifted and exit 0);
    3. copies the committed bun.lock in and runs bun install --production --omit=peer --frozen-lockfile, so the dependency set is the reviewed one (peers are omitted because omp's legacy pi compat layer provides @earendil-works/pi-* and typebox itself);
    4. runs gap-check.ts, which imports omp's three legacy shims and refuses the install when the bridge imports a value name they do not export (the guard for omp upgrades);
    5. writes RECEIPT (tarball, patch and lockfile sha256 lines, then the installed @anthropic-ai/claude-agent-sdk* versions) and renames the staging directory to ~/.local/lib/omp-extensions/pi-claude-bridge.

    A run whose RECEIPT head already equals the pinned inputs changes nothing. The step is skipped with a message when bun or omp is absent. Run it alone with scripts/update-agent-assets.sh update_pi_claude_bridge.

    Patches¶

    Each patch is a plain diff -ruN a b between consecutive stages of the upstream package/ tree, so a reviewer can re-derive it.

    Patch Why
    01-omp-shim-exports.patch omp's legacy pi-coding-agent shim does not export formatSkillsForPrompt, so src/skills.ts carries Pi's implementation (MIT, same output). The shim does export keyHint and buildSessionContext (gap-check.ts lists both as FOUND), so upstream's calls to them stay.
    02-content-text.patch The pi-ai shim does not export contentText; src/transcript.ts carries pi-ai 1.4.0's eight-line implementation (MIT). Without it omp logs Failed to load extension ... Export named 'contentText' not found.
    03-no-bash-timeout-injection.patch Decision 38: the bridge added timeout: 120 to every bash tool call it handed to Pi (mapToolArgs in src/index.ts; seen on the wire as {"command":...,"timeout":120}). omp's bash tool keeps its own timeout handling.
    04-setting-sources-none.patch The provider query() passes settingSources: [], so the child Claude Code loads no user, project or local settings.json: the host's hooks, plugins and permission rules do not run inside bridge turns. The claude.ai login is not a setting and still applies. Measured 2026-10-23: with the default, the child's thinking cited the host's superpowers system reminders.
    05-register-on-reactivation.patch omp builds a Task subagent by calling the extension factory again on the same module instance (one moduleInstanceId in the bridge debug log), clears the bridge's provider registrations from the model registry the parent shares, and keeps only the registrations queued during that call. Upstream deferred a second activation to a session_start check through ctx.modelRegistry.getProvider(), which omp's registry lacks (omp logs Extension error ... getProvider is not a function), so claude-bridge vanished for both sessions. The bridge now registers at load when the active stream function is this instance's own; re-registering the same function replaces nothing. A second module instance (another copy of the bridge) keeps upstream's deferral.
    06-global-config-only-bounded-diag.patch Upstream loadConfig merged <cwd>/.omp/claude-bridge.json over the agent dir's claude-bridge.json, so a checked-out repository could name the Claude Code executable the bridge spawns (provider.pathToClaudeCodeExecutable), turn on AskClaude with allowFullMode (a Claude Code child with Bash and Write under bypassPermissions), or drop --strict-mcp-config (provider.strictMcpConfig: false). The bridge now reads only the agent dir's file (~/.omp/agent/ or the seat profile's agent/), which the operator owns; a project file is never read. The same patch bounds claude-bridge-diag.log: once it holds 512 KiB it moves to claude-bridge-diag.log.1, replacing the older one (upstream appended without a limit; a macOS worker seat's log reached 1 MB). Measured 2026-10-25 under a scratch HOME with a hostile project file: patches 01-05 spawned the project's executable without --strict-mcp-config and loaded askClaude.allowFullMode: true; patches 01-06 spawned the agent dir's executable with --strict-mcp-config and an empty askClaude. 2000 diag dumps left 717 KB across the two files.

    Upstream kept the default settingSources so that Bedrock and Vertex users keep env and apiKeyHelper from settings.json (comment above CLAUDE_MD_EXCLUDES in src/index.ts). This route uses the claude.ai login, so nothing it needs lives in those files. The alternative, a PI_CODING_AGENT_DIR early exit in every hook, would touch every hook script and still load the host's plugins; one option on the query is smaller.

    Launcher flag¶

    The seat launcher passes, verbatim:

    -e ~/.local/lib/omp-extensions/pi-claude-bridge

    omp resolves the directory manifest-first (pi.extensions in package.json names ./src/index.ts) and resolves dependencies upward from the entry's real path, which is why the install directory carries its own node_modules. --no-extensions beside -e is optional and keeps other extensions out.

    Plain launch¶

    A plain omp (default profile, no -e) loads the bridge through the top-level extensions key of ~/.omp/agent/config.yml (omp 18.11.3 src/extensibility/settings.ts:10, joined with the -e paths in src/sdk.ts:1076). The manifest lists the directory under omp.extensions, scripts/generate-agent-configs.py renders it into home/.chezmoitemplates/omp-config-managed.yml, and home/dot_omp/private_agent/modify_private_config.yml writes it with ~ expanded. Without it, findInitialModel (src/config/model-resolver.ts:2391-2407) does not find the modelRoles.default claude-bridge/claude-fable-5-1 and silently starts on another authenticated provider (anthropic/claude-opus-5-5 on the macOS host) or exits with No default model selected. (the Ubuntu host). scripts/validate-agent-assets.py refuses an interactive_profile whose omp provider comes from an extension that omp.extensions does not list.

    • Measured 2026-10-25 on macOS: with an overlay holding only that extensions entry, omp --no-session --mode json -p "Reply with the single word PONG." answers PONG on provider claude-bridge, model claude-fable-5-1, stopReason stop.
    • The same directory passed again with -e loads once: discoverExtensionPaths keys each entry file on its resolved path (src/extensibility/extensions/loader.ts:572-659); measured, the same answer and no new warning.
    • Seats are unaffected: --profile <role> reads ~/.omp/profiles/<role>/agent/config.yml, never this file (pi-utils src/dirs.ts:119-121). Measured under a scratch HOME whose config.yml lists the bridge, the default profile reaches it (Not logged in) and --profile probe reports Model "claude-bridge/claude-fable-5-1" not found. The seat launcher keeps passing -e.

    Operator login¶

    The child Claude Code uses the host's claude.ai login: the Keychain on macOS, ~/.claude/.credentials.json (mode 0600) on Linux (Claude Code authentication doc, "Credential management"). Before the first bridge turn, the operator runs claude once and completes /login in their own terminal; no script does this. Without the login a bridge turn ends with Not logged in · Please run /login.

    A Linux seat host reached over SSH (herdr --remote) has no browser of its own. There, claude auth login sends its URL to $BROWSER, which seat-login-preflight <role> points at regime-open-url, so the laptop browser opens it. The callback port is random (50903, 50915 and 50920 on three runs, Claude Code 2.1.309), so no SSH forward can carry it. The URL asks for the code flow (code=true), so the page shows a code to paste at the terminal's prompt. The fallback is claude setup-token on the laptop: the operator stores the printed one-year token in ~/.config/claude-code/oauth-token on the seat host, mode 0600, by hand. ~/.zshenv and ~/.profile then export it as CLAUDE_CODE_OAUTH_TOKEN when the file is non-empty. The Agent SDK reads that variable, except in bare mode, and the bridge never passes --bare: its only extra CLI arguments are model, strict-mcp-config and thinking-display (src/index.ts, extraArgs). The steps are in docs/remote-host-logins.md.

    Load check¶

    omp models never evaluates extension modules, so the only instrument is a session:

    scripts/update-agent-assets.sh check_pi_claude_bridge

    It runs omp --no-extensions -e <install dir> --no-session --model claude-bridge/claude-haiku-4-5 --max-time 60 -p "Reply with the single word PONG.", fails when stderr or the omp log files written by that run contain Failed to load extension, and passes when the output reaches the model (PONG with a login, Not logged in without). It runs under the real HOME and spends one short model turn on a logged-in host; make doctor calls it. On Linux a scratch HOME keeps the session out of the real ~/.omp. Do not do that on macOS: the child Claude Code asks the login keychain for its credentials, and with no keychain search list under the scratch HOME macOS shows a "keychain unknown cannot be found" dialog for every run.

    Subagents¶

    An omp Task subagent on the claude-bridge route broke the seat that spawned it before 05-register-on-reactivation.patch. Measured on 2026-10-24 at about 06:03Z: the orchestrator seat spawned a Task subagent (an inventory scout), the subagent failed with No API key for provider: claude-bridge, and from then on every hcom delivery into that seat failed with Extension sendUserMessage failed, so the seat was dead to the loop; the two worker seats on the same route and the host login were unaffected. So every seat policy denies the task tool (tools.approval.task: deny in home/dot_agents/omp/policies/{orchestrator,worker,audit}.yml, U34 in U36), and the seats do their reading with their own tools. omp refuses the call before the tool runs: tests/unit/test_omp_seat_policy.py OmpTaskDenyLiveTest drives the installed omp against a local fake model that asks for a task call and gets back Tool "task" is blocked by user policy. To allow: remove "tools.approval.task: deny" from config. for each role.

    Measured on 2026-10-24 at about 22:10Z (omp 18.11.3, macOS) with omp --no-session -e <tree> --model claude-bridge/claude-fable-5-1 --mode json --max-time 240 -p "Use the task tool exactly once to spawn one subagent whose whole job is to reply with the single word PONG, then reply with what it returned.":

    • patches 01-04: the subagent resolved claude-bridge/claude-fable-5-1 and failed after 44 ms with No API key found for claude-bridge.; the parent's next turn ended "stopReason":"error", "errorMessage":"No API key for provider: claude-bridge", exit 1;
    • patches 01-05: the subagent answered PONG on claude-bridge/claude-fable-5-1, the parent's final turn ended "stopReason":"stop", exit 0;
    • patches 01-05 with task.agentIdleTtlMs: 3000 in a --config overlay and a prompt that spawns one subagent, runs sleep 15 and spawns a second: the first subagent was parked (disposed) mid-run, which runs the bridge's session_shutdown handler (clearing ACTIVE_STREAM_SIMPLE_KEY in the debug log); the second subagent registered again, both answered, and the run ended stop, exit 0;
    • patches 01-05, one plain Reply with the single word PONG. turn: PONG, stop; the same directory given twice (-e <tree> -e <tree>/, or -e <tree> plus a --config overlay listing it under extensions:) runs the bridge's factory once.

    These are print-mode runs. The seat failure ran through hcom delivery into an interactive seat, which these runs do not cover, so the seat policies keep the deny until a seat measurement shows a Task subagent and the next hcom delivery both succeed.

    The plain launch (above) loads the bridge through extensions instead of -e and hit the same failure before patch 05: measured 2026-10-25 on macOS with patches 01-04, a plain print-mode session asked to spawn one Task subagent saw the subagent fail in 74 ms with No API key found for claude-bridge. and its own next turn end with No API key for provider: claude-bridge (exit 1). A plain session has no task deny, so the plain-launch extensions key depends on patch 05 being installed (make update installs both).

    Fallbacks¶

    • anthropic/<model> with ANTHROPIC_API_KEY is omp's built-in provider and needs no extension; use it when the bridge cannot load or the login is unavailable.
    • An exported ANTHROPIC_API_KEY, ANTHROPIC_AUTH_TOKEN or ANTHROPIC_BASE_URL redirects the child Claude Code to that gateway (upstream README), so the bridge seat must not inherit them unless that is intended.

    Upgrading¶

    Change pin and sha256 in assets.pi-claude-bridge, run uv run --no-project --with pyyaml scripts/generate-agent-configs.py to render the constants into scripts/update-agent-assets.sh, regenerate bun.lock from the new tarball (bun install --omit=peer --lockfile-only inside its package/), re-check that every patch still applies, and run the load check. An omp upgrade needs no change here unless gap-check.ts reports a MISSING row; then the missing name gets a patch like 01 or 02.
