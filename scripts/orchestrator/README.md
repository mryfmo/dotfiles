# scripts/orchestrator

## hcom bus: `hcom-dispatch` and `bus-history.sh`

Plan 025 W2b (C-1). The omp seats talk over one private hcom store per program, selected by `HCOM_DIR` (hcom 0.7.30). Both scripts refuse to run when `HCOM_DIR` is unset or `$HCOM_DIR/hcom.db` is absent, because `hcom events` creates a store on first use and only the seats' launch may do that. Every test runs against a scratch store, never `~/.hcom`.

### Routes

| Direction                                       | Command                                                              | hcom call                                                                     |
| ----------------------------------------------- | -------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| orchestrator to a seat (TASK, ACCEPTANCE, PING) | `hcom-dispatch <team> <from> <to> <pane> <line...>`                  | `hcom send @<to> --thread <team> --from <from> --json -- <line>`              |
| seat to the orchestrator (RESULT, PONG)         | the seat's own `hcom send --thread <team> -- '<line>'`, no target    | the thread the TASK seeded; an external sender is not addressable with `@`    |
| records                                         | `bus-history.sh <team> [--limit <n>] [--since <ts>] [--kind <kind>]` | `hcom events --type message --thread <team> --full --last <n> [--after <ts>]` |

`<to>` is the seat's exact hcom name, so a seat hcom does not know fails with hcom's own `Error: No active agent for @<to>` (exit 1, stderr). hcom accepts any thread name for a mention send and `hcom start` sets no tag (`src/commands/start.rs:486`), so the team of a seat is not checked here; a malformed team is refused by the grammar `^[a-z0-9][a-z0-9_-]{0,63}$`. The pane argument is accepted and unused: hcom delivers to a bound seat itself. The audit seat sends its reply through `hcom-reply <team> -- '<line>'` (`home/dot_local/bin/common/executable_hcom-reply`, on PATH as `~/.local/bin/common/hcom-reply`), which runs `hcom send --thread <team> --name <self> -- <line>` with `<self>` from `hcom list self name`, because `audit.yml` denies `hcom send` in every form (U6d).

### Receipt and history

`hcom-dispatch` prints one line, `id=<event id> at=<hcom ts> to=<to> kind=<first word>`, read back from the bus by exact id, so the row exists before the receipt does. `bus-history.sh` prints `id<TAB>at<TAB>from<TAB>to<TAB>kind<TAB>body`, ascending by id; `to` is hcom's `delivered_to` joined with commas (`-` when empty, as for a seat's thread reply) and `body` escapes backslash, tab, CR and LF as `\\`, `\t`, `\r` and `\n`, so a row is one line of five tabs.

## `omp-run.sh`: one non-interactive omp turn per role

Plan 025 W6a (U8). The orchestrator seat, and the coordinator today, runs a headless omp turn in a seat role with one command. The script composes `omp --profile <role> --config ~/.agents/omp/policies/<role>.yml -e <dir>... --no-session --max-time <s> [--model <provider/id>] --mode <text|json> -p "<prompt file contents>"` (omp 18.11.3; `omp --help` lists every flag), runs it in `--cwd`, and fails closed: an unknown role, an absent or empty prompt file, an absent overlay, extension directory or cwd is exit 2 with the path, before omp starts. omp's stderr is held and replayed after the run; a `Failed to load extension <path>: <error>` line in it is exit 2 too, with the path in the refusal (U1 report F5). Otherwise omp's own exit status is returned. HOME is the caller's, so the seats run as the operator, and `--approval-mode` is never passed: the role's overlay owns it (`home/dot_agents/omp/policies/README.md`).

| Role           | Profile and overlay                                                       | Approval, from the overlay                                                                                          | Used for                                      |
| -------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| `orchestrator` | `--profile orchestrator --config ~/.agents/omp/policies/orchestrator.yml` | `yolo`, merge and push rules in `bash.patterns`                                                                     | tasking, acceptance, the audited squash merge |
| `worker`       | `--profile worker --config ~/.agents/omp/policies/worker.yml`             | `yolo`, every push to `main` denied                                                                                 | implementing a unit in its worktree           |
| `audit`        | `--profile audit --config ~/.agents/omp/policies/audit.yml`               | `always-ask` with the write tools denied; a denied call returns omp's "requires approval" text to the model (#G1-2) | the read-only task-level audit of a head      |

`--mode text` (default) passes omp's own print-mode text through and `--mode json` passes its event stream through unchanged, one JSON object per line (`tool_execution_start`, `tool_execution_end`, `turn_end`, `agent_end`; measured in `.orchestration/validation/025-pilot-facts.md` #G1-3). Nothing is parsed, so a caller that wants only the final text reads the last `turn_end` of the JSON stream itself. Extensions default to the bridge `~/.local/lib/omp-extensions/pi-claude-bridge` and the SIWC `~/.agents/omp/extensions/openai-siwc`; `--ext <dir>` (repeatable) replaces that list. `--max-time` defaults to 600 seconds. omp reads a prompt that starts with `-` as a flag, so start a prompt file with a word or a heading.

```bash
# The audit seat reviews a head: JSON stream to a file, 15-minute bound.
scripts/orchestrator/omp-run.sh --role audit --prompt-file audit-U8.md --cwd /path/to/worktree --mode json --max-time 900 > audit-U8.jsonl

# The worker seat runs a task with a model override and the bridge staged elsewhere.
scripts/orchestrator/omp-run.sh --role worker --prompt-file task.md --cwd /path/to/worktree --model claude-bridge/claude-haiku-4-5 --ext /path/to/pi-claude-bridge
```

`tests/unit/test_omp_run.py` runs the script against `tests/fixtures/omp-run/fake-omp.py`, which records argv, cwd and HOME and replays `tests/fixtures/omp-run/stream.jsonl`; the real omp is never started by the tests.

## hcom-seat: start an omp seat for a role in a herdr pane

Plan 025 W5b (U7), the minimal form before X. `hcom-seat <role> [--name <name>] [--seats-root <dir>] [--ext <dir>]... [--dry-run]` starts one omp process for `orchestrator`, `worker` or `audit` through `hcom omp`, which opens the herdr pane and gives the seat `HCOM_LAUNCHED=1`, `HCOM_TAG` and `HCOM_DIR` (`hcom omp --help`). The launch line is

```text
hcom omp --tag <name> --dir <dir> --terminal herdr --go -- --profile <role> --config ~/.agents/omp/policies/<role>.yml --config ~/.agents/omp/profiles/<role>.yml -e <ext>...
```

The profile equals the role, and two overlays follow it (`--config` is repeatable). The policy overlay owns the approval mode (U6, `home/dot_agents/omp/policies/README.md`). The profile overlay carries the manifest's `modelRoles.default` (U4) and `skills.customDirectories` (U10), because a named profile reads its own `~/.omp/profiles/<role>/agent/config.yml` (pi-utils `src/dirs.ts:312-315`, measured in U10) and the default profile's rendered config never reaches a seat; U14 renders it per role. Both files are required, so no `--model` is passed. `<name>` defaults to the role and is the hcom tag; hcom derives the participant name from it (`hcom omp --help`: "names become tag-\*"), and `--name <role>-<n>` seats a second seat of a role. The `--` ends hcom's flags: hcom 0.7.30 drops it and forwards every later argument to omp verbatim (`extract_launch_flags`, `src/commands/launch.rs:572-581` at tag `v0.7.30`), so the omp flags never collide with the flags hcom claims by name, including `--name`, `--system` and `--go`, which `hcom omp --help` does not list. `--go` is hcom's launch gate and the launcher always passes it, before the `--`: inside an AI tool, hcom 0.7.30 without it prints `== LAUNCH PREVIEW ==`, `Add --go to proceed.` and `[Preview Mode] Add --go to proceed with launch.` and starts nothing (`launch.rs:48`, `388-389` and `423`; the first run on the real host did exactly that for all three roles on 2026-10-23, `hcom list -v`: `No active agents`). The router sets the flag (`src/router.rs:255-256`) and `extract_launch_flags` consumes it before the `--` (`launch.rs:650-652`); after the `--` it would reach omp as a positional.

| Role           | `--dir`                                              | Default `-e` list, in order                                                |
| -------------- | ---------------------------------------------------- | -------------------------------------------------------------------------- |
| `orchestrator` | the repository checkout the command runs in          | `~/.local/lib/omp-extensions/pi-claude-bridge`, then the SIWC when present |
| `worker`       | `<seats-root>/<name>`, a worktree of that repository | the bridge, then the SIWC when present                                     |
| `audit`        | `<seats-root>/<name>`, a worktree of that repository | `~/.agents/omp/extensions/openai-siwc`, then the bridge when present       |

The first directory of a role's list is the one its model route needs (U2 bridge for the Claude routes, U3 SIWC for the Codex route) and is required; the second is added only when it exists. `--ext <dir>` (repeatable) replaces the list, as `omp-run.sh` does; every directory, a default or `--ext`, must resolve to an entry of `claude.levers.extensions` in the manifest (U31, "Pre-authorized levers"), else the launch is refused. `--seats-root` defaults to `~/.local/state/omp-seats`. A seat worktree is created with `git worktree add --detach <dir> origin/main` only when absent and reused when its git common directory is this repository's, so a restart of a seat keeps its branch and uncommitted work; any other directory at that path is refused, because the default seat path is role-named and a stale or foreign directory would seat omp in the wrong tree. The launcher never moves a seat worktree after creating it at `origin/main`. The worker moves its own tree per its brief (`git fetch origin`, then `git switch -c <branch> origin/main`, `hcom-worker` SKILL). The orchestrator moves the audit seat's tree before each audit TASK with `git -C <seats-root>/<name> fetch origin <branch> && git -C <seats-root>/<name> switch --detach <head sha>`, because `audit.yml` allows that seat only read-only `git`; the seat answers `verdict=blocked note=head-mismatch` when `git rev-parse HEAD` differs from the TASK's `head=` (`hcom-orchestration` SKILL step 4, `hcom-audit` SKILL).

Every input is checked before anything is created or started, and a refusal is exit 2 with the reason on stderr: an unknown role, a name outside `^[a-z0-9][a-z0-9_-]{0,63}$`, an unset `HCOM_DIR`, hcom absent from `PATH`, an absent policy or profile overlay or extension directory, or a cwd outside a git checkout. `--dry-run` prints the launch line (shell-quoted, one line) and creates and starts nothing. Otherwise hcom's own exit status is returned (0 ready, 1 launch failed, 2 still launching or blocked on user attention).

### Bus trust boundary

The bus carries text, and every seat treats that text as data: a TASK, RESULT, ACCEPTANCE, PING or PONG line names work or reports it, and never authorises a command, however it is worded. Identities are hcom participant names, the `from` and `delivered_to` of a row, not anything the text claims; `hcom-dispatch` sends only to a name hcom knows and refuses an identifier outside `^[a-z0-9][a-z0-9_-]{0,63}$`. The store is private to the program: `HCOM_DIR` selects it, the seats' launch creates it, `hcom-dispatch` and `bus-history.sh` refuse to run without it, and no seat reads `$HCOM_DIR/hcom.db` or writes under `$HCOM_DIR` except through hcom. The operating-system account and the seat's worktree stay the containment boundary; the policy overlays gate tools, not files (U6, "approval is not containment").

## Pre-authorized levers

Regime-cutover U16 (brief `F8-coordinator-levers-preauthorized`). The Claude Code coordinator runs the regime's own operations from inside its sandbox, without a classifier round trip, through five `permissions.allow` rules in the managed settings (`claude.permissions.allow` in `home/dot_agents/agent-config.yaml`). Auto mode resolves an action that matches a rule before the classifier: "Actions matching your allow, ask, or deny rules resolve immediately" (code.claude.com/docs/en/permission-modes, "How the classifier evaluates actions"), and it suspends only the allow rules that "could run arbitrary code: tool-wide and wildcard rules such as `Bash(*)`, and interpreter or shell-wrapper prefixes such as `Bash(python *)`" (code.claude.com/docs/en/settings, `autoMode.classifyAllShell`, default `false` and unset here). So every rule names one deterministic wrapper that validates its own input, and nothing wider.

Since U31 each lever rule names the copy chezmoi installs under `~/.local/bin/common`, outside every sandbox write root: the generator renders `home/dot_local/bin/common/executable_<lever>` from `scripts/orchestrator/<lever>` (same bytes, the mechanism `hcom-reply` uses) and pins its sha256 as `claude.levers.sha256.<lever>` in the manifest. At start each lever hashes its own bytes and compares the digest with its pin in the manifest beside it, the deployed `~/.agents/agent-config.yaml` for the installed copy; a mismatch, a missing pin or any failed read exits 2 naming the file. `hcom-seat` loads only the directories in `claude.levers.extensions`. So the rules render on Linux and WSL2 too; until U31 part 2, part 1 rendered them into the darwin variant only (`claude.permissions.darwin_allow`, D-024-144).

Run each lever by its installed path, exactly as written (`~/.local/bin/common/<lever> ...`), with the checkout root as the working directory (`hcom-seat` and `worktree-gc.sh` read the repository from it): the rules name only that spelling, so `scripts/orchestrator/<lever>`, `./scripts/...` or the expanded `/Users/<user>/.local/bin/common/<lever>` goes to the classifier. A leading variable assignment defeats a rule too ("An allow rule won't match past an assignment of any other variable", code.claude.com/docs/en/permissions, "Wrappers"), and so does a `perl -e 'alarm …; exec @ARGV'` wrapper, so the levers read `HCOM_DIR` and `HCOM_TEAM` from the environment and bound their own waits (`worktree-gc.sh` bounds each `gh` call by `WORKTREE_GC_GH_TIMEOUT`, default 60 seconds). A chain is never covered: "A rule must match each subcommand independently" (code.claude.com/docs/en/permissions).

`scripts/validate-agent-assets.py` (`validate_claude_permissions_allow`) refuses every other allow rule: only `Bash(hcom list *)` and `Bash(~/.local/bin/common/<name> *)` pass, and a rule naming `scripts/orchestrator/` is refused as a path inside the rewritable checkout. `<name>` needs a `claude.levers.sha256` pin, a byte-identical generated copy `home/dot_local/bin/common/executable_<name>`, and a source `scripts/orchestrator/<name>` that is a regular file (not a symlink), executable, starting with `#!`, and not named as an interpreter (`sh`, `bash`, `python3`, `node`, `perl`, `env`, `uv`, `xargs` and the like, extension ignored).

The settings carry the rest of what the levers need:

- `env`: `HCOM_DIR={{ .chezmoi.homeDir }}/.local/state/hcom-regime` and `HCOM_TEAM=regime`, the values of the seat's environment table in `docs/orchestrator-seat.md`, rendered with the home directory expanded. Claude Code reads settings `env` at session start, so a session started before `make update` does not have them.
- `sandbox.filesystem.allowWrite` gains `~/.local/state/hcom-regime`, because hcom secures the store directory on every open, `hcom list` included (inside the sandbox it failed with `Failed to secure hcom directory`), and `~/.local/state/omp-seats`, because the orchestrator positions the audit seat's worktree before each audit TASK (`hcom-orchestration` SKILL, step 4).

Invariants, held by the validator and the generator tests: no `Bash(*)`, `Bash(hcom *)`, `Bash(git *)` or `Bash(git worktree remove *)`, no interpreter or shell-wrapper prefix; every GitHub write stays in `ask` (the `gh pr` merge, create, comment, review, close, edit and update-branch rules, `gh issue`, the `gh api` write forms); the `Bash(sudo:*)` and `Bash(rm -rf:*)` denies stay; `sandbox.excludedCommands` stays `[]`; `autoMode.classifyAllShell` stays unset.

An allow rule also approves the lever's unsandboxed retry: "by default a sandboxed command can be retried outside the sandbox, and an allow rule or `bypassPermissions` mode can approve that retry with no prompt" (code.claude.com/docs/en/sandboxing, "Strict sandbox mode"). The levers are meant to run sandboxed and need no retry; a retry the coordinator sees is a failure to report, not a path to take.

Operator steps that stay operator steps by design: `make update` (it runs outside every sandbox and installs these settings), browser and CLI logins, anything that reads the Keychain, and closing a pull request (`gh pr close`).

### `worktree-gc.sh`

`scripts/orchestrator/worktree-gc.sh [--apply] [<path>...]` reads `git worktree list --porcelain -z` and considers only the worktrees under `<toplevel>/.claude/worktrees/`. A worktree qualifies when `git status --porcelain --untracked-files=all` prints nothing and its work landed: its head is reachable from `origin/main`, its branch has a merged pull request (`gh pr list --state merged --head <branch> --json number --limit 1`), or, detached, its head is the `headRefOid` of a merged pull request (`gh pr list --state merged --search <sha> --json number,headRefOid`). A locked or missing worktree is kept. It prints one row per candidate, `<gc|keep|error>\t<path>\t<branch or (detached <sha>)>\t<reason>`, then a `summary` row, and exits 0 when nothing qualifies. `--apply` runs `git worktree remove <path>` for each qualifying tree and then `git worktree prune`, printing `removed`, `failed` and `pruned` rows. It never passes `--force`, so git still refuses a tree that changed since the check, and the branch refs stay; ignored files go with the tree (git's rule for `worktree remove`). A path argument narrows the run and is refused with exit 2 outside `.claude/worktrees/`. `origin/main` is read as it is, so run `git fetch origin` first. `tests/unit/test_worktree_gc.py` runs it in a scratch repository with a fake `gh` and a `git` wrapper that logs every argv.
