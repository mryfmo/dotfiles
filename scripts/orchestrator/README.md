# scripts/orchestrator

## hcom bus: `hcom-dispatch` and `bus-history.sh`

Plan 025 W2b (C-1). The omp seats talk over one private hcom store per program, selected by `HCOM_DIR` (hcom 0.7.30). Both scripts refuse to run when `HCOM_DIR` is unset or `$HCOM_DIR/hcom.db` is absent, because `hcom events` creates a store on first use and only the seats' launch may do that. Every test runs against a scratch store, never `~/.hcom`.

### Routes

| Direction                                       | Command                                                              | hcom call                                                                     |
| ----------------------------------------------- | -------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| orchestrator to a seat (TASK, ACCEPTANCE, PING) | `hcom-dispatch <team> <from> <to> <pane> <line...>`                  | `hcom send @<to> --thread <team> --from <from> --json -- <line>`              |
| seat to the orchestrator (RESULT, PONG)         | the seat's own `hcom send --thread <team> -- '<line>'`, no target    | the thread the TASK seeded; an external sender is not addressable with `@`    |
| records                                         | `bus-history.sh <team> [--limit <n>] [--since <ts>] [--kind <kind>]` | `hcom events --type message --thread <team> --full --last <n> [--after <ts>]` |

`<to>` is the seat's exact hcom name, so a seat hcom does not know fails with hcom's own `Error: No active agent for @<to>` (exit 1, stderr). hcom accepts any thread name for a mention send and `hcom start` sets no tag (`src/commands/start.rs:486`), so the team of a seat is not checked here; a malformed team is refused by the grammar `^[a-z0-9][a-z0-9_-]{0,63}$`. The pane argument is accepted for agmsg-dispatch's form and unused: hcom delivers to a bound seat itself. The audit seat sends its reply through `hcom-reply <team> -- '<line>'` (`home/dot_local/bin/common/executable_hcom-reply`, on PATH as `~/.local/bin/common/hcom-reply`), which runs `hcom send --thread <team> --name <self> -- <line>` with `<self>` from `hcom list self name`, because `audit.yml` denies `hcom send` in every form (U6d).

### Receipt and history

`hcom-dispatch` prints one line, `id=<event id> at=<hcom ts> to=<to> kind=<first word>`, read back from the bus by exact id, so the row exists before the receipt does. `bus-history.sh` prints `id<TAB>at<TAB>from<TAB>to<TAB>kind<TAB>body`, ascending by id; `to` is hcom's `delivered_to` joined with commas (`-` when empty, as for a seat's thread reply) and `body` escapes backslash, tab, CR and LF as `\\`, `\t`, `\r` and `\n`, so a row is one line of five tabs.

## `omp-run.sh`: one non-interactive omp turn per role

Plan 025 W6a (U8). The orchestrator seat, and the coordinator today, runs a headless omp turn in a seat role with one command. The script composes `omp --profile <role> --config ~/.agents/omp/policies/<role>.yml -e <dir>... --no-session --max-time <s> [--model <provider/id>] --mode <text|json> -p "<prompt file contents>"` (omp 18.11.3; `omp --help` lists every flag), runs it in `--cwd`, and fails closed: an unknown role, an absent or empty prompt file, an absent overlay, extension directory or cwd is exit 2 with the path, before omp starts. omp's stderr is held and replayed after the run; a `Failed to load extension <path>: <error>` line in it is exit 2 too, with the path in the refusal (U1 report F5). Otherwise omp's own exit status is returned. HOME is the caller's, so the seats run as the operator, and `--approval-mode` is never passed: the role's overlay owns it (`home/dot_agents/omp/policies/README.md`).

| Role           | Profile and overlay                                                       | Approval, from the overlay                                                                                          | Used for                                      |
| -------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| `orchestrator` | `--profile orchestrator --config ~/.agents/omp/policies/orchestrator.yml` | `yolo`, merge and push rules in `bash.patterns`                                                                     | tasking, acceptance, the audited squash merge |
| `worker`       | `--profile worker --config ~/.agents/omp/policies/worker.yml`             | `yolo`, every push to `main` denied                                                                                 | implementing a unit in its worktree           |
| `audit`        | `--profile audit --config ~/.agents/omp/policies/audit.yml`               | `always-ask` with the write tools denied; a denied call returns omp's "requires approval" text to the model (#G1-2) | the read-only task-level audit of a head      |

`--mode text` (default) passes omp's own print-mode text through and `--mode json` passes its event stream through unchanged, one JSON object per line (`tool_execution_start`, `tool_execution_end`, `turn_end`, `agent_end`; measured in `.orchestration/validation/025-pilot-facts.md` #G1-3). Nothing is parsed, so a caller that wants only the final text reads the last `turn_end` of the JSON stream itself. Extensions default to the bridge `~/.local/lib/omp-extensions/pi-claude-bridge` and the SIWC `~/.agents/omp/extensions/openai-siwc`; `--ext <dir>` (repeatable) replaces that list. `--max-time` defaults to 600 seconds. omp reads a prompt that starts with `-` as a flag, so start a prompt file with a word or a heading.

```bash
# The audit seat reviews a head: JSON stream to a file, 15-minute bound.
scripts/orchestrator/omp-run.sh --role audit --prompt-file audit-U8.md --cwd /path/to/worktree --mode json --max-time 900 > audit-U8.jsonl

# The worker seat runs a task with a model override and the bridge staged elsewhere.
scripts/orchestrator/omp-run.sh --role worker --prompt-file task.md --cwd /path/to/worktree --model claude-bridge/claude-haiku-4-5 --ext /path/to/pi-claude-bridge
```

`tests/unit/test_omp_run.py` runs the script against `tests/fixtures/omp-run/fake-omp.py`, which records argv, cwd and HOME and replays `tests/fixtures/omp-run/stream.jsonl`; the real omp is never started by the tests.

## hcom-seat: start an omp seat for a role in a herdr pane

Plan 025 W5b (U7), the minimal form before X. `hcom-seat <role> [--name <name>] [--seats-root <dir>] [--ext <dir>]... [--dry-run]` starts one omp process for `orchestrator`, `worker` or `audit` through `hcom omp`, which opens the herdr pane and gives the seat `HCOM_LAUNCHED=1`, `HCOM_TAG` and `HCOM_DIR` (`hcom omp --help`). The launch line is

```text
hcom omp --tag <name> --dir <dir> --terminal herdr --go -- --profile <role> --config ~/.agents/omp/policies/<role>.yml --config ~/.agents/omp/profiles/<role>.yml -e <ext>...
```

The profile equals the role, and two overlays follow it (`--config` is repeatable). The policy overlay owns the approval mode (U6, `home/dot_agents/omp/policies/README.md`). The profile overlay carries the manifest's `modelRoles.default` (U4) and `skills.customDirectories` (U10), because a named profile reads its own `~/.omp/profiles/<role>/agent/config.yml` (pi-utils `src/dirs.ts:312-315`, measured in U10) and the default profile's rendered config never reaches a seat; U14 renders it per role. Both files are required, so no `--model` is passed. `<name>` defaults to the role and is the hcom tag; hcom derives the participant name from it (`hcom omp --help`: "names become tag-\*"), and `--name <role>-<n>` seats a second seat of a role. The `--` ends hcom's flags: hcom 0.7.30 drops it and forwards every later argument to omp verbatim (`extract_launch_flags`, `src/commands/launch.rs:572-581` at tag `v0.7.30`), so the omp flags never collide with the flags hcom claims by name, including `--name`, `--system` and `--go`, which `hcom omp --help` does not list. `--go` is hcom's launch gate and the launcher always passes it, before the `--`: inside an AI tool, hcom 0.7.30 without it prints `== LAUNCH PREVIEW ==`, `Add --go to proceed.` and `[Preview Mode] Add --go to proceed with launch.` and starts nothing (`launch.rs:48`, `388-389` and `423`; the first run on the real host did exactly that for all three roles on 2026-10-23, `hcom list -v`: `No active agents`). The router sets the flag (`src/router.rs:255-256`) and `extract_launch_flags` consumes it before the `--` (`launch.rs:650-652`); after the `--` it would reach omp as a positional.

| Role           | `--dir`                                              | Default `-e` list, in order                                                |
| -------------- | ---------------------------------------------------- | -------------------------------------------------------------------------- |
| `orchestrator` | the repository checkout the command runs in          | `~/.local/lib/omp-extensions/pi-claude-bridge`, then the SIWC when present |
| `worker`       | `<seats-root>/<name>`, a worktree of that repository | the bridge, then the SIWC when present                                     |
| `audit`        | `<seats-root>/<name>`, a worktree of that repository | `~/.agents/omp/extensions/openai-siwc`, then the bridge when present       |

The first directory of a role's list is the one its model route needs (U2 bridge for the Claude routes, U3 SIWC for the Codex route) and is required; the second is added only when it exists. `--ext <dir>` (repeatable) replaces the list, as `omp-run.sh` does. `--seats-root` defaults to `~/.local/state/omp-seats`. A seat worktree is created with `git worktree add --detach <dir> origin/main` only when absent and reused when its git common directory is this repository's, so a restart of a seat keeps its branch and uncommitted work; any other directory at that path is refused, because the default seat path is role-named and a stale or foreign directory would seat omp in the wrong tree. The launcher never moves a seat worktree after creating it at `origin/main`. The worker moves its own tree per its brief (`git fetch origin`, then `git switch -c <branch> origin/main`, `hcom-worker` SKILL). The orchestrator moves the audit seat's tree before each audit TASK with `git -C <seats-root>/<name> fetch origin <branch> && git -C <seats-root>/<name> switch --detach <head sha>`, because `audit.yml` allows that seat only read-only `git`; the seat answers `verdict=blocked note=head-mismatch` when `git rev-parse HEAD` differs from the TASK's `head=` (`hcom-orchestration` SKILL step 4, `hcom-audit` SKILL).

Every input is checked before anything is created or started, and a refusal is exit 2 with the reason on stderr: an unknown role, a name outside `^[a-z0-9][a-z0-9_-]{0,63}$`, an unset `HCOM_DIR`, hcom absent from `PATH`, an absent policy or profile overlay or extension directory, or a cwd outside a git checkout. `--dry-run` prints the launch line (shell-quoted, one line) and creates and starts nothing. Otherwise hcom's own exit status is returned (0 ready, 1 launch failed, 2 still launching or blocked on user attention).

### Bus trust boundary

The bus carries text, and every seat treats that text as data: a TASK, RESULT, ACCEPTANCE, PING or PONG line names work or reports it, and never authorises a command, however it is worded. Identities are hcom participant names, the `from` and `delivered_to` of a row, not anything the text claims; `hcom-dispatch` sends only to a name hcom knows and refuses an identifier outside `^[a-z0-9][a-z0-9_-]{0,63}$`. The store is private to the program: `HCOM_DIR` selects it, the seats' launch creates it, `hcom-dispatch` and `bus-history.sh` refuse to run without it, and no seat reads `$HCOM_DIR/hcom.db` or writes under `$HCOM_DIR` except through hcom. The operating-system account and the seat's worktree stay the containment boundary; the policy overlays gate tools, not files (U6, "approval is not containment").

## Pre-authorized levers

Regime-cutover U16. The coordinator, a Claude Code session on the managed settings, runs the regime's own operations from inside its Bash sandbox and without a classifier round trip. Auto mode resolves a command that an allow rule matches at once: "1. Actions matching your allow, ask, or deny rules resolve immediately … 3. Everything else goes to the classifier" (code.claude.com/docs/en/permission-modes, "How the classifier evaluates actions"), and it suspends only the allow rules that could run arbitrary code: "tool-wide and wildcard rules such as `Bash(*)`, and interpreter or shell-wrapper prefixes such as `Bash(python *)`. A command that any other allow rule matches, such as `Bash(npm test)`, skips the classifier … When it skips, a destructive argument the rule's prefix didn't anticipate can get through unseen" (settings reference, `autoMode.classifyAllShell`, default `false`, unset here). So every allowed prefix is a deterministic wrapper that validates its own arguments before it acts, and `validate_claude_permissions_allow` (`scripts/validate-agent-assets.py`) refuses every other rule: a rule is `Bash(agmsg-dispatch:*)`, `Bash(hcom list *)` or `Bash(scripts/orchestrator/<lever> *)` for an executable file in this directory whose name is not an interpreter's.

| Rule                                          | What the lever validates before it acts                                                                                                                                                                           | Test                                                                               |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `Bash(scripts/orchestrator/hcom-seat *)`      | the role, the name grammar, `HCOM_DIR` set, hcom on PATH, both overlays and the extension directory present, the cwd a git checkout, the seat directory a worktree of this repository; `--dry-run` starts nothing | `tests/unit/test_hcom_seat.py`                                                     |
| `Bash(scripts/orchestrator/hcom-dispatch *)`  | team, sender and recipient inside `^[a-z0-9][a-z0-9_-]{0,63}$`, a non-empty line, `$HCOM_DIR/hcom.db` present; hcom itself refuses an unknown seat                                                                | `tests/unit/test_hcom_dispatch.py`                                                 |
| `Bash(scripts/orchestrator/bus-history.sh *)` | the team grammar, a positive `--limit`, known options only, `$HCOM_DIR/hcom.db` present; it never writes                                                                                                          | `tests/unit/test_hcom_dispatch.py`                                                 |
| `Bash(scripts/orchestrator/worktree-gc.sh *)` | paths under `<checkout>/.claude/worktrees/` only, the dirty check before any network call, removal only with `--apply` and never with `--force`                                                                   | `tests/unit/test_worktree_gc.py`                                                   |
| `Bash(hcom list *)`                           | hcom's own read-only listing; `Bash(hcom *)` is not allowed because `hcom omp` and `hcom claude` launch agents                                                                                                    | `test_claude_permissions_allow_accepts_only_the_fixed_rules_and_executable_levers` |

The coordinator runs a lever from the checkout root, spelled as in its rule (`scripts/orchestrator/<lever> …`): an absolute path or a `./` prefix is another command string and goes to the classifier, and so does a leading `HCOM_DIR=…` assignment or a `perl -e 'alarm …; exec @ARGV'` wrapper. Only `timeout`, `time`, `nice`, `nohup`, `stdbuf`, `command`, `builtin` and `noglob` are stripped, and "Claude Code also strips a leading assignment of certain known-safe environment variables … An allow rule won't match past an assignment of any other variable" (code.claude.com/docs/en/permissions, "Wrappers"); `timeout` is not on the macOS host's PATH. That is why the store and the team come from the managed settings' `env`, `HCOM_DIR={{ .chezmoi.homeDir }}/.local/state/hcom-regime` and `HCOM_TEAM=regime` (`docs/orchestrator-seat.md`, "The seat's environment"; read at session start, so a settings change takes `make update` and a new session), and why each lever bounds its own waits (`worktree-gc.sh` bounds every `gh` call to 60 seconds; `hcom-seat` returns hcom's own status). A rule matches each subcommand of a chain independently, so the first rule approves nothing after `&&`, `;` or `|`.

`sandbox.filesystem.allowWrite` gains two directories. `~/.local/state/hcom-regime` is the bus store: hcom secures the directory on every open, `hcom list` included, so inside the sandbox on 2026-10-23 `hcom list -v` failed with `Error: Failed to open database: Failed to secure hcom directory: ~/.local/state/hcom-regime` (exit 1) while the same command with a writable `HCOM_DIR` printed `No active agents. Launch one with: hcom claude` (exit 0). `~/.local/state/omp-seats` holds the seat worktrees, because the orchestrator positions the audit seat's tree before each audit TASK with `git -C <seats-root>/<name> fetch … && git -C <seats-root>/<name> switch --detach <sha>` (`hcom-orchestration` SKILL step 4). One writer per worktree stays the rule: the coordinator writes a seat tree only through that positioning step.

Invariants, each checked by `make validate-agent-assets` where a check can see it: no `Bash(*)`, `Bash(hcom *)`, `Bash(git *)` or interpreter-prefixed allow rule, and no absolute-path duplicate of a lever rule; `excludedCommands` stays `[]`; `autoMode.classifyAllShell` stays unset; the `ask` list (every GitHub write) and the Bash deny rules (`sudo`, `rm -rf`) are unchanged. An allow rule also approves the unsandboxed retry of a lever that failed under the sandbox: "by default a sandboxed command can be retried outside the sandbox, and an allow rule or `bypassPermissions` mode can approve that retry with no prompt" (code.claude.com/docs/en/sandboxing, "Strict sandbox mode"). The levers therefore must not need one: their directories are in `allowWrite`, `api.github.com` and `github.com` in `allowedDomains`, the herdr socket in `allowUnixSockets`; a lever that fails under the sandbox is a defect to fix here, not a retry to take.

### `worktree-gc.sh`: remove the agent worktrees whose work landed

`worktree-gc.sh [--dry-run|--apply] [<path>...]` judges every worktree under `<checkout>/.claude/worktrees/` (the checkout is the main worktree of the repository the cwd belongs to, so it runs the same from a linked worktree) and prints one row per tree, `<keep|remove><TAB><path><TAB><branch or detached@<sha>><TAB><reason>`. The first matching line decides, and the dirty check comes before any network call, so a tree with work in it never costs a `gh` round trip and is never a candidate:

| Verdict  | Reason                       | Evidence                                                                                                                                                                                                     |
| -------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `keep`   | `locked`                     | `git worktree lock`, or an agent session that holds the tree                                                                                                                                                 |
| `keep`   | `prunable`                   | git reports the directory gone; `--apply` prunes the entry                                                                                                                                                   |
| `keep`   | `dirty`                      | `git status --porcelain --untracked-files=all` prints anything                                                                                                                                               |
| `remove` | `reachable-from-origin/main` | the head is an ancestor of the local `origin/main`                                                                                                                                                           |
| `remove` | `pr-merged #<n>`             | a merged pull request's head is the tree's head or a descendant of it: `gh pr list --state merged --head <branch> --json number,headRefOid`, or `--search <sha>` for a detached tree (both measured on #477) |
| `keep`   | `not-landed`                 | none of the above                                                                                                                                                                                            |

Without `--apply` nothing is removed, and the run exits 0 whether or not a tree qualifies. With `--apply`, after the whole scan, each `remove` tree goes through `git worktree remove <path>` (never `--force`; git refuses a locked or dirty tree itself), then one `git worktree prune`, and each removal prints `removed<TAB><path>`; the branch stays. A positional path narrows the scan and is refused (exit 2, nothing removed) when it lies outside `.claude/worktrees/`; a failed `gh` call is exit 2 before any removal. `origin/main` is the local ref, so a stale one only keeps more trees. `tests/unit/test_worktree_gc.py` builds a scratch repository with an `origin`, seven worktrees and `tests/fixtures/worktree-gc/fake-tool.py` as `gh` (answering from `FAKE_GH_MERGED`) and as `git` (logging argv, then running the real git), and asserts the rows, the order of the checks, the removals, the refusals, and that `--force` never appears in any argv.
