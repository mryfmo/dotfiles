# scripts/orchestrator

## hcom bus: `hcom-dispatch` and `bus-history.sh`

Plan 025 W2b (C-1). The omp seats talk over one private hcom store per program, selected by `HCOM_DIR` (hcom 0.7.30 and 0.7.31). Both scripts read the store from `HCOM_DIR` when it is set, else derive it from the checkout they run in (`regime-env`, U33: `~/.local/state/hcom/<slug>`, section "regime-init and regime-env"), and refuse to run when that store's `hcom.db` is absent, because `hcom events` creates a store on first use and only the seats' launch may do that. Every test runs against a scratch store, never `~/.hcom`.

### Routes

| Direction                                       | Command                                                              | hcom call                                                                     |
| ----------------------------------------------- | -------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| orchestrator to a seat (TASK, ACCEPTANCE, PING) | `hcom-dispatch <team> <from> <to> <pane> <line...>`                  | `hcom send @<to> --thread <team> --from <from> --json -- <line>`              |
| seat to the orchestrator (RESULT, PONG)         | the seat's own `hcom send --thread <team> -- '<line>'`, no target    | the thread the TASK seeded; an external sender is not addressable with `@`    |
| records                                         | `bus-history.sh <team> [--limit <n>] [--since <ts>] [--kind <kind>]` | `hcom events --type message --thread <team> --full --last <n> [--after <ts>]` |

`<to>` is the seat's exact hcom name, so a seat hcom does not know fails with hcom's own `Error: No active agent for @<to>` (exit 1, stderr). hcom accepts any thread name for a mention send and `hcom start` sets no tag (`src/commands/start.rs:486`), so the team of a seat is not checked here; a malformed team is refused by the grammar `^[a-z0-9][a-z0-9_-]{0,63}$`. The pane argument is accepted and unused: hcom delivers to a bound seat itself. The audit is no seat and has no route: each audit is one `omp-run.sh --role audit` run whose verdict the orchestrator reads from its stdout (U57); the audit seat's `hcom-reply` lever was removed with the seat (U58).

### Line kinds

A bus line's first word is its kind, and the levers treat it as an opaque word (`bus-history.sh --kind` matches it exactly):

| Kind      | Sent by          | Carries                                                                                                  |
| --------- | ---------------- | -------------------------------------------------------------------------------------------------------- |
| `TASK`    | the orchestrator | `task_id`, `brief=`, `branch=`; a fix unit's `findings=`                                                 |
| `RESULT`  | a worker seat    | `task_id`, `status=`, `pr=`, `head=`                                                                     |
| `VERDICT` | the orchestrator | `task_id`, `verdict=` (`correct` or `incorrect`; a `blocked` audit run sends none), `head=`, `findings=` |
| `PONG`    | any seat         | `task_id`, `status=` (below) and a one-sentence `note=`                                                  |
| `MERGED`  | the orchestrator | `task_id`, `sha=` of the merge commit                                                                    |
| `HOLD`    | the orchestrator | `task_id`, `note=` why the task waits                                                                    |

The kinds carry no prefix (U35). A seat that still writes the retired `AGMSG-` prefix (`AGMSG-TASK`, ...) is read the same by the stop gate, which strips it before it looks the kind up; `bus-history.sh --kind` treats the two spellings as different words. A worker's `PONG` carries `status=blocked` or `status=question` (the `hcom-worker` skill, "Blocked"), and no `PONG` moves a task in the stop gate. The audit seat's PONG statuses (`status=findings` and the measurement requests `measure-request`, `measured`, `measure-refused`) left with the seat (U58): a runtime claim an audit run cannot check is one of its findings, which the orchestrator reproduces in a `git archive` copy of the head (the `hcom-orchestration` skill, step 4).

### Receipt and history

`hcom-dispatch` prints one line, `id=<event id> at=<hcom ts> to=<to> kind=<first word>`, read back from the bus by exact id, so the row exists before the receipt does. `bus-history.sh` prints `id<TAB>at<TAB>from<TAB>to<TAB>kind<TAB>body`, ascending by id; `to` is hcom's `delivered_to` joined with commas (`-` when empty, as for a seat's thread reply) and `body` escapes backslash, tab, CR and LF as `\\`, `\t`, `\r` and `\n`, so a row is one line of five tabs.

## `omp-run.sh`: one non-interactive omp turn per role

Plan 025 W6a (U8). The orchestrator seat, and the coordinator today, runs a headless omp turn in a seat role with one command. The script composes `omp --profile <role> --config ~/.agents/omp/policies/<role>.yml --config ~/.agents/omp/profiles/<role>.yml -e <dir>... --no-session --max-time <s> [--model <provider/id>] --mode <text|json> -p "<prompt file contents>"` (omp 18.11.3; `omp --help` lists every flag), runs it in `--cwd`, and fails closed: an unknown role, an absent or empty prompt file, an absent policy or profile overlay, extension directory or cwd is exit 2 with the path, before omp starts. The two overlays are the ones `hcom-seat` passes every role ("`hcom-seat`" below): the profile overlay carries the manifest's `modelRoles.default` for the role, which a named profile reads nowhere else. omp's stderr is held and replayed after the run; a `Failed to load extension <path>: <error>` line in it is exit 2 too, with the path in the refusal (U1 report F5). Otherwise omp's own exit status is returned. HOME is the caller's, so the seats run as the operator, and `--approval-mode` is never passed: the role's overlay owns it (`home/dot_agents/omp/policies/README.md`).

| Role           | Profile and overlays                                                                                                        | Approval, from the overlay                                                                                          | Used for                                      |
| -------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| `orchestrator` | `--profile orchestrator --config ~/.agents/omp/policies/orchestrator.yml --config ~/.agents/omp/profiles/orchestrator.yml`  | `yolo`, merge and push rules in `bash.patterns`                                                                     | tasking, acceptance, the audited squash merge |
| `worker`       | `--profile worker --config ~/.agents/omp/policies/worker.yml --config ~/.agents/omp/profiles/worker.yml`                    | `yolo`, every push to `main` denied                                                                                 | implementing a unit in its worktree           |
| `audit`        | `--profile audit --config ~/.agents/omp/policies/audit.yml --config ~/.agents/omp/profiles/audit.yml`, plus the third below | `always-ask` with the write tools denied; a denied call returns omp's "requires approval" text to the model (#G1-2) | the read-only task-level audit of a head      |

`--role audit` is the audit path (`hcom-orchestration` SKILL, step 4): one run per head, fresh by `--no-session`, never a long-lived seat that carries earlier audits in its context. Its `--cwd` is a worktree at the head, read as data only. The rules are the whole `AGENTS.md` of `refs/remotes/origin/main` in that repository (`git show`; the full ref, so a tag or a local branch named `origin/main` cannot stand in for it), put before the caller's prompt between `<base-rules>` tags, so a pull request cannot rewrite its own auditor's rules; Claude Code Review likewise reads its instructions "from the base or default branch and never from the pull request's own changes" (https://code.claude.com/docs/en/code-review). omp reads project context (context files such as `AGENTS.md`, rules such as `.clinerules` and `.agent/rules`, skills, settings, hooks, tools, MCP servers) from its cwd and the cwd's ancestors through the discovery providers of its capability registry (omp 18.11.3 `src/discovery/index.ts`), and its `disabledProviders` setting switches a provider off for user and project scope alike (`src/capability/index.ts` `filterProviders`). So omp never runs in the head, and runs with every provider off: the script reads the registry's provider ids with `bun` from the `src/discovery/index.ts` of the package `omp` resolves to (`getAllProvidersInfo`; omp itself runs on bun), adds the entries the two overlays already disable (a later overlay's list replaces an earlier one), and passes that `disabledProviders` as a third `--config`. A name list of context files would miss the next provider; the registry cannot. bun is the PATH entry made absolute, never dereferenced: mise's bun shim is a symlink to the mise executable, which acts as bun only under that name and rejects `--no-install` under its own. The model, the policy and the `-e` extensions do not come from discovery and stay. One more reader sits outside the providers: the task tool's agent list (`src/task/discovery.ts`, every `.omp/agents/*.md` in the cwd's ancestors), which `TaskTool.create` puts into the task tool's description. So the audit also passes `--tools=read,grep,glob,bash`, the read tools `audit.yml` lets run and no tool it denies: `resolveBuiltinToolPlan` (`src/tools/index.ts`) builds only the listed tools, so the task tool, and with it the agent scan, never exists in the run. omp runs in `<scratch>/cwd`, an empty directory, `<scratch>` made directly in `TMPDIR` (default `/tmp`; made absolute with `pwd -P` and exported so, so the exit trap removes the right directory after the `cd` and omp's `os.tmpdir()` is absolute), with `GIT_DIR` and `GIT_WORK_TREE` naming the worktree; omp's plugin registry walk, which no provider gates, stops before `TMPDIR` (`src/discovery/helpers.ts` `getProjectDiscoveryCeilings`). `<scratch>` is removed on exit, a failed `realpath` of it included. A cwd outside git, an absent `refs/remotes/origin/main`, no `AGENTS.md` there, bun absent, no registry beside omp, no provider list from it or a `TMPDIR` that cannot be made absolute are exit 2 before omp starts.

Measured 2026-10-25 with the real omp 18.11.3 (no model call: a shim ran omp-run.sh's exact argv with `--mode rpc` and one `get_state` in place of `--mode json -p`, and read the assembled `systemPrompt`): with `AGENTS.md`, an `alwaysApply` `.clinerules`, an `alwaysApply` `.agent/rules/planted.md`, a `.omp/config.yml` and a `.claude/settings.json` (both `disabledProviders: []`) in the parent of `TMPDIR`, the run without the third overlay loaded all three planted texts and the run with it loaded none; both resolved the model `openai-siwc/gpt-6-astra` from the audit profile overlay through the SIWC extension. `--mode text` (default) passes omp's own print-mode text through and `--mode json` passes its event stream through unchanged, one JSON object per line (`tool_execution_start`, `tool_execution_end`, `turn_end`, `agent_end`; measured in `.orchestration/validation/025-pilot-facts.md` #G1-3). Nothing is parsed, so a caller that wants only the final text reads the last `turn_end` of the JSON stream itself. Extensions default to the bridge `~/.local/lib/omp-extensions/pi-claude-bridge` and the SIWC `~/.agents/omp/extensions/openai-siwc`; `--ext <dir>` (repeatable) replaces that list. `--max-time` defaults to 600 seconds. omp reads a prompt that starts with `-` as a flag, so start a prompt file with a word or a heading.

```bash

scripts/orchestrator/omp-run.sh --role audit --prompt-file audit-U8.md --cwd /path/to/worktree-at-head --max-time 1800 > verdicts/U8-<head>.md

# The worker seat runs a task with a model override and the bridge staged elsewhere.
scripts/orchestrator/omp-run.sh --role worker --prompt-file task.md --cwd /path/to/worktree --model claude-bridge/claude-haiku-4-5 --ext /path/to/pi-claude-bridge
```

## hcom-seat: start an omp seat for a role in a herdr pane

Plan 025 W5b (U7), the minimal form before X. `hcom-seat <role> [--name <name>] [--seats-root <dir>] [--ext <dir>]... [--dry-run]` starts one omp process for `orchestrator` or `worker` through `hcom omp`, which opens the herdr pane and gives the seat `HCOM_LAUNCHED=1`, `HCOM_TAG` and `HCOM_DIR` (`hcom omp --help`). There is no audit seat: `hcom-seat audit` is refused as an unknown role, and every audit is one `omp-run.sh --role audit` run (U57, U58). The launch line is

```text
hcom omp --tag <name> --dir <dir> --terminal herdr --go -- --profile <role> --config ~/.agents/omp/policies/<role>.yml --config ~/.agents/omp/profiles/<role>.yml -e <ext>...
```

The profile equals the role, and two overlays follow it (`--config` is repeatable). The policy overlay owns the approval mode (U6, `home/dot_agents/omp/policies/README.md`). The profile overlay carries the manifest's `modelRoles.default` (U4) and `skills.customDirectories` (U10), because a named profile reads its own `~/.omp/profiles/<role>/agent/config.yml` (pi-utils `src/dirs.ts:312-315`, measured in U10) and the default profile's rendered config never reaches a seat; U14 renders it per role. Both files are required, so no `--model` is passed. `<name>` defaults to the role and is the hcom tag; hcom derives the participant name from it (`hcom omp --help`: "names become tag-\*"), and `--name <role>-<n>` seats a second seat of a role. The `--` ends hcom's flags: hcom 0.7.30 and 0.7.31 drop it and forward every later argument to omp verbatim (`extract_launch_flags`, `src/commands/launch.rs:572-581` at tag `v0.7.30`), so the omp flags never collide with the flags hcom claims by name, including `--name`, `--system` and `--go`, which `hcom omp --help` does not list. `--go` is hcom's launch gate and the launcher always passes it, before the `--`: inside an AI tool, hcom 0.7.30 without it prints `== LAUNCH PREVIEW ==`, `Add --go to proceed.` and `[Preview Mode] Add --go to proceed with launch.` and starts nothing (`launch.rs:48`, `388-389` and `423`; the first run on the real host did exactly that for all three roles on 2026-10-23, `hcom list -v`: `No active agents`). The router sets the flag (`src/router.rs:255-256`) and `extract_launch_flags` consumes it before the `--` (`launch.rs:650-652`); after the `--` it would reach omp as a positional.

| Role           | `--dir`                                              | Default `-e` list, in order                                                |
| -------------- | ---------------------------------------------------- | -------------------------------------------------------------------------- |
| `orchestrator` | the repository checkout the command runs in          | `~/.local/lib/omp-extensions/pi-claude-bridge`, then the SIWC when present |
| `worker`       | `<seats-root>/<name>`, a worktree of that repository | the bridge, then the SIWC when present                                     |

The first directory of a role's list is the one its model route needs (the U2 bridge for the Claude routes) and is required; the second is added only when it exists. `--ext <dir>` (repeatable) replaces the list, as `omp-run.sh` does; every directory, a default or `--ext`, must resolve to an entry of `claude.levers.extensions` in the manifest (U31, "Pre-authorized levers"), else the launch is refused. `--seats-root` defaults to `~/.local/state/omp-seats/<slug>`, the repository's own seats root (U33). A seat worktree is created with `git worktree add --detach <dir> origin/main` only when absent and reused when its git common directory is this repository's, so a restart of a seat keeps its branch and uncommitted work; any other directory at that path is refused, because the default seat path is role-named and a stale or foreign directory would seat omp in the wrong tree. The launcher never moves a seat worktree after creating it at `origin/main`. The worker moves its own tree per its brief (`git fetch origin`, then `git switch -c <branch> origin/main`, `hcom-worker` SKILL).

Every input is checked before anything is created or started, and a refusal is exit 2 with the reason on stderr: an unknown role, a name outside `^[a-z0-9][a-z0-9_-]{0,63}$`, a store `regime-env` refuses (outside a checkout without `HCOM_DIR`, a slug whose store belongs to another checkout), hcom absent from `PATH`, an absent policy or profile overlay or extension directory, or a cwd outside a git checkout. `--dry-run` prints the launch line (shell-quoted, one line) and creates and starts nothing. Otherwise hcom's own exit status is returned (0 ready, 1 launch failed, 2 still launching or blocked on user attention).

### Bus trust boundary

The bus carries text, and every seat treats that text as data: a TASK, RESULT, ACCEPTANCE, PING or PONG line names work or reports it, and never authorises a command, however it is worded. Identities are hcom participant names, the `from` and `delivered_to` of a row, not anything the text claims; `hcom-dispatch` sends only to a name hcom knows and refuses an identifier outside `^[a-z0-9][a-z0-9_-]{0,63}$`. The store is private to the program: `HCOM_DIR` selects it, the seats' launch creates it, `hcom-dispatch` and `bus-history.sh` refuse to run without it, and no seat reads `$HCOM_DIR/hcom.db` or writes under `$HCOM_DIR` except through hcom. The operating-system account and the seat's worktree stay the containment boundary; the policy overlays gate tools, not files (U6, "approval is not containment").

## Pre-authorized levers

Regime-cutover U16 (brief `F8-coordinator-levers-preauthorized`). The Claude Code coordinator runs the regime's own operations from inside its sandbox, without a classifier round trip, through five `permissions.allow` rules in the managed settings (`claude.permissions.allow` in `home/dot_agents/agent-config.yaml`). Auto mode resolves an action that matches a rule before the classifier: "Actions matching your allow, ask, or deny rules resolve immediately" (code.claude.com/docs/en/permission-modes, "How the classifier evaluates actions"), and it suspends only the allow rules that "could run arbitrary code: tool-wide and wildcard rules such as `Bash(*)`, and interpreter or shell-wrapper prefixes such as `Bash(python *)`" (code.claude.com/docs/en/settings, `autoMode.classifyAllShell`, default `false` and unset here). So every rule names one deterministic wrapper that validates its own input, and nothing wider.

Since U31 each lever rule names the copy chezmoi installs under `~/.local/bin/common`, outside every sandbox write root: the generator renders `home/dot_local/bin/common/executable_<lever>` from `scripts/orchestrator/<lever>` (same bytes) and pins its sha256 as `claude.levers.sha256.<lever>` in the manifest. At start each lever hashes its own bytes and compares the digest with its pin in the manifest beside it, the deployed `~/.agents/agent-config.yaml` for the installed copy; a mismatch, a missing pin or any failed read exits 2 naming the file. `hcom-seat` loads only the directories in `claude.levers.extensions`. So the rules render on Linux and WSL2 too; until U31 part 2, part 1 rendered them into the darwin variant only (`claude.permissions.darwin_allow`, D-024-144).

### `worktree-gc.sh`

`scripts/orchestrator/worktree-gc.sh [--apply] [<path>...] | --purge <days>` reads `git worktree list --porcelain -z` and considers only the worktrees under `<toplevel>/.claude/worktrees/`, except those in its quarantine `.claude/worktrees/.gc-quarantine/`, which are never candidates (a path argument there is refused with exit 2). A worktree qualifies when `git status --porcelain --ignored=matching --untracked-files=all` prints nothing and its work landed: its head is reachable from `origin/main`; it landed by content, meaning every path `git diff --no-renames --name-only -z <merge-base> <head>` names holds in `origin/main` the `git ls-tree -r` entry (mode and object) it holds in the head, or is absent from both (a squash merge with no later commit); or its head is the `headRefOid` of a merged pull request of this repository (`gh pr list --state merged --head <branch> --json number,headRefOid --limit 100`, detached `--search <sha>`). The content test runs no merge, so a configured merge driver (`merge.default`, a `merge=` attribute) cannot resolve an unlanded conflict to `main`'s tree, and a git failure there is an `error` row that moves nothing. A merged pull request with the branch's name and another head does not count: commits pushed after a squash merge are not in `main`, and `--head` also matches a fork's branch of that name. An ignored file keeps the tree, because `git worktree remove` deletes ignored files and exits 0 (git-worktree(1) defines clean as no untracked files and no tracked modification). A locked or missing worktree is kept. It prints one row per candidate, `<gc|keep|error>\t<path>\t<branch or (detached <sha>)>\t<reason>`, one `quarantine` row per quarantined worktree with its age, then a `summary` row, and exits 0 when nothing qualifies. No check can be made atomic with a deletion (audit rounds U56b and U56c each found a file or commit written between the last check and `git worktree remove`), so taking a tree out of use and deleting it are separate runs, as Codex snapshots a managed worktree before deleting it and Claude Code deletes only after `cleanupPeriodDays`. `--apply` deletes nothing: each qualifying tree is renamed by `git worktree move <path> .gc-quarantine/<random>/<name>` (one rename on the same filesystem, so a process inside keeps its working directory; git refuses a locked tree), `<epoch> <classified head>` is written to `gc-quarantined-at` in its admin directory, and the moved tree is checked again: clean, ignored files included, and its HEAD the classified one. Both hold: a `quarantined` row; either fails (a `.env` written or a commit made while `gh` answered, say): a `held` row with the reason, and the tree stays in the quarantine with that change, never moved back. A refused move is a `failed` row and exit 1. `--purge <days>` reads only the quarantine: an entry whose marker is at least `<days>` days old (`0`: any age) is classified again by the same rules, HEAD read again, then removed with `git worktree remove <path>`, which also removes its admin data; an entry without a marker, younger, locked or no longer qualifying is kept, and a refused removal is a `failed` row and exit 1. Nothing passes `--force`, so git still refuses a tree with tracked or untracked changes, and the branch refs stay. It never runs `git worktree prune`, which would drop the admin data of every worktree whose directory is missing, an unlocked omp seat included. A path argument narrows the listing and `--apply`, and is refused with exit 2 outside `.claude/worktrees/`; `--purge` takes none. `origin/main` is read as it is, so run `git fetch origin` first. `tests/unit/test_worktree_gc.py` runs it in a scratch repository with a fake `gh` and a `git` wrapper that logs every argv.

## Seat levers for GitHub writes

Regime-cutover U28. The GitHub writes the loop needs besides the merge, the worker's push and `gh pr create`/`gh pr comment` run from the omp seat whose role owns them, each through one lever below, so that no step but a login or a Keychain prompt waits for a human. Each is a `scripts/orchestrator/` source with shdoc, installed read-only as `~/.local/bin/common/<lever>` with its `claude.levers.sha256` pin and the U31 self-check, and allowed by name in its role's omp policy (`home/dot_agents/omp/policies/README.md`, "GitHub-write levers (U28)"); the Claude coordinator gets none of them and keeps its `ask` rules. Common to all: `set -euo pipefail`; every argument checked before the first `gh` call; `<owner>/<repo>` from `gh repo view --json nameWithOwner`, never from an argument; each `gh` call bounded by `PR_LEVER_GH_TIMEOUT` seconds (default 60, perl `alarm`); a failed read is exit 1 and writes nothing (`preferences.md` standing order 21); a refusal is exit 2 with `<lever>: refused: <why>` on stderr and no write; the receipt is one line on stdout. No lever passes `--delete-branch`, `--admin` or `--rebase`.

The reply grammar (`preferences.md` standing order 22) is one first line: `fixed: <40-hex sha>`, `refuted: <text citing a URL or a file:line>`, `residual: unit=U<n> gate=<clause>` or `residual: operator=<decisions.tsv ts>`. `pr-thread-reply.sh` posts only such a line. Whether it holds is judged by one function, `disposition`, the same text in `pr-thread-resolve.sh` and `pr-threads-check.sh` (`DispositionDriftTest`): `fixed:` names a local commit in the head and committed after the finding, `refuted:` cites, `residual: unit=` answers a P2 or P3 with its `units.tsv` row, `residual: operator=` has its `decisions.tsv` row. The resolve lever resolves only a thread whose disposition holds, and the merge check applies it to every thread, resolved ones included (U28b F1).

## regime-init and regime-env: the regime in any repository

Regime-cutover U33. The levers no longer assume the dotfiles checkout: they run from `~/.local/bin/common` (U31) and take the program's store, team and seat worktrees from the repository they run in. `regime-env` is the one implementation of that derivation. It is a helper the levers source from the directory they run from (`LEVER_DIR`), pinned and self-checked like a lever but never run, so it has no allow rule. It defines `regime_toplevel`, `regime_slug` and `regime_env`.

| Value       | Default when the environment does not set it                                                                                                                                                                                                                                                                         |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| toplevel    | the main checkout: the parent of the git common directory, so a seat worktree or a `.claude/worktrees/*` worktree derives the same values as the checkout it was added from                                                                                                                                          |
| `<slug>`    | the toplevel's basename, lower-cased, every character outside `[a-z0-9_-]` replaced by `-`, at most 40 characters, refused unless it starts with `[a-z0-9]` (hcom's team and tag grammar)                                                                                                                            |
| `HCOM_TEAM` | `<slug>`                                                                                                                                                                                                                                                                                                             |
| `HCOM_DIR`  | `~/.local/state/hcom/<slug>`, bound to the checkout by its `origin` file: only `regime-init` writes it, and every other lever refuses a derived store without it or with another toplevel in it (two checkouts with one basename). No part of the path (`~/.local/state/hcom`, the store, `origin`) may be a symlink |
| seats root  | `~/.local/state/omp-seats/<slug>` (`hcom-seat --seats-root` overrides)                                                                                                                                                                                                                                               |

An explicit `HCOM_DIR`, `HCOM_TEAM` or `--seats-root` always wins, which is how the dotfiles seats launched before U33 keep their store until the orchestrator moves them. `hcom-seat` exports the derived pair to the seat, so the seat and its stop gate read the same store; `--dry-run` prints the pair on stderr. `hcom-dispatch` and `bus-history.sh` derive the same store and refuse while its `hcom.db` does not exist. A repository whose `refs/remotes/origin/main` is absent seats its worktrees at `HEAD`; a ref that is broken or names no commit, or a failing `git for-each-ref`, is a refusal. hcom does not pass `HCOM_TEAM` into the pane it launches, so `hcom-seat` ends the launch line with `--hcom-team <team>`, exactly the team it was given, and loads the stop gate's directory `~/.agents/omp/hooks` on every launch (in `claude.levers.extensions`, U33c); the gate reads the flag, never a team derived from the cwd, and exports it as `HCOM_TEAM` into the seat.

`regime-init <program> [--force] [--write-agents]`, run in the checkout, creates `.orchestration/orchestrate/<program>/` with the templates from `~/.agents/regime/` (`preferences.md` with the host-independent standing orders, and `units.tsv`, `ledger.tsv`, `decisions.tsv`, `gates.md` with their header rows). It also writes `~/.local/state/hcom/<slug>/origin` with the toplevel, then prints the AGENTS.md audit section, or appends it with `--write-agents` when `AGENTS.md` has no `## Audit` heading, and prints the next commands. A file equal to its template is left alone, one that differs is kept unless `--force` replaces it, and a second run prints `nothing changed`. It never writes through a symlink, and it refuses outside a checkout and on a slug collision.
